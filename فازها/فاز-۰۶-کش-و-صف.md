# فاز ۶ — کش، صف و پردازش پس‌زمینه

> 🧒 **داستان:** در سال ۲۰۰۳ میلادی، وب‌سایت LiveJournal به یکی از شلوغ‌ترین بسترهای وبلاگ‌نویسی جهان بدل شد. ویژگی ساده‌ای در صفحهٔ اول وجود داشت که فهرست کاربران آنلاین را نشان می‌داد. اما برای تولید این ویجت ساده، در هر ثانیه هزاران بار پرس‌وجوی سنگین به پایگاه داده فرستاده می‌شد. سرورهای دیتابیس ساعت‌ها زیر بار این پرسش‌های مکرر و تکراری از کار می‌افتادند.
>
> در ۲۲ مه ۲۰۰۳، برنامه‌نویسی به نام **برد فیتزپاتریک (Brad Fitzpatrick)** ابزاری خلق کرد که رویکرد وب را برای همیشه تغییر داد: **Memcached**. ایده بسیار شفاف بود: داده‌های گران‌قیمت را یک‌بار از دیتابیس بخوان، نتیجه را درون حافظهٔ موقت سریع (RAM) نگه دار و برای مراجعات بعدی مستقیماً از حافظه پاسخ بده — این مفهوم همان **کش (Cache)** است.
>
> چند سال بعد در سال ۲۰۰۹، با ظهور سامانه‌های ابری و فریم‌ورک‌های رویدادمحور، سالواتوره سان‌فیلیپو پروژهٔ **Redis** را معرفی کرد. برنامه‌نویسان دریافتند که بسیاری از کارها (مانند ارسال ایمیل فعال‌سازی، ساخت فایل گزارش PDF یا تبدیل سایز تصاویر) نیازی ندارند در لحظهٔ کلیک کاربر و پیش از ارسال پاسخ HTTP انجام شوند. کارها را می‌توان در یک صف پیام ساختاریافته سپرد تا کارگران پس‌زمینه (Workers) سر فرصت و با تضمین پایداری آن‌ها را اجرا کنند.
>
> این فاز هنر مدیریت زمان و منابع است: یاد می‌گیریم کدام داده‌ها را در حافظه منجمد کنیم تا پایگاه داده نفس بکشد، و کدام وظایف سنگین را از چرخهٔ حیات پاسخ HTTP بیرون کشیده و به صف‌های نامتقارن بسپاریم.

## مقدمه: سه مسئله، یک راه‌حل

در معماری سامانه‌های مدرن، کارایی سیستم بر پایهٔ تفکیک کارهای ضروری از کارهای غیرفوری بنا می‌شود:

| مسئله در دنیای واقعی | مثال ملموس | راهکار مهندسی |
|----------------------|------------|---------------|
| پردازش مکرر داده‌های کم‌تغییر | محاسبهٔ مداوم گزارش آمار پرفروش‌ترین کالاها | **کش کردن (Cache):** ذخیرهٔ موقت نتیجه در حافظهٔ رم |
| عملیات زمان‌بر با معطلی کاربر | ساخت فایل PDF گزارش حسابرسی یا فشرده‌سازی ویدیو | **صف ناهمگام (Background Queue):** پردازش در پس‌زمینه |
| وابستگی به سرویس‌های ناپایدار خارجی | ارسال پیامک درگاه یا ارسال اعلان‌های پرداخت | **صف همراه با آزمون مجدد (Retries + DLQ)** |

> 💡 **قاعدهٔ طلایی پاسخ‌گویی وب:** آنچه کاربر برای دیدن نتیجه‌اش ناگزیر به انتظار است، در مسیر مستقیم درخواست بماند؛ هر کاری که کاربر نیازی به معطلی در لحظه برای آن ندارد، باید بلافاصله به صف پس‌زمینه سپرده شود.

## ۱. کش (Cache) — چرا وجود دارد؟

> 🧒 **داستان این بخش:** یک رستوران محبوب را در نظر بگیر؛ اگر سرآشپز برای هر پرس خورشت قورمه‌سبزی، از اول دیگ را بار بگذارد و پیاز داغ کند، هر مشتری باید سه ساعت برای غذایش منتظر بماند. راهکار عقلانی این است که ظرفی آماده از خورشت روی پیشخوان گرم نگه داشته شود تا سفارش‌ها در کمتر از ۳۰ ثانیه تحویل گردند.
>
> در دنیای وب، پرس‌وجوهای پیچیدهٔ دیتابیس و اتصالات به APIهای ثالث درست مانند همان پخت سه ساعته هستند؛ نگهداری پاسخ آماده درون حافظهٔ موقت Redis زمان سرویس‌دهی را از صدها میلی‌ثانیه به کسری از میلی‌ثانیه کاهش می‌دهد.
>
> **این بخش جواب می‌دهد:** کش کردن برای چه سناریوهایی مناسب است و چرا کش هرگز نباید پایگاه دادهٔ اصلی سامانه تلقی شود.

### فلسفهٔ سلسله‌مراتب حافظه

دسترسی به داده‌ها در رم (RAM) صدها برابر سریع‌تر از خواندن داده‌ها از دیسک‌های SSD یا شبکه‌های ذخیره‌سازی ابری است. کش کردن یعنی قرار دادن داده‌های پرتقاضا در سریع‌ترین لایهٔ ممکن.

| سناریوی عملیاتی | زمان واکشی خام | صرفهٔ کش‌گذاری |
|-----------------|----------------|---------------|
| کوئری پیچیده با JOIN‌های چندگانه | ۵۰ تا ۵۰۰ میلی‌ثانیه | بسیار بالا |
| فراخوانی API سرویس‌های شخص ثالث | ۲۰۰ تا ۲۵۰۰ میلی‌ثانیه | حیاتی |
| گزارش‌های آماری و داشبوردهای تحلیلی | ۱ تا ۱۰ ثانیه | اجباری |
| خواندن یک رکورد ساده بر اساس کلید اصلی | ۲ تا ۵ میلی‌ثانیه | متوسط (در ترافیک بالا ضروری) |

> 🔑 **قاعده:** اگر هزینهٔ بازتولید یا واکشی یک داده به مراتب بیشتر از هزینهٔ نگهداری آن در حافظه باشد و داده تغییرات لحظه‌ای نداشته باشد، کش کردن آن بهترین تصمیم مهندسی است.

## ۲. الگوی Cache-Aside

> 🧒 **داستان این بخش:** کارمندی را تصور کن که هر بار پرونده‌ای می‌خواهد، ابتدا کشوی دم دستش را نگاه می‌کند؛ اگر پرونده آنجا بود، بلافاصله کار را پیش می‌برد. اگر نبود، به بایگانی مرکزی در زیرزمین می‌رود، پرونده را می‌آورد، یک نسخه از آن را در کشوی میزش می‌گذارد و سپس به مشتری پاسخ می‌دهد.
>
> این شیوه در مهندسی نرم‌افزار **الگوی Cache-Aside (یا بارگذاری تنبل - Lazy Loading)** نام دارد: برنامه خود واسط میان حافظهٔ موقت و دیتابیس است و کش به مرور زمان با داده‌های واقعی پر می‌شود.
>
> **این بخش جواب می‌دهد:** گام‌های پیاده‌سازی Cache-Aside چیست و پدیدهٔ خطرناک طوفان گله (Thundering Herd) چگونه رخ می‌دهد.

### چرخهٔ گام‌به‌گام Cache-Aside

۱. **گام اول:** ابتدا کلید مورد نظر از کش (Redis) استعلام می‌شود.
۲. **در صورت رخداد Cache HIT:** داده بلافاصله Parse شده و به کلاینت پاسخ داده می‌شود.
۳. **در صورت رخداد Cache MISS:** داده از پایگاه داده اصلی واکشی می‌شود.
۴. **پر کردن کش:** دادهٔ خوانده‌شده همراه با زمان انقضا (TTL) در کش ذخیره شده و به کاربر بازگردانده می‌شود.

```typescript
import { Redis } from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);

export async function getProductById(productId: string) {
  const cacheKey = `products:${productId}`;

  // ۱. بررسی حافظه کش
  const cachedData = await redis.get(cacheKey);
  if (cachedData) {
    return JSON.parse(cachedData); // Cache HIT
  }

  // ۲. استعلام از پایگاه داده اصلی (Cache MISS)
  const product = await db.products.findById(productId);
  if (!product) return null;

  // ۳. ثبت در کش با زمان انقضای ۵ دقیقه
  await redis.set(cacheKey, JSON.stringify(product), 'EX', 300);

  return product;
}
```

### معضل طوفان گله (Thundering Herd / Cache Stampede)

اگر کلید یک کالای بسیار محبوب با انقضای زمان کش حذف شود و دقیقاً در همان لحظه ۱۰۰۰ درخواست هم‌زمان برای آن کالا وارد سرور گردد، تمامی ۱۰۰۰ درخواست با رخداد Cache MISS روبرو می‌شوند و همگی هم‌زمان به دیتابیس حمله می‌کنند! این هجوم ناگهانی می‌تواند پایگاه داده را کاملاً فلج سازد.

**راهکار: قفل توزیع‌شده با کلید موقت (Mutex Lock)**

```typescript
export async function getProductWithStampedeProtection(productId: string) {
  const cacheKey = `products:${productId}`;
  const lockKey = `locks:${cacheKey}`;

  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  // تلاش برای تصاحب قفل انحصاری با زمان انقضای کوتاه
  const acquiredLock = await redis.set(lockKey, '1', 'EX', 5, 'NX');

  if (!acquiredLock) {
    // قفل در دست درخواست دیگری است؛ ۵۰ میلی‌ثانیه صبر کن و مجدداً کش را چک کن
    await sleep(50);
    const retryCached = await redis.get(cacheKey);
    if (retryCached) return JSON.parse(retryCached);
    return db.products.findById(productId);
  }

  try {
    const product = await db.products.findById(productId);
    if (product) {
      await redis.set(cacheKey, JSON.stringify(product), 'EX', 300);
    }
    return product;
  } finally {
    // آزادسازی قطعی قفل
    await redis.del(lockKey);
  }
}
```

## ۳. استراتژی‌های Eviction — چه چیزی را حذف کنیم وقتی پر شد؟

> 🧒 **داستان این بخش:** کمد لباستان ظرفیت محدودی دارد. وقتی کمد کاملاً پر شد و کت جدیدی می‌خرید، چاره‌ای ندارید جز اینکه یکی از لباس‌های قدیمی را ببخشید. اما کدام لباس را انتخاب می‌کنید؟ لباسی که سه سال است پوشیده نشده، یا پالتویی که همین دیروز به تن کرده‌اید؟
>
> حافظهٔ RAM اختصاص‌یافته به Redis ابعاد مشخصی دارد (مثلاً ۴ گیگابایت). هنگامی که این سقف پر شد، پایگاه داده با **سیاست‌های تخلیه (Eviction Policies)** تعیین می‌کند کدام کلیدها از حافظه به بیرون پرتاب شوند.
>
> **این بخش جواب می‌دهد:** الگوریتم‌های LRU و LFU چه تفاوتی با یکدیگر دارند و تنظیمات مناسب سرور Redis برای جلوگیری از خطای کمبود حافظه چیست.

### سیاست‌های تخلیه حافظه در Redis

| استراتژی | منطق ریاضی | بهترین کاربرد |
|----------|------------|---------------|
| **`allkeys-lru`** | کلیدی که طولانی‌ترین زمان از آخرین استفادهٔ آن گذشته است حذف می‌شود | 🏆 استاندارد طلایی و پیش‌فرض بهترین پروژه‌ها |
| **`volatile-lru`** | الگوریتم LRU تنها روی کلیدهایی که زمان انقضا (TTL) دارند اعمال می‌شود | سناریوهایی که برخی کلیدها باید تا ابد بمانند |
| **`allkeys-lfu`** | کلیدی که در طول تاریخچه، کمترین فراوانی تکرار را داشته حذف می‌شود | داده‌هایی که الگوهای تکرار دائمی دارند |
| **`volatile-ttl`** | کلیدی که کمترین زمان باقی‌مانده تا انقضا را دارد زودتر حذف می‌شود | ترجیح پاک‌سازی داده‌های در آستانهٔ کهنگی |
| **`noeviction`** | هیچ داده‌ای حذف نمی‌شود و در صورت پر شدن حافظه، خطای OOM پرتاب می‌شود | سناریوهایی که پایداری تک‌تک کلیدها حیاتی است |

## ۴. سیاست‌های انقضا (TTL) — مهم‌ترین تصمیم طراحی

> 🧒 **داستان این بخش:** مغازه‌داری را فرض کن که شیرهای پاکتی را داخل یخچال می‌چیند اما تاریخ انقضای آن‌ها را خط می‌زند. دو ماه بعد، مشتری شیری ترشیده تحویل می‌گیرد. اگر تاریخ انقضا (TTL) روی داده‌های کش قرار نگیرد یا زمان آن نامعقول انتخاب شود، سیستم کاربران را با اطلاعات کهنه، اشتباه و فریبنده گمراه خواهد کرد.
>
> **این بخش جواب می‌دهد:** طول عمر مناسب برای انواع داده چیست و چگونه با ابطال فعال (Cache Invalidation) داده‌های کهنه را فورا از چرخه خارج سازیم.

### انتخاب زمان انقضای متناسب (TTL)

- **داده‌های تقریباً ایستا (مشخصات استان‌ها و شهرها):** ۱ تا ۲۴ ساعت.
- **اطلاعات محصولات و ویترین فروشگاه:** ۱۰ دقیقه تا ۱ ساعت.
- **داشبوردهای تحلیلی و آماری:** ۱ تا ۵ دقیقه.
- **قیمت لحظه‌ای طلا، رمزارز یا موجودی بلیت هواپیما:** ۵ تا ۳۰ ثانیه (یا ترجیحاً عدم کش‌گذاری مستقیم).

### راهبرد مکمل: ابطال فعال (Proactive Invalidation)

توسعه‌دهنده نباید صرفاً منتظر فرا رسیدن زمان انقضا بنشیند؛ هر زمان داده‌ای در پایگاه داده ویرایش یا حذف شد، باید کلید کش متناظر بلافاصله نابود شود:

```typescript
export async function updateProduct(productId: string, updateData: any) {
  // ۱. اعمال تغییر در پایگاه داده اصلی
  const updatedProduct = await db.products.update(productId, updateData);

  // ۲. ابطال بلافاصلهٔ کلیدهای کش متأثر
  await redis.del(`products:${productId}`);
  await redis.del('products:featured_list');

  return updatedProduct;
}
```

## ۵. Cache Stampede در برابر Cache Penetration

> 🧒 **داستان این بخش:** سامانه‌ای را در نظر بگیر که هدف حمله قرار گرفته است؛ فردی اسکریپتی می‌نویسد که شناسه‌های ناموجود (مانند کاربر با آیدی ۹۹۹۹۹۹۹) را مدام استعلام می‌کند. این شناسه درون کش نیست؛ سرور به دیتابیس سر می‌زند و چیزی نمی‌یابد. درخواست دوم باز هم کش را خالی می‌یابد و مجدداً به دیتابیس می‌رود. در نتیجه سیستم کش کاملاً خنثی شده و سرور زیر بار سنگین فرو می‌ریزد.
>
> **این بخش جواب می‌دهد:** سه آسیب مشهور کش (Stampede, Penetration, Avalanche) چه مکانیزم‌هایی دارند و چگونه با تکنیک کش منفی و ضریب اختلال (Jitter) آن‌ها را خنثی کنیم.

### مثلث تهدیدات لایهٔ کش

۱. **نفوذ به کش (Cache Penetration):**
   - استعلام مداوم کلیدهایی که در دیتابیس وجود ندارند، کش را بی‌اثر می‌کند.
   - **راه‌حل:** کش کردن پاسخ منفی (`null`) با زمان انقضای کوتاه (مثلاً ۶۰ ثانیه) یا استفاده از ساختار دادهٔ احتمالی **فیلتر بلوم (Bloom Filter)** در دروازهٔ ورود.

۲. **آوار کش (Cache Avalanche):**
   - هم‌زمانی انقضای هزاران کلید مختلف در یک ثانیهٔ مشخص (مثلاً ساعت ۱۲ شب) که باعث سقوط ناگهانی بار روی دیتابیس می‌شود.
   - **راه‌حل: افزودن ضریب اختلال تصادفی (TTL Jitter):**

```typescript
// ایجاد زمان انقضا با نوسان تصادفی ±۲۰٪ جهت پخش بار انقضا
function calculateTtlWithJitter(baseTtlSeconds: number): number {
  const jitterRange = baseTtlSeconds * 0.2;
  const randomOffset = (Math.random() * 2 - 1) * jitterRange;
  return Math.floor(baseTtlSeconds + randomOffset);
}
```

## ۶. صف (Queue) — چرا وجود دارد؟

> 🧒 **داستان این بخش:** مشتری وارد بانک می‌شود و درخواست افتتاح حساب می‌دهد؛ کارمند بانک فرم را تحویل می‌گیرد، کارتی برای رهگیری نوبت به او می‌دهد و می‌گوید: «درخواست شما ثبت شد، پیامک تأیید ظرف نیم‌ساعت دیگر برایتان ارسال می‌شود». مشتری بانک را ترک می‌کند تا به کارهای روزمره‌اش برسد.
>
> اگر کارمند مشتری را مجبور می‌کرد که سه ساعت کنار باجه بایستد تا استعلام‌ها به نوبت انجام شوند، صف مشتریان تا انتهای خیابان کشیده می‌شد. در برنامه‌های وب، **صف‌های پردازش پس‌زمینه** کارها را از جلوی پای کاربر برمی‌دارند تا سرور بدون معطلی به درخواست‌های بعدی بپردازد.
>
> **این بخش جواب می‌دهد:** میانجی پیام (Message Broker) چیست و مقایسهٔ RabbitMQ، Redis Streams و سرویس‌های ابری چگونه است.

### مقایسه ابزارهای پیام‌بندی (Message Brokers)

| سامانه | ماهیت فنی | نقاط قوت | سناریوی ایده‌آل |
|--------|-----------|----------|-----------------|
| **Redis Streams / BullMQ** | افزونه بر بستر Redis | سبک، پیکربندی بسیار ساده، بدون وابستگی جدید | برنامه‌های استارتاپی، صف‌های پس‌زمینه تا ۵۰ هزار پیام در ثانیه |
| **RabbitMQ** | پیام‌بند استاندارد صنعتی (AMQP) | مسیریابی پیچیده، تفکیک Exchange و Queue، صف اولویت‌دار | سیستم‌های توزیع‌شدهٔ سازمانی و تبادل پیام میان میکروسرویس‌ها |
| **Apache Kafka** | لاگ توزیع‌شده با کارایی فوق‌العاده بالا | پردازش رویدادهای کلان ترتیبی، ماندگاری نامحدود | تحلیل کلان داده‌ها، پردازش ترافیک میلیونی و لاگ‌های سیستم |

```text
  [کلاینت فرانت‌اند]
          │ ثبت سفارش (POST /orders)
          ▼
  [سرور Express API] ──── ثبت پیام در صف ───► [Redis / RabbitMQ Queue]
          │ پاسخ فوری (202 Accepted)                   │
          ▼                                            ▼ واکشی کارها
  [کاربر آزاد می‌شود]                             [ورکرهای پس‌زمینه Worker]
                                                       ├─► ارسال فاکتور ایمیلی
                                                       ├─► کسر موجودی انبار
                                                       └─► اطلاع‌رسانی پیامکی
```

## ۷. تضمین تحویل پیام — At-Least-Once یا At-Most-Once؟

> 🧒 **داستان این بخش:** نامه‌رسانی که بستهٔ محرمانه‌ای را تحویل می‌دهد با چالشی مواجه می‌شود: در را می‌زند اما جوابی نمی‌شنود. اگر بسته را پشت در بگذارد و برود، ممکن است بسته دزدیده شود (گم شدن پیام). اگر فردا دوباره برگردد و بسته را تحویل دهد، ممکن است دیروز فرد دیگری بسته را تحویل گرفته باشد و بسته تکراری شود!
>
> در شبکه‌های رایانه‌ای، به دلیل ماهیت ناپایدار اتصالات، تضمین اینکه پیامی **«دقیقاً یک‌بار»** تحویل داده شود در عمل ناممکن است. سیستم‌ها ناچارند میان «حداکثر یک‌بار» یا «حداقل یک‌بار» دست به انتخاب بزنند.
>
> **این بخش جواب می‌دهد:** چرا سیستم‌های پایدار از مدل At-Least-Once همراه با قابلیت توان‌پایی (Idempotency) استفاده می‌کنند.

### مدل‌های تضمین تحویل در صف

- **At-Most-Once (حداکثر یک‌بار):** پیام ممکن است در صورت خرابی ورکر برای همیشه گم شود، اما هرگز دوباره پردازش نخواهد شد. (نامناسب برای امور مالی و حیاتی).
- **At-Least-Once (حداقل یک‌بار):** تضمین قطعی که پیام گم نمی‌شود؛ اما در صورت بروز اختلال در ثبت پایان کار، ممکن است بیش از یک‌بار توسط ورکر بازخوانی شود.
- **راهکار طلایی: پیاده‌سازی کارگران توان‌پا (Idempotent Consumers)**
  ورکر باید به گونه‌ای طراحی شود که اگر پیامی ده بار نیز دریافت شد، نتیجهٔ نهایی روی سیستم دقیقاً معادل یک‌بار اجرا باشد.

```typescript
export async function processPaymentJob(job: { id: string; orderId: string; amount: number }) {
  // ۱. بررسی سابقه در پایگاه داده جهت رد پیام‌های تکراری
  const alreadyProcessed = await db.processedJobs.findOne({ jobId: job.id });
  if (alreadyProcessed) {
    console.log(`[IDEMPOTENT_SKIP] جاب ${job.id} قبلاً اجرا شده است؛ صرف‌نظر شد.`);
    return;
  }

  // ۲. انجام کار مالی درون تراکنش دیتابیس
  await db.transaction(async (tx) => {
    await tx.orders.updateStatus(job.orderId, 'PAID');
    await tx.processedJobs.insert({ jobId: job.id, completedAt: new Date() });
  });
}
```

## ۸. Job Scheduling — کارهای زمان‌بندی‌شده

> 🧒 **داستان این بخش:** ساعت ۲ بامداد، سیستم حسابداری باید صورت‌حساب‌های ماهانه را ببندد و فایل‌های گزارش موقت را پاک کند. در سیستم‌عامل‌های یونیکسی دهه‌هاست برنامه‌ای به نام **cron** این وظیفه را بر دوش دارد. اما وقتی اپلیکیشن شما روی پنج سرور ابری توزیع می‌شود، اگر تدبیری نیندیشید، هر پنج سرور در رأس ساعت ۲ کار را هم‌زمان اجرا می‌کنند و پنج صورت‌حساب تکراری برای مشتری صادر خواهد شد!
>
> **این بخش جواب می‌دهد:** ساختار نگارش Cron چیست و چطور با قفل‌های توزیع‌شده مانع از تکرار اجرای تسک‌ها در کلاستر شویم.

### سینتکس استاندارد عبارات Cron

عبارت کرون از ۵ فیلد با فاصله تشکیل شده است:
```text
┌───────────── دقیقه (۰ - ۵۹)
│ ┌─────────── ساعت (۰ - ۲۳)
│ │ ┌───────── روز ماه (۱ - ۳۱)
│ │ │ ┌─────── ماه سال (۱ - ۱۲)
│ │ │ │ ┌───── روز هفته (۰ - ۶ که ۰ = یکشنبه است)
│ │ │ │ │
* * * * *
```

- `0 3 * * *`: رأس ساعت ۳:۰۰ بامداد هر روز.
- `*/10 * * * *`: هر ۱۰ دقیقه یک‌بار.
- `0 0 1 * *`: در ابتدای اولین روز هر ماه میلادی.

```typescript
import { Queue } from 'bullmq';

const reportQueue = new Queue('reports', { connection: redis });

// تعریف تسک تکرارشونده در BullMQ با مدیریت قفل داخلی ردیس
await reportQueue.upsertJobScheduler(
  'daily-audit-report',
  { pattern: '0 2 * * *' }, // هر شب ساعت ۲ بامداد
  {
    name: 'generate-audit',
    data: { scope: 'all_tenants' },
  }
);
```

## ۹. طراحی صف تولیدی — نکات حیاتی

> 🧒 **داستان این بخش:** تصور کن نامه‌رسانی بسته‌ای را تحویل می‌گیرد اما نشانی گیرنده وجود خارجی ندارد. اگر نامه‌رسان هر روز دوباره همان بسته را بردارد و تلاش کند، اتلاف وقت و انرژی ادامه خواهد داشت. بستهٔ معیوب باید به باجهٔ بسته‌های مرجوعی (Dead Letter) منتقل شود تا پرونده‌اش جداگانه بررسی گردد.
>
> صف‌های محیط عملیاتی بدون این مکانیزم‌ها خیلی زود دچار خفگی می‌شوند.
>
> **این بخش جواب می‌دهد:** راهبرد عقب‌نشینی نمایی (Exponential Backoff)، صف مرگ (DLQ) و خاموشی پاکیزه (Graceful Shutdown) چگونه بقای سیستم را تضمین می‌کنند.

### ۱. تلاش مجدد با عقب‌نشینی نمایی (Exponential Backoff)

هنگامی که خطایی رخ می‌دهد، ورکر نباید فوراً دوباره تلاش کند؛ بلکه فاصلهٔ تلاش‌ها به شکل تصاعدی زیاد می‌شود:
تلاش اول: ۱ ثانیه بعد ⬅️ تلاش دوم: ۲ ثانیه بعد ⬅️ تلاش سوم: ۴ ثانیه بعد...

### ۲. صف مرگ (Dead Letter Queue - DLQ)

اگر پیامی پس از ۵ بار تلاش همچنان با خطا مواجه شود، از صف اصلی خارج شده و به **DLQ** منتقل می‌گردد. این کار مانع از مسدود شدن صف توسط پیام‌های سمی (Poison Pills) شده و به تیم فنی اجازه می‌دهد علت شکست را ریشه‌یابی کنند.

### ۳. خاموشی پاکیزهٔ ورکر (Graceful Shutdown)

هنگام به‌روزرسانی کدها یا خاموش شدن کانتینر، ورکر نباید کارهای در حال پردازش را نیمه‌کاره رها کند:

```typescript
process.on('SIGTERM', async () => {
  console.log('[SHUTDOWN] سیگنال دریافت شد؛ منتظر پایان کارهای جاری می‌مانیم...');

  // ۱. توقف پذیرش کارهای جدید
  await worker.pause();

  // ۲. مهلت دادن به کار جاری جهت تکمیل (با سقف حداکثر ۳۰ ثانیه)
  await worker.close();

  // ۳. بستن ایمن ارتباطات
  await redis.quit();
  process.exit(0);
});
```

## ۱۰. Webhook — کاری که خودت مقیاس می‌کنی

> 🧒 **داستان این بخش:** کاربری در سایت خرید می‌کند و به درگاه بانک هدایت می‌شود. سرور بانک پس از کسر وجه، باید موفقیت تراکنش را به سرور شما اطلاع دهد. آیا سرور شما باید هر دو ثانیه از بانک بپرسد: «آیا فلان سفارش پرداخت شد؟» (Polling)؟ قطعاً خیر. بانک مستقیماً به آدرس تعیین‌شدهٔ شما یک درخواست HTTP POST با جزییات تراکنش ارسال می‌کند — این مکانیزم **Webhook** است.
>
> **این بخش جواب می‌دهد:** چگونه صحت امضای وب‌هوک را بسنجیم و چرا وظایف سنگین وب‌هوک باید بلافاصله به صف منتقل شوند.

```typescript
import crypto from 'node:crypto';

export function verifyWebhookSignature(rawBody: string, signature: string, secret: string): boolean {
  const hmac = crypto.createHmac('sha256', secret);
  const expectedSignature = hmac.update(rawBody).digest('hex');
  return crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expectedSignature));
}

// اندپوینت دریافت وب‌هوک پرداخت:
app.post('/api/webhooks/payment', express.raw({ type: 'application/json' }), async (req, res) => {
  const signature = req.headers['x-signature'] as string;

  // ۱. اعتبارسنجی قطعی امضا بر روی بدنه خام
  if (!verifyWebhookSignature(req.body.toString(), signature, process.env.WEBHOOK_SECRET!)) {
    return res.status(401).json({ error: 'امضای وب‌هوک معتبر نیست' });
  }

  // ۲. سپردن بار سنگین به صف پس‌زمینه
  const event = JSON.parse(req.body.toString());
  await paymentQueue.add('verify-payment', event);

  // ۳. ارسال پاسخ فوری ۲۰۰ به درگاه بانکی در کمتر از ۲۰۰ میلی‌ثانیه
  res.status(200).json({ received: true });
});
```

## ۱۱. الگوهای پیشرفته

> 🧒 **داستان این بخش:** در یک سیستم ثبت سفارش، ابتدا رکورد سفارش در پایگاه داده ثبت می‌شود؛ بلافاصله در خط بعد باید رویداد `OrderCreated` در صف پیام منتشر شود تا سایر میکروسرویس‌ها باخبر شوند. اما اگر درست پس از Commit دیتابیس و پیش از ارسال پیام به صف، برق سرور قطع شود چه رخ می‌دهد؟ سفارش در دیتابیس ثبت شده اما هیچ پیامی به انبار و حسابداری نرسیده است!
>
> **این بخش جواب می‌دهد:** الگوی صندوق پستی (Transactional Outbox) و جداسازی خواندن از نوشتن (CQRS) چگونه پایداری سامانه‌های بزرگ را حفظ می‌کنند.

### الگوی Transactional Outbox

برای رفع معضل تناقض دو سیستم مجزا (Dual-Write):
۱. رویداد مورد نظر درون **همان تراکنش اصلی دیتابیس** در یک جدول اختصاصی به نام `outbox` ذخیره می‌شود.
۲. پروسه‌ای مستقل و سبک (مانند Debezium با Change Data Capture) جدول `outbox` را خوانده و با خیال آسوده به صف پیام ارسال می‌کند. بدین ترتیب یا هر دو ثبت می‌شوند یا هیچ‌کدام.

- مدیریت امن وب‌هوک‌ها با مقایسهٔ زمان‌ثابت امضای رمزنگاری و ارسال سریع تأییدیه.

## 🔨 چه می‌سازی؟

- **سرویس کش هوشمند با تایپ‌اسکریپت:** شامل لایهٔ Cache-Aside همراه با قفل ضد طوفان گله و محاسبهٔ پویا با Jitter.
- **سامانهٔ پردازش پس‌زمینه با BullMQ:** شامل صف ارسال ایمیل، صف تولید گزارش و مدیریت صف اولویت‌دار.

- **درگاه پردازش وب‌هوک مقاوم:** اعتبارسنجی امضای HMAC بدنه خام و اتصال آن به صف کارهای مالی.

## ✅ معیار اتمام فاز ۶

- [ ] تفاوت فنی پدیده‌های Cache Stampede، Cache Penetration و Cache Avalanche را تشریح می‌کنی و راهکار دفاعی هریک را می‌دانی.
- [ ] علت غیرممکن بودن تضمین Exactly-Once در شبکه‌های توزیع‌شده را درک کرده‌ای و ورکر توان‌پا (Idempotent) می‌نویسی.
- [ ] می‌توانی با کد نشان دهی که چطور با استفاده از `SET NX EX` جلوی ارسال هم‌زمان کوئری‌های تکراری به پایگاه داده را بگیری.
- [ ] دلیل ضرورت پاسخ فوری ۲۰۰ به وب‌هوک‌ها پیش از اجرای کارهای سنگین را می‌دانی.
- [ ] قادری سناریوی خرابی Dual-Write را توضیح دهی و نحوهٔ حل آن با الگوی Transactional Outbox را پیاده‌سازی کنی.
- [ ] اهمیت خاموشی پاکیزه (Graceful Shutdown) در ورکرهای پس‌زمینه را درک کرده‌ای و آن را در کدهای سرور خود پیاده کرده‌ای.
