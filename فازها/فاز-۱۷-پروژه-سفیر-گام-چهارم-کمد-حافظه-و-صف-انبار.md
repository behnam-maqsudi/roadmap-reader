## ۱. 🧰 جعبه‌ابزار مأموریت (دانلود قبل از شروع کار آفلاین)

برای این ایستگاه به سرور ردیس و دو کتابخانه کلیدی اکوسیستم نودجی‌اس نیاز داریم:

### ۱. موتور Redis برای ویندوز
ردیس یک دیتابیس در حافظه رم (In-Memory Data Store) است. برای ویندوز دو روش آسان و بدون دردسر وجود دارد:
- **روش اول (فایل اجرایی سبک و پرتابل بدون نیاز به نصب پیچیده):**  
  نسخه پورت‌شده ردیس برای ویندوز (از مخزن رسمی مایکروسافت/tporadowski) شامل دو فایل کوچک `redis-server.exe` و `redis-cli.exe` است که با یک کلیک اجرا می‌شوند.  
  [دانلود فایل پرتابل Redis ویندوز از گیت‌هاب (فایل redis-x64.zip)](https://github.com/tporadowski/redis/releases)
- **روش دوم (در صورت نصب بودن Docker):**  
  ```bash
  docker run --name safir-redis -p 6379:6379 -d redis:alpine
  ```
- **روش اجرای آماده در پروژه سفیر (بدون نیاز به داکر یا اینترنت):**  
  داخل پوشه `safir-project`، ردیس اختصاصی لوکال با نسخه پایدار ۸ قرار گرفته و با یکی از دستورات زیر روشن می‌شود:
  ```powershell
  npm run redis
  # یا مستقیماً:
  .\start-redis.bat
  ```

> 💡 **چرا این دستور را می‌زنیم و پشت صحنه چه رخ می‌دهد؟**  
> - **کِی اجرا می‌کنیم؟** قبل از تست یا اجرای کدهای گام‌های ۴، ۷ و ۸ که به حافظه پرسرعت و صف‌های انبار نیاز دارند.
> - **چرا می‌زنیم؟** ردیس یک پایگاه داده درون حافظه رم (RAM) است. وقتی این دستور را می‌زنی، `redis-server` روی پورت ۶۳۷۹ بالا می‌آید تا درخواست‌های کمد کش و صف‌های بسته انبار BullMQ بدون اتلاف وقت و با سرعت فوق‌العاده پردازش شوند.
> - **تست سلامت در ترمینال:**
>   ```powershell
>   node -e "const Redis = require('ioredis'); new Redis().ping().then(r => { console.log('پاسخ ردیس:', r); process.exit(0); });"
>   # خروجی موفق: پاسخ ردیس: PONG
>   ```


### ۲. پکیج اتصال نود به ردیس (`ioredis`)
- **چرا نیاز داریم:** سریع‌ترین، قدرتمندترین و استانداردترین کلاینت ارتباط با Redis در دنیای Node.js با پشتیبانی داخلی از Cluster و Sentinel.

## ۲. الفبای کش و صف به زبان یک کودک ۵ ساله (مفاهیم کلیدی)

> 🧒 **داستان این بخش:** تفاوت رم (RAM) و هارد (Disk) مثل تفاوت «میز کار جلوی دستت» با «زیرزمین خانه مادربزرگ» است! اگر برای هر مدادرنگی لازم باشد تا زیرزمین بروی و برگردی، تمام روزت تلف می‌شود. مدادهای پرمصرف را روی میز می‌گذاری. ردیس همان میز کار جلوی دست است که سرعتش نور است، اما اگر برق برود یا پر شود، باید حساب‌شده از آن استفاده کرد.

---

### ۲.۱. کش چطور کار می‌کند؟ (الگوی Cache-Aside)

الگوی **Cache-Aside** (کش کنار دست) استانداردی است که ۹۰ درصد شرکت‌های بزرگ دنیا از آن استفاده می‌کنند:

```
[کاربر] ---> درخواست استعلام سفارش ۱۰۱ ---> [وب‌سرور سفیر]
                                              │
                      ┌───────────────────────┴───────────────────────┐
                      ▼                                               ▼
         ۱. اول به ردیس سر بزن!                           آیا در ردیس بود؟
        [Redis Memory (0.5ms)]                             │             │
                                                    بله (Hit)           خیر (Miss)
                                                           │             │
                                            اطلاعات را سریع بده   ۲. برو دیتابیس اصلی
                                                                  [PostgreSQL (45ms)]
                                                                         │
                                                                  ۳. نتیجه را در ردیس بگذار
                                                                     (با تاریخ انقضا TTL)
                                                                         │
                                                                  ۴. به کاربر تحویل بده
```

| اصطلاح | مفهوم به زبان ساده | چه اتفاقی می‌افتد؟ |
|:---|:---|:---|
| **Cache Hit** | گل به خودی نخوردیم! دیتا آماده بود | سفارش در حافظه رم بود و بدون مزاحمت برای دیتابیس در ۱ میلی‌ثانیه تحویل داده شد. |
| **Cache Miss** | کمد خالی بود | بار اول بود؛ سرور مجبور شد به PostgreSQL برود، دیتا را بخواند، در کش بگذارد و سپس بدهد. |
| **TTL (Time To Live)** | تاریخ انقضای ماست | هر دیتایی در کش نباید تا ابد بماند؛ مثلاً می‌گوییم بعد از ۳۰۰ ثانیه (۵ دقیقه) خودکار تبخیر شود. |

---

### ۲.۲. بزرگ‌ترین معمای مهندسی: باطل‌سازی کش (Cache Invalidation)

یک جمله معروف در دنیای نرم‌افزار وجود دارد:
> *«تنها دو کار سخت در علوم کامپیوتر وجود دارد: باطل کردن کش و نام‌گذاری متغیرها!»*

اگر وضعیت سفارش شماره ۱۰۱ از «ثبت اولیه» به «تحویل راننده پیک داده شد» تغییر کند، اما ما فراموش کنیم کش قدیمی ردیس را پاک کنیم، چه می‌شود؟  
مشتری استعلام می‌گیرد و ردیس با افتخار در ۱ میلی‌ثانیه می‌گوید «بسته شما هنوز ثبت اولیه است!». مشتری عصبانی می‌شود!  
**قانون طلایی:** به محض اینکه هر دیتایی در PostgreSQL آپدیت یا حذف شد، باید کلید متناظر آن در ردیس با دستور `redis.del('order:101')` باطل (منقضی) شود.

---

### ۲.۳. صف پردازش (Job Queue) چیست و چرا وب‌سرور نباید کار سنگین بکند؟

فرض کن وقتی بسته‌ای تحویل داده شد، باید ۳ کار انجام شود:
1. تولید فاکتور رسمی PDF با بارکد (۲ ثانیه CPU سنگین).
2. ارسال پیامک به خریدار از طریق وب‌سرویس پیامکی (۱.۵ ثانیه انتظار اینترنت).
3. ارسال ایمیل با فایل فاکتور پیوست (۲ ثانیه).

اگر سرور Fastify بخواهد این ۵.۵ ثانیه را صبر کند و بعد به کاربر پاسخ دهد:
- کلاینت ۵.۵ ثانیه لودینگ می‌بیند!
- اگر درگاه پیامک قطع باشد، کل درخواست کاربر با خطای ۵۰۰ کرش می‌کند!
- سرور نمی‌تواند همزمان به کاربران دیگر جواب دهد چون نخ (Thread) آن درگیر تولید PDF شده است.

**راهکار با BullMQ:**  
سرور Fastify فقط یک برگه کار (Job) داخل صف ردیس می‌اندازد:
`await notificationQueue.add('send-receipt', { orderNumber: '101' })`  
و در عرض **۲ میلی‌ثانیه** به کاربر می‌گوید: «سفارش ثبت شد! کد پیگیری شما j-9843 است (کد وضعیت 202 Accepted)».  
کارگر پشت صحنه (**Worker**) که در یک پروسه مجزا در حال گوش دادن به ردیس است، سر فرصت جاب را برمی‌دارد، PDF را می‌سازد و پیامک می‌زند. اگر درگاه پیامک قطع بود، خودش ۳ بار با فاصله زمانی تلاش مجدد (Retry) می‌کند!

## ۳. ارتقای نقشه دیتابیس و کدهای پروژه سفیر

پروژه سفیر در این مرحله از ۲ فایل مستقل تشکیل می‌شود:
1. `server.js`: وب‌سرور سریع که کارهای سریع را خودش با کش ردیس انجام می‌دهد و کارهای سنگین را داخل صف می‌اندازد.
2. `worker.js`: کارگر خستگی‌ناپذیر که در پس‌زمینه کارهای صف را یکی‌یکی انجام می‌دهد.

### ۳.۱. کدهای سرور اصلی (`server.js`) با کش و صف

```javascript
// server.js — نسخه ۳: گام چهارم (کمد حافظه Redis و صف انبار BullMQ)

require('dotenv').config();
const fastify = require('fastify')({ logger: true });
const { PrismaClient } = require('@prisma/client');
const { PrismaPg } = require('@prisma/adapter-pg');
const Redis = require('ioredis');
const { Queue } = require('bullmq');

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
const prisma = new PrismaClient({ adapter });

// ۱. برقراری اتصال به کمد حافظه ردیس
const redis = new Redis({
  host: process.env.REDIS_HOST || '127.0.0.1',
  port: process.env.REDIS_PORT || 6379,
  maxRetriesPerRequest: null // الزامی برای سازگاری با BullMQ
});

// ۲. ساخت صف کارهای پس‌زمینه با BullMQ
const notificationQueue = new Queue('safirNotifications', { connection: redis });

// ۳. مسیر نبض سلامت (بررسی همزمان PostgreSQL و Redis)
fastify.get('/health', async (request, reply) => {
  try {
    await prisma.$queryRaw`SELECT 1`;
    const redisPing = await redis.ping();
    return {
      status: 'healthy',
      database: 'connected (PostgreSQL)',
      cache: `connected (Redis PING: ${redisPing})`,
      uptime: process.uptime(),
      timestamp: new Date().toISOString()
    };
  } catch (err) {
    reply.status(500);
    return { status: 'unhealthy', error: err.message };
  }
});

// ۴. استعلام وضعیت سفارش با الگوی طلایی Cache-Aside
fastify.get('/api/orders/:orderNumber', async (request, reply) => {
  const { orderNumber } = request.params;
  const cacheKey = `order:${orderNumber}`;

  const startTime = Date.now();

  // الف) اول کمد حافظه ردیس را چک کن!
  const cachedData = await redis.get(cacheKey);
  if (cachedData) {
    const elapsed = Date.now() - startTime;
    reply.header('X-Cache-Status', 'HIT');
    reply.header('X-Response-Time-Ms', elapsed);
    return {
      success: true,
      source: 'CACHE (Redis)',
      responseTimeMs: elapsed,
      order: JSON.parse(cachedData)
    };
  }

  // ب) نبود (Cache Miss) -> برو سراغ دیتابیس اصلی
  const order = await prisma.order.findUnique({
    where: { orderNumber: String(orderNumber) },
    include: { customer: { select: { name: true, phone: true } } }
  });

  if (!order) {
    reply.status(404);
    return { success: false, error: `سفارشی با شماره ${orderNumber} یافت نشد!` };
  }

  // ج) نتیجه را با طول عمر ۳۰۰ ثانیه (۵ دقیقه) در ردیس ذخیره کن
  await redis.setex(cacheKey, 300, JSON.stringify(order));

  const elapsed = Date.now() - startTime;
  reply.header('X-Cache-Status', 'MISS');
  reply.header('X-Response-Time-Ms', elapsed);
  return {
    success: true,
    source: 'DATABASE (PostgreSQL)',
    responseTimeMs: elapsed,
    order
  };
});

// ۵. تغییر وضعیت سفارش توسط مدیر و باطل‌سازی آنی کش (Cache Invalidation)
fastify.patch('/api/orders/:orderNumber/status', async (request, reply) => {
  const { orderNumber } = request.params;
  const { status } = request.body || {};

  if (!status) {
    reply.status(400);
    return { success: false, error: 'وضعیت جدید الزامی است.' };
  }

  // ۱. آپدیت در دیتابیس اصلی
  const updatedOrder = await prisma.order.update({
    where: { orderNumber: String(orderNumber) },
    data: { status }
  });

  // ۲. گام حیاتی: پاک کردن کش کهنه از ردیس!
  await redis.del(`order:${orderNumber}`);

  // ۳. انداختن کار سنگین اطلاع‌رسانی به خریدار داخل صف انبار BullMQ
  const job = await notificationQueue.add('order-status-changed', {
    orderNumber: updatedOrder.orderNumber,
    newStatus: updatedOrder.status,
    updatedAt: new Date().toISOString()
  }, {
    attempts: 3, // در صورت قطعی درگاه، ۳ بار تلاش کن
    backoff: { type: 'exponential', delay: 2000 } // با تاخیر فزاینده
  });

  return {
    success: true,
    message: 'وضعیت سفارش بروز شد، کش باطل گردید و عملیات پیامک به صف فرستاده شد.',
    order: updatedOrder,
    jobId: job.id
  };
});

// ۶. استعلام وضعیت جاب در صف (برای رهگیری توسط کلاینت)
fastify.get('/api/jobs/:id', async (request, reply) => {
  const { id } = request.params;
  const job = await notificationQueue.getJob(id);

  if (!job) {
    reply.status(404);
    return { success: false, error: 'جاب پیدا نشد.' };
  }

  const state = await job.getState(); // waiting, active, completed, failed
  return {
    id: job.id,
    name: job.name,
    state,
    progress: job.progress,
    result: job.returnvalue,
    failedReason: job.failedReason
  };
});

fastify.listen({ port: 3000, host: '0.0.0.0' }).then(addr => {
  console.log(`🚀 سرور سفیر مجهز به موتور Redis و BullMQ روی ${addr} آغاز به کار کرد!`);
});
```

### ۳.۲. کدهای کارگر پشت صحنه (`worker.js`)

این فایل مستقل را در یک ترمینال جداگانه با دستور `node worker.js` اجرا می‌کنی:

```javascript
// worker.js — کارگر وظیفه‌شناس پردازش کارهای سنگین سفیر در پس‌زمینه

const { Worker } = require('bullmq');
const Redis = require('ioredis');

const connection = new Redis({
  host: process.env.REDIS_HOST || '127.0.0.1',
  port: process.env.REDIS_PORT || 6379,
  maxRetriesPerRequest: null
});

console.log('👷 کارگر پردازش سفیر بیدار شد و در حال گوش دادن به صف safirNotifications است...');

const worker = new Worker('safirNotifications', async (job) => {
  console.log(`\n📥 [شروع پردازش جاب #${job.id}] عنوان: ${job.name}`);
  console.log('📦 داده‌های جاب:', job.data);

  if (job.name === 'order-status-changed') {
    // شبیه‌سازی کار زمان‌بر: صدور فاکتور PDF و ارسال پیامک (۲ ثانیه)
    console.log('⏳ در حال تولید فاکتور دیجیتال و اتصال به وب‌سرویس پیامک...');
    await new Promise((resolve) => setTimeout(resolve, 2000));

    console.log(`✅ پیامک تغییر وضعیت به خریدار سفارش ${job.data.orderNumber} ارسال گردید!`);
    
    return {
      sentSms: true,
      deliveredAt: new Date().toISOString(),
      details: `پیامک به شماره ثبت‌شده برای سفارش ${job.data.orderNumber} مخابره شد.`
    };
  }

  return { processed: true };
}, { connection });

worker.on('completed', (job, returnvalue) => {
  console.log(`🎉 جاب #${job.id} با موفقیت به پایان رسید. خروجی:`, returnvalue);
});

worker.on('failed', (job, err) => {
  console.error(`❌ خطا در اجرای جاب #${job.id}:`, err.message);
});
```

## ۵. تمرین‌های تثبیت و چالش چریکی

1. **چالش مسابقه کش (Cache Stampede):**  
   اگر یک میلیون کاربر همزمان سفارش یک کالای تخفیف‌خورده را صدا بزنند و کش دقیقاً در همان لحظه منقضی شود، چه اتفاقی می‌افتد؟ هر یک میلیون درخواست به سمت PostgreSQL هجوم می‌برند و سرور پایین می‌آید!  
   *راهکار چریکی:* به جای TTL ثابت (مثلاً دقیقاً ۳۰۰ ثانیه)، یک عدد رندوم بین ۲۵۰ تا ۳۵۰ ثانیه بده (**Jitter**) تا همه کش‌ها همزمان تبخیر نشوند.
2. **چالش قطعی درگاه پیامک و بازتلاش (Exponential Backoff):**  
   در فایل `worker.js` عمداً یک خطای فرضی (`throw new Error("پنل پیامک قطع است!")`) بنداز و ببین چطور BullMQ بدون اینکه کاربر متوجه شود، کار را بعد از ۲ ثانیه، سپس ۴ ثانیه و سپس ۸ ثانیه مجدداً امتحان می‌کند!
