## ۱. تفاوت‌های بنیادی با TypeScript

> 🧒 **داستان این بخش:** از جاوااسکریپت آمده‌ای و فکر می‌کنی پایتون همان است با
> اسمی دیگر. نیست. بزرگ‌ترین تفاوت، **تورفتگی** است.

> در جاوااسکریپت `{}` تعیین می‌کند یک بلوک کجاست. در پایتون همان کار را
> **فاصله‌ی ابتدای خط** می‌کند — یعنی دقیقاً همان چیزی که در همه‌ی سطرها کمک
> می‌کند. نتیجه: کد پایتون برای خواننده ساده‌تر و برای ابزار، دقیق‌تر است.
>
> تفاوت دوم این است که در پایتون، هر متغیر می‌تواند **نوع عوض کند**. این در
> جاوااسکریپت هم هست، ولی اینجا ابزارِ type checking فقط **راهنمای ادیتور** است
> و اجباری نیست — و همین، بزرگ‌ترین منبع سردرگمیِ تازه‌کارها است.
>
> **این بخش جواب می‌دهد:** کدام سه چیز در پایتون جاوااسکریپت را غافلگیر
> می‌کند (تورفتگی، نوعِ پویا، فهرست‌های قابل تغییر) و هر کدام چه دردسری می‌سازد.

| جنبه | TypeScript | Python |
|------|-----------|--------|
| نوع‌دهی | **استاتیک** (کامپایل) | **داینامیک** (اجرا) — ولی type hint دارد |
| کامپایل | به JS تبدیل می‌شود | کامپایل نمی‌شود، اجرا می‌شود |
| سرعت اجرا | سریع | کندتر (معمولاً) |
| مدیریت بسته | npm / pnpm | pip / uv |
| ویراستار | tsconfig.json | pyproject.toml |
| حلقه‌ها | `{}` الزامی | `: ` (سرفصل) اختیاری |
| null | `null` و `undefined` | `None` |
| async | `async/await` بومی | `async/await` + `asyncio` |
| لیست/آرایه | `number[]` | `list[int]` |

### آیا پایتون هم مثل TypeScript type دارد؟

بله، ولی فرق مهم است:

```typescript
// TypeScript: type checking قبل از اجرا انجام می‌شود
function add(a: number, b: number): number {
  return a + b;
}
add("1", 2);          // ❌ خطای کامپایل
```

```python
# Python: type hint فقط راهنمای ادیتور است، اجباری نیست
def add(a: int, b: int) -> int:
    return a + b

add("1", 2)           # ⚠️ اجرا می‌شود! و TypeError می‌دهد (در runtime)
add("1", "2")         # ⚠️ اجرا می‌شود و "12" برمی‌گرداند!
```

> 🔑 **تفاوت کلیدی:** type hint در پایتون **اختیاری** و **غیراجباری** است. برای گرفتن مزیت واقعی، حتماً `mypy` یا `pyright` را روی پروژه اجرا کن.

```bash
# ✅ ابزارهای type checking و lint
pip install mypy ruff
mypy src/
ruff check src/
```

## ۲. محیط و مدیریت بسته

> 🧒 **داستان این بخش:** سه نفر روی یک پروژه کار می‌کنند: یکی ویندوز، یکی مک،
> یکی لینوکس. روز اول همه `pip install` می‌زنند و همه چیز کار می‌کند. ماه بعد،
> یکی از آن‌ها یک بسته را ارتقا می‌دهد و **فقط روی سیستم خودش** خراب می‌شود.
>
> کسی راه‌حل را نمی‌داند، چون کسی نوشته **چه** بسته‌هایی نصب شده‌اند و با چه
> نسخه‌ای. آن فایل را `requirements.txt` می‌نامند و کارش مثل لیست خریدی است
> که همیشه با هم قرو می‌شود.
>
> ولی همین هم یک مشکلِ تازه ساخت: اگر همه در یک محیطِ مشترک نصب کنند، یکی
> بسته را عوض می‌کند و پروژه‌ی بقیه می‌شکند. راه‌حلِ امروزی، **محیط جدا برای
> هر پروژه** است.
>
> **این بخش جواب می‌دهد:** محیطِ مجزا (virtual environment) چرا لازم است،
> `requirements.txt` و `uv` چه می‌کنند، و چرا نسخه‌ها را باید قفل کرد.

### چرا `venv`؟

**`venv` (محیط مجازی)** یک **پوشه‌ی جداگانه در همان پروژه** می‌سازد که نسخه‌های مستقلی از پایتون و کتابخانه‌ها داخلش نصب می‌شوند. یعنی هر پروژه **محیط ایزوله‌ی خودش** را دارد و نصب بسته‌های یک پروژه، پروژه‌ی دیگر را خراب نمی‌کند. خود پایتون هم معمولاً داخل همین پوشه نصب می‌شود، پس نسخه‌ی پایتون هم مستقل است.

اگر پروژه‌ای `numpy` ۲.۰ می‌خواهد و پروژه‌ی دیگر `numpy` ۱.۲، بدون محیط مجزا هرکدام install کنی، یکی خراب می‌شود.

```bash
# ساخت محیط مجزا
python -m venv .venv

# فعال‌سازی
# لینوکس/مک:
source .venv/bin/activate
# ویندوز:
.venv\Scripts\activate

# نصب بسته
pip install fastapi uvicorn sqlalchemy

# ذخیره‌ی نسخه‌های دقیق
pip freeze > requirements.txt
```

### uv — ابزار جدید و بسیار سریع

`uv` جایگزین مدرن `pip` است و **۱۰ تا ۱۰۰ برابر سریع‌تر**:

```bash
# نصب خود uv
curl -LsSf https://astral.sh/uv/install.sh | sh

# استفاده (مثل pip ولی سریع)
uv add fastapi
uv sync                  # نصب از روی lockfile، قطعی و تکرارپذیر
uv run pytest            # اجرا در محیط پروژه
```

**`pyproject.toml`**: یک فایل متنی در ریشه‌ی پروژه که **پیکربندی پروژه** را یک‌جا جمع می‌کند — نام و نسخه، وابستگی‌ها، و تنظیمات ابزارها (ruff، mypy، pytest). یعنی همان چیزی که در فاز ۲ بین `package.json` و `tsconfig.json` تقسیم شده بود، اینجا یک فایل است.

**`lockfile`** (فایل قفل، اینجا `uv.lock`): فایلی که **نسخه‌ی دقیقِ دقیق**ی از هر بسته را ثبت می‌کند — نه «numpy هر نسخه‌ای»، بلکه «numpy دقیقاً نسخه‌ی ۲.۱.۳ و این ۱۲ بسته‌ی دیگر با همین نسخه». بدون آن، هرکس `install` کند ممکن است نسخه‌ی متفاوتی بگیرد و پروژه یک روز روی سیستم تو کار کند و روی سیستم یکی دیگر نه. با آن، **همه‌ی کاربران و سرورها دقیقاً یک محیط یکسان** می‌گیرند.

برای همین `uv sync` — یعنی «محیط را دقیقاً از روی lockfile بساز» — قابل اعتماد است، در حالی که `pip install` بدون قید نسخه، قابل اعتماد نیست.

| ابزار | نقش |
|-------|------|
| `venv` | ساخت محیط مجزا (پایه‌ای) |
| `pip` | نصب بسته |
| `uv` | ⭐ جایگزین سریع pip + مدیریت lockfile |
| `poetry` / `pdm` | مدیریت پروژه (بیشتر برای کتابخانه) |
| `pipx` | نصب ابزار خط فرمان به‌صورت ایزوله |

> زیرکِ غیرقابل‌فهم است. حتی در پایتون.
>
> **این بخش جواب می‌دهد:** list/dict/set comprehension، f-string، context manager

### List Comprehension — نوشتن لوپ بدون لوپ

**List Comprehension** یعنی ساختن یک لیست (یا دیکشنری، یا مجموعه) از روی یک دنباله، **در یک خط** — بدون نوشتن `for` و `append` جدا.

- **به زبان ساده:** مثل اینکه به‌جای اینکه صد برگه را یکی‌یکی بگذاری توی جعبه، به کارمندت بگویی «همه‌ی برگه‌های روی میز را بگذار توی جعبه». کار یکی است، فقط بیانش کوتاه‌تر است.
- **چرا مهم است:** هم سریع‌تر است (در CPython حلقه‌ی کامپایل‌شده یک‌باره اجرا می‌شود) و هم خواناتر. در کد پایتون حرفه‌ای، تقریباً همیشه باید از آن استفاده کنی.

سه بخش دارد: **خروجی** (چه چیزی بسازیم) ← **شرط** (کدام‌ها بمانند) ← **دنباله** (از کجا).

```python
# ❌ سنتی
squares = []
for n in range(10):
    squares.append(n ** 2)

# ✅ Pythonic
squares = [n ** 2 for n in range(10)]

# با شرط
evens = [n for n in range(100) if n % 2 == 0]

# با تبدیل
upper_names = [name.upper() for name in users if name]

# دیکشنری
lookup = {user.id: user for user in users}

# مجموعه
unique_ids = {user.id for user in users}
```

> 💡 این تنها جایی است که پایتون از JS «زیباتر» است. واقعاً بخوان و استفاده کن.

### unpacking

**Unpacking** (باز کردن بسته) یعنی یک مقدار را در یک **ساختار چندتایی** (تاپل، لیست، دیکشنری) نگه می‌داری، بعد با یک علامت `=` آن را **به چند متغیر جدا** باز می‌کنی. عمل برعکسش هم هست: چند مقدار را در یک تاپل جمع می‌کنی.

- **به زبان ساده:** یک بسته‌ی چندمحصولی را باز می‌کنی و محصولات را جدا روی میز می‌گذاری.

سینتکس `*rest` یعنی «**بقیه‌ی** موارد را در یک لیست جمع کن»، و `first, *rest, last` یعنی اولی را بگیر، آخری را بگیر، و هر چه وسط است در `rest`.

```python
a, b, c = 1, 2, 3
first, *rest, last = [1, 2, 3, 4, 5]     # first=1, rest=[2,3,4], last=5

# swap بدون متغیر موقت
a, b = b, a

# دیکشنری
config = {"host": "localhost", "port": 5432}
host, port = config["host"], config["port"]

# در حلقه
for key, value in config.items():
    ...
```

### f-string — رشته‌های قالب‌بندی

**f-string** راه نوشتن رشته‌های ترکیبی در پایتون است: یک `f` جلوی گیومه‌ی شروع می‌گذاری و هر `{name}` داخلش مستقیم **همان لحظه** به مقدار واقعی تبدیل می‌شود.

- **چرا مهم است:** خواناتر از `%` و `.format()` است، و مهم‌تر — چون مقدار واقعی در کد نوشته می‌شود (نه در قالب)، ویرایشگر می‌تواند تشخیص دهد کدام متغیر استفاده شده. این همان چیزی است که لاگ‌های فاز ۸ را دقیق می‌کند.

بعد از `:` می‌توانی **فرمت** هم بدهی — `{price:,.0f}` یعنی «با جداکننده‌ی هزارگان و بدون رقم اعشار».

```python
# ❌ روش قدیمی
msg = "کاربر %s با نقش %s" % (name, role)
msg = "کاربر {} با نقش {}".format(name, role)

# ✅ f-string
msg = f"کاربر {name} با نقش {role}"

# فرمت‌های پیشرفته
price = 1250000.5
print(f"{price:,.0f}")          # 1,250,000
print(f"{price:.2f}")            # 1250000.50
print(f"{value:.1%}")            # 85.3%

# در لاگ
logger.info(f"user_id={user_id} action={action} duration_ms={dur:.1f}")
```

### Context Manager — مدیریت منابع

**Context Manager** (مدیر زمینه) با دستور `with` یک **منبع** (فایل، کانکشن دیتابیس، قفل) را باز می‌کند و تضمین می‌کند که **حتی اگر وسط کار خطا رخ بدهد**، باز هم بسته شود.

- **چرا وجود دارد:** اگر خودت یادت بماند ببندی، یک روزی فراموش می‌کنی — و فایل قفل می‌ماند، یا تراکنش نیمه‌باز می‌ماند. با `with` این خطر **در سطح زبان** حذف می‌شود، نه در سطح انضباط تو.
- **پروتکلش چیست:** هر شیءی که داخل `with` بگذاری باید دو متد داشته باشد: `__enter__` (در لحظه‌ی ورود صدا زده می‌شود و مقدار برمی‌گرداند) و `__exit__` (در لحظه‌ی خروج صدا زده می‌شود — چه خطا رخ داده باشد چه نداده). مقدار برگشتی `__enter__` است که با `as` می‌گیری.
- **به زبان ساده:** مثل یک اتاق با قفل خودکار. وارد می‌شوی (در باز می‌شود)، کارت را می‌زنی (قفل می‌کند) — چه بخواهی بروی چه وسط کار برق قطع شود، در بسته می‌شود.

```python
# فایل
with open("data.json") as f:
    data = json.load(f)
# حتی اگر خطا دهد، فایل بسته می‌شود

# دیتابیس
with db.begin() as tx:
    tx.execute(...)
# اگر خطا دهد، تراکنش rollback می‌شود
```

### Decorator — بسته‌بندی رفتار

**Decorator** (دکوراتور) تابعی است که **تابع دیگری را می‌گیرد و تابعی تازه به تو برمی‌گرداند** که رفتار اصلی را دارد، به‌علاوه‌ی چیزهای بیشتر (اندازه‌گیری، احراز هویت، ثبت لاگ، کش).

- **سینتکس `@name`** دقیقاً معادل `func = name(func)` است. یعنی `@timer` یعنی «`train_model` را به `timer` بده و آنچه برمی‌گرداند جایگزینش کن». یعنی هیچ تغییری در خودِ تابع نمی‌دهی.
- **به زبان ساده:** یک کادوی که روی یک جعبه‌ی هدیه می‌پیچی. محتویات جعبه (تابع اصلی) عوض نمی‌شود؛ فقط یک لایه‌ی بیرونی اضافه می‌شود.
- **چرا مهم است:** رفتارهای عرضی (cross-cutting) را یک‌بار می‌نویسی و به ده‌ها تابع می‌چسبانی، بدون تکرار کد و بدون دست زدن به بدنه‌ی آن‌ها.

```python
import functools
import time

def timer(func):
    @functools.wraps(func)              # ⭐ متادیتای تابع حفظ می‌شود
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__}: {time.perf_counter()-start:.2f}s")
        return result
    return wrapper

@timer
def train_model():
    ...
```

> 💡 Decorator در پایتون معادل **Composition** در JS است — ولی خواناتر.

### async/await — I/O هم‌زمان

**`async/await`** در پایتون برای **I/O هم‌زمان** است: وقتی برنامه منتظر پاسخ شبکه یا دیتابیس است، به جای اینکه معلق بماند (و بقیه‌ی درخواست‌ها را هم متوقف کند)، **رها می‌کند** تا کارهای دیگر جلو بروند.

- **`async def`** یعنی این تابع **می‌تواند** بدهد و برگردد. **`await`** یعنی «نتیجه‌اش را برایم بیاور» — همان لحظه که `await` می‌نویسی، **همان تابع** معلق می‌شود و بقیه‌ی کارهای I/O شروع می‌شوند.
- **`async with`** نسخه‌ی `async` همان Context Manager فاز قبل است، برای منابعی مثل `AsyncClient` که خودش هم‌زمان است.

**`asyncio.gather`** این‌جا کار می‌کند: چند کارِ هم‌زمان (coroutine) را همه با هم شروع می‌کند و **فقط وقتی همه تمام شدند** نتایجشان را برمی‌گرداند. نتیجه هم به همان ترتیب ورودی‌هاست، نه به ترتیب پایان.

- **به زبان ساده:** به‌جای اینکه نامه را پست کنی و کنار صندوق بایستی تا جواب بیاید، نامه‌ها را پست می‌کنی و می‌روی. `gather` یعنی «همه را پست کن، بعد با هم جواب‌ها را تحویل بگیر».

```python
import asyncio
import httpx

async def fetch_all(urls: list[str]) -> list[dict]:
    async with httpx.AsyncClient() as client:
        # ⭐ همه‌ی درخواست‌ها هم‌زمان
        tasks = [client.get(url) for url in urls]
        responses = await asyncio.gather(*tasks)
        return [r.json() for r in responses]

results = await fetch_all(urls)
```

> 🔑 **قاعده:** در پایتون `asyncio` مثل JS است ولی باید `await` را واقعاً استفاده کنی. کد CPU-bound را در `asyncio` نگذار — حلقه‌ی رویداد را بلاک می‌کند.

## ۴. FastAPI — وب فریم‌ورک پایتونی

> 🧒 **داستان این بخش:** یک تیم برای هر API کوچک، یک فایل طولانی می‌نوشت و
> هرگز مستنداتی نداشت. یعنی هر کسی می‌خواست بداند این سرویس چه ورودی‌ای می‌گیرد،
> باید کسی را بپرسد یا کد را بخواند.

> FastAPI راهِ دیگری را برگزید: تو **نوعِ** ورودی و خروجی را در خودِ کد می‌نویسی،
> و فریم‌ورک از همان، هم **اعتبارسنجی** می‌سازد، هم **مستنداتِ زنده**.
> آدرس `/docs` خودش کار می‌کند — نه نوشته می‌شود، نه کهنه می‌شود.
>
> این نتیجه‌ی یک تصمیمِ ساده است: **نوع‌ها را یک بار بنویس** و بقیه خودشان
> از آن ساخته می‌شوند.
>
> **این بخش جواب می‌دهد:** FastAPI چطور با نوع‌نویسی، اعتبارسنجی و
> مستندات را با هم می‌سازد، و چرا این برای رابط‌های بین سرویس‌ها حیاتی است.

- **چرا FastAPI:** خودکار بودن مستندات، type hint محوری، و سرعت بالا.
- **به زبان ساده:** مثل Express ولی خودش مستندات و اعتبارسنجی را رایگان می‌دهد.

**FastAPI** چیست: یک **وب فریم‌ورک** (چارچوب وب) برای ساخت API در پایتون — همان نقشی که Express در Node دارد. سه چیز آن را از بقیه متمایز می‌کند و هر سه از یک ریشه‌اند: **type hint** در امضای تابع.

- **چون تایپ‌ها را نوشته‌ای، خودش فرم JSON می‌سازد** و ورودی را **اعتبارسنجی** می‌کند (کلاس `Pydantic`).
- **چون تایپ‌ها را نوشته‌ای، خودش مستندات API تولید می‌کند** — بدون نوشتن حتی یک خط YAML.
- **چون تایپ‌ها را نوشته‌ای، ویرایشگرها بهتر کمک می‌کنند.**

پایه‌اش **Starlette** است و لایه‌ی اعتبارسنجی‌اش **Pydantic**.

```python
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel, EmailStr

app = FastAPI(title="Orders API", version="1.0.0")

# ---------- مدل درخواست/پاسخ (Pydantic = اعتبارسنجی خودکار) ----------
class UserCreate(BaseModel):
    email: EmailStr                            # ⭐ اعتبار ایمیل خودکار
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=0, le=120)

class UserResponse(BaseModel):
    id: int
    email: str
    name: str

# ---------- مسیرها ----------
@app.post("/users", response_model=UserResponse, status_code=201)
async def create_user(data: UserCreate) -> UserResponse:
    if await user_exists(data.email):
        raise HTTPException(409, "ایمیل قبلاً ثبت شده")
    return UserResponse(id=1, email=data.email, name=data.name)

# ⭐ مستندات خودکار: /docs (Swagger UI) و /redoc
```

### Dependency Injection — تزریق وابستگی

**Dependency Injection (DI)** یعنی: به‌جای اینکه یک تابع **خودش** چیزی را که لازم دارد بسازد یا پیدا کند (مثلاً خودش کانکشن دیتابیس را باز کند)، آن چیز را **از بیرون به آن بدهی**.

- **به زبان ساده:** بدون DI، کارمند خودش قلم و کاغذ می‌آورد. با DI، رئیس قلم را آماده روی میزش می‌گذارد. حالا می‌توانی قلم دیگری هم به او بدهی، بدون اینکه رفتارش عوض شود.
- **چرا مهم است:** تست کردن. اگر تابع، دیتابیس واقعی را خودش بسازد، برای تست باید دیتابیس واقعی بالا بیاوری. اگر از بیرون بگیرد، در تست یک **نسخه‌ی قلابی** (mock) تحویلش می‌دهی و سریع و بی‌دردسر تست می‌شود.

در FastAPI این کار با `Depends(...)` انجام می‌شود: FastAPI تابع وابستگی را صدا می‌زند، نتیجه‌اش را به تابع اصلی تحویل می‌دهد — و تو فقط نام تابع را در امضا می‌نویسی.

```python
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession

async def get_db() -> AsyncSession:
    async with async_session() as session:
        yield session

async def get_current_user(
    token: str = Depends(oauth2_scheme),
    db: AsyncSession = Depends(get_db),
) -> User:
    user = await get_user_from_token(token, db)
    if not user:
        raise HTTPException(401, "توکن نامعتبر")
    return user

@app.get("/users/me")
async def read_me(user: User = Depends(get_current_user)):
    return user          # ⭐ تمیز و قابل تست
```

> 💡 این دقیقاً همان الگوی `middleware` در فاز ۳ است، ولی با یک تفاوت: در FastAPI می‌توانی به **هر تابعی** وابستگی تزریق کنی، نه فقط به مسیرها.

## ۶. NumPy — پایه‌ی همه‌چیز

> 🧒 **داستان این بخش:** یک آرایه‌ی یک میلیون عدد را در ۱۰۰۰ حلقه‌ی پایتون
> جمع می‌زنی — چند ثانیه. NumPy همان کار را در **یک خط** می‌کند — چند میلی‌ثانیه.
> چرا؟ چون به‌جای تک‌تک عددها، کلِ آرایه را **یک‌جا** به پردازنده می‌دهد.
>
> این فقط سرعت نیست؛ این **مدلِ ذهنی** است. به‌جای «حلقه بزن و تک‌تک حساب کن»،
> فکر می‌کنی «روی کلِ آرایه یک عمل ریاضی بگذار». به این می‌گویند **برداری‌سازی**.
>
> تاریخش هم داستانِ جالبی دارد: پایتون از دهه‌ی ۹۰ دو بسته‌ی عددیِ جدا داشت.
> سال ۲۰۰۵ نگاشتن به scipy به هم آمد و یکی شدند، و **کار نپیسانت**
> آن‌ها را با NumPy یکی کرد؛ نسخه‌ی ۱.۰ در سال ۲۰۰۶ بیرون آمد.
>
> **این بخش جواب می‌دهد:** آرایه چندبعدی (ndarray)، محور (axis) یعنی چه، و
> چرا همه‌ی کتابخانه‌های علم داده روی همین یکی ساخته شده‌اند.

- **چرا وجود دارد:** پایتون خالص برای محاسبات عددی **خیلی کند** است. NumPy این کار را در C انجام می‌دهد.
- **به زبان ساده:** مثل یک آشپز که ۱۰۰۰ هویج را یک‌جا و سریع خرد می‌کند، در برابر ۱۰۰۰ نفر که هرکدام یک هویج خرد می‌کنند.

```python
import numpy as np

# ❌ خیلی کند — ۱ میلیون حلقه در جاوااسکریپت/پایتون
total = 0
for x in data:
    total += x * x

# ✅ NumPy — عملیات برداری، در C
arr = np.array(data)
total = np.sum(arr ** 2)

# ⚡ ۵۰ تا ۱۰۰ برابر سریع‌تر
```

### مفاهیم کلیدی

دو کلمه‌ای که در همه‌ی مثال‌های زیر می‌بینی و باید دقیق بدانی چه هستند:

- **`shape` (شکل):** ابعاد آرایه، به ترتیب. آرایه‌ی یک‌بعدی شکل `(5,)` دارد (یک عدد در پرانتز). آرایه‌ی سطری‌ستونی ۲×۳ شکل `(2, 3)` دارد — یعنی ۲ سطر و ۳ ستون. اولین عدد همیشه تعداد **سطر** است، دومی تعداد **ستون**.
- **`dtype` (نوع داده):** هر عدد در آرایه چه نوعی ذخیره می‌شود. `int64` عدد صحیح ۶۴ بیتی است، `float32` اعشاری ۳۲ بیتی. نوع داده مستقیماً روی **سرعت و حافظه** اثر دارد: `float32` دقیقاً نصف حافظه‌ی `float64` را می‌گیرد و در محاسبات عددی برای مدل‌های یادگیری ماشین تقریباً به همان اندازه کافی است.

**View در برابر Copy:** برش (`arr[1:3]`) در NumPy **کپی نمی‌کند**؛ یک **view** می‌سازد — یعنی پنجره‌ای روی همان حافظه‌ی اصلی. برای همین `v[1:3]` در کد زیر با `← برش (view، نه کپی!)` نشانه‌گذاری شده. پیامد عملی: نوشتن روی view، داده‌ی اصلی را هم عوض می‌کند (و برعکس) — پس سریع است ولی حواست باشد. اگر واقعاً کپی جدا می‌خواهی، صریح بنویس `.copy()`.

```python
# بردار (Vector) — آرایه‌ی هم‌نوع
v = np.array([1, 2, 3, 4, 5])
v.shape          # (5,)         ← شکل
v.dtype          # int64        ← نوع
v[1:3]           # [2, 3]       ← برش (view، نه کپی!)

# ماتریس
m = np.array([[1, 2], [3, 4]])
m.shape          # (2, 2)
m.T              # ترانهاده
m @ m            # ضرب ماتریسی

# محور (axis) — کلید یادگیری
arr = np.array([[1, 2, 3], [4, 5, 6]])
arr.sum()            # 21   ← همه
arr.sum(axis=0)      # [5,7,9] ← روی ستون‌ها
arr.sum(axis=1)      # [6,15]  ← روی سطرها
```

> 💡 `axis` را مثل pandas صفت کن: `axis=0` یعنی «روی ردیف‌ها حرکت کن، برای هر ستون جمع بگیر».

### Broadcasting — گسترش خودکار ابعاد

**Broadcasting** یعنی وقتی دو آرایه با شکل‌های متفاوت را با هم ترکیب می‌کنی (جمع، ضرب و...)، NumPy به‌طور خودکار **بُعد کوچک‌تر را تکرار می‌کند** تا شکل‌ها با هم بخوانند — بدون اینکه تو حتی یک حلقه بنویسی.

قاعده‌ی تصمیم‌گیری: ابعاد از **آخر** به اول مقایسه می‌شوند. دو بُعد وقتی سازگارند که **برابر باشند** یا یکی‌شان **۱** باشد. در مثال زیر شکل `(3, 1)` و `(3,)` هستند: بُعد دوم `1` در برابر `3` است، پس `1` **سه بار تکرار** می‌شود:

- **به زبان ساده:** یک ستون سه‌تایی و یک سطر سه‌تایی را در ذهن تصور کن. NumPy آن سطر را سه بار کنار هم می‌کشد تا با سه سطر ستون جفت شود.

```python
a = np.array([[1], [2], [3]])   # شکل (3, 1)
b = np.array([10, 20, 30])       # شکل (3,)

a + b   # شکل (3, 3) — بدون حلقه!
# [[11, 21, 31],
#  [12, 22, 32],
#  [13, 23, 33]]
```

## ۷. pandas — کار با داده‌ی جدولی

> 🧒 **داستان این بخش:** یک فایل اکسل با ۵۰ هزار ردیف داری و پنج سوال از آن.
> در پایتون، بدون ابزار، هر سوال ده خط کد و یک حلقه‌ی کند می‌خواهد.

> **wes مک‌کینی** که پایتون را برای تحلیلِ داده در شرکت AQR ساخته بود، در ۲۰۰۸
> بسته‌ای نوشت به اسم `pandas` (از واژه‌ی panel data) و در ۲۰۰۹ عمومی‌اش کرد.
> فکر اصلی‌اش از R می‌آمد: جدول یعنی **ستون‌هایی به اسم‌های معنادار**، نه
> آرایه‌ی عددیِ بی‌نام.

> **این بخش جواب می‌دهد:** DataFrame دقیقاً چیست، چه کارهایی با آن در یک
> خط انجام می‌شود، و چرا `groupby` قلبِ تحلیلِ داده است.

- **چرا وجود دارد:** داده‌ی واقعی (CSV دیتابیس، خروجی API، فایل اکسل) همیشه **جدولی** است: سطر و ستون، با ستون‌هایی از جنس متن و عدد و تاریخ. در جاوااسکریپت برای هر فیلتر و گروه‌بندی باید ده‌ها خط حلقه می‌نوشتی. pandas این کارهای تکراری را از قبل نوشته و بهینه کرده است.
- **به زبان ساده:** یک **صفحه‌ی محاسبه** (مثل Excel) که با یک زبان برنامه‌نویسی راه می‌آید. می‌توانی ستون اضافه کنی، ردیف‌ها را فیلتر کنی، بر اساس یک ستون گروه‌بندی کنی و میانگین بگیری — همه در چند خط.

### دو نوع داده که همه‌جا لازم داری

پایتون فقط **یک** نوع داده برای این کارها دارد، به اسم **Series**. اگر این را بفهمی، بقیه‌ی pandas جا می‌افتد:

- **Series**: یک **ستون** — یعنی یک آرایه‌ی یک‌بعدی که هر عضوش یک **برچسب** (اندیس) دارد، نه فقط یک شماره. یعنی هر مقدار می‌داند «مال کیست».
- **DataFrame**: یک **جدول دوبعدی** که از چند **Series** با اندیس یکسان ساخته شده — یعنی هر ستون یک Series است و همه‌شان در «شماره‌ی ردیف» با هم هماهنگ‌اند.

**تشخیصشان از هر کجا:** اگر فقط **یک ستون** را برداری، Series؛ اگر **چند ستون** برداری، DataFrame. همین قاعده همه‌جا در pandas برقرار است.

### خواندن و شناخت داده

```python
import pandas as pd

df = pd.read_csv("users.csv")   # ⭐ خواندن فایل CSV به شکل DataFrame
df.head()                        # ۵ ردیف اول — برای یک نگاه سریع
df.info()                        # تعداد ردیف، نام ستون‌ها، نوع هر ستون، مقادیر گمشده
df.describe()                    # آمار عددی: میانگین، انحراف معیار، کمینه و بیشینه
```

`df.head()` اولین چیزی است که بعد از هر `read_csv` باید بزنی — در یک ثانیه می‌فهمی داده‌ی تو اصلاً شبیه چیزی هست که فکر می‌کردی یا نه.

### انتخاب: ستون و فیلتر



```python
df["age"]                    # یک ستون (Series)
df[["name", "email"]]        # چند ستون (DataFrame)
df[df["age"] > 25]           # فیلتر — یک ماسک True/False
df[df["city"].isin(["تهران", "شیراز"])]
df[df["age"].between(18, 65)]
df.query("age > 25 and city == 'تهران'")
```

**قانون مهم:** فیلتر کردن همیشه **دو گام** است. اول یک ماسک `True/False` بساز، بعد با `df[ماسک]` انتخاب کن. همین ترکیب باعث می‌شود بتوانی چند شرط را با `&` و `|` (و `~` برای «برعکس») کنار هم بگذاری:

```python
mask = (df["age"] > 25) & (df["city"] == "تهران")
result = df[mask]                    # کاربران ۲۵+ در تهران
result = df[~df["email"].isna()]     # ردیف‌هایی که ایمیل دارند
```

### گروه‌بندی و آمار

```python
stats = df.groupby("city")["salary"].agg(
    count="count",
    mean="mean",
    median="median",
    std="std",
).sort_values("mean", ascending=False)
```

**`groupby` سه گام دارد:** اول بر اساس کدام ستون گروه کنم، بعد روی کدام ستون محاسبه کنم، آخر چه محاسبه‌ای. اینجا: گروه بر اساس `city`، روی ستون `salary`، با میانگین و میانه و انحراف معیار.

### تبدیل و ساخت ستون تازه

```python
df["age_group"] = pd.cut(df["age"], bins=[0, 18, 35, 50, 100],
                         labels=["نوجوان", "جوان", "میان‌سال", "مسن"])
df["name"] = df["name"].str.strip().str.lower()
```

`pd.cut` داده‌ی پیوسته (سن) را به **دسته** تبدیل می‌کند. نکته: `df["ستون"] = ...` همیشه **ستون را می‌سازد یا جایگزین** می‌کند — همین الگو برای هر ستون محاسباتی تکرار می‌شود.

### داده‌ی گمشده

```python
df.isna().sum()                      # چند تا NaN داریم؟
df["age"].fillna(df["age"].median())
df.dropna(subset=["email"])
```

**`NaN`** یعنی «مقدار غایب» — pandas به‌جای خالی، این نشان را می‌گذارد. اول **بشمار** تا بدانی چقدر مشکل داری، بعد تصمیم بگیر: پر کردن با میانه (`fillna`) یا حذف کردن ردیف‌های ناقص (`dropna`).

### ادغام دو جدول

```python
users.merge(orders, on="user_id", how="left")
```

**`merge`** جدول‌ها را با یک ستون مشترک (`user_id`) به هم می‌چسباند. `how="left"` یعنی «همه‌ی ردیف‌های جدول اصلی بمانند، حتی اگر در جدول دیگر معادلی نداشته باشند» — اگر به‌جایش `inner` بگذاری، ردیف‌های بدون تطابق حذف می‌شوند.

### پنجره‌ی زمانی

```python
df["date"] = pd.to_datetime(df["date"])
df.set_index("date")["amount"].resample("D").sum()
```

ابتدا ستون تاریخ باید واقعاً از نوع تاریخ باشد (`pd.to_datetime`) — وگرنه `resample` کار نمی‌کند. بعد با `set_index` تاریخ می‌شود کلید جدول، و `resample("D")` همه را در **سطل‌های روزانه** جمع می‌زند.

### نقشه‌ی سریع — کدام تابع، کِی؟

هر ردیف همان چیزی است که در بالا یاد گرفتی؛ این جدول فقط برای پیدا کردن سریع موقع کار است:

- **خواندن** (`read_csv`, `read_json`, `read_parquet`): داده‌ی ورودی را از فایل به DataFrame می‌آورد. قبل از اجرای هر تحلیلی، ابتدا `head()` و `info()` را بزن.
- **انتخاب** (`df[col]`, `df[cond]`, `df.query()`): یک ستون یا چند ستون را برمی‌دارد، یا ردیف‌ها را با شرط فیلتر می‌کند.
- **گروه‌بندی** (`df.groupby().agg()`): بر اساس یک ستون گروه می‌کند، سپس روی ستون دیگر آمار (میانگین، شمارش،...) می‌گیرد.
- **ادغام** (`merge()`, `join()`, `concat()`): دو جدول را کنار هم می‌گذارد. `merge` (کلید مشترک) رایج‌ترین، `concat` (روی هم چیدن ساده‌ی ردیف‌ها) ساده‌ترین است.
- **پنجره‌ی زمانی** (`resample()`): ستون تاریخ باید ابتدا به اندیس و به نوع درست تبدیل شود، سپس در سطل‌های زمانی (روز، هفته، ماه) جمع می‌زند.
- **تبدیل نوع** (`astype()`, `pd.to_datetime()`): نوع یک ستون را عوض می‌کند — از متن به عدد، یا از متن به تاریخ.
- **داده‌ی گمشده** (`fillna()`, `dropna()`, `isna()`): `isna()` می‌شمارد، `fillna()` پر می‌کند، `dropna()` حذف می‌کند. ترتیب مهم است: اول بشمار، بعد تصمیم بگیر.

### Tensor — مفهوم بنیادی

**Tensor** (تنسور) آرایه‌ی چندبعدیِ قابل محاسبه روی GPU است. همان `shape` و `dtype` NumPy را دارد با یک تفاوت حیاتی: هر عملیاتی روی آن، **گراف محاسباتی** (گراف عملیاتی) می‌سازد تا بعداً بتوانی **به عقب** حساب کنی که هر وزن چقدر در خطا نقش داشته — همان چیزی که در بخش `backward()` می‌بینی.

- **به زبان ساده:** یک آرایه که هم روی پردازنده‌ی گرافیکی (GPU) می‌تواند اجرا شود و هم می‌داند از کجا آمده تا یاد بگیرد اشتباه کجا بوده.

`device` یعنی کجا زندگی می‌کند: `cpu` یا `cuda:0` (کارت گرافیک).

```python
import torch

x = torch.tensor([[1.0, 2.0], [3.0, 4.0]])
x.shape      # torch.Size([2, 2])
x.dtype      # torch.float32
x.device     # cpu یا cuda:0

x.cuda()                              # انتقال به GPU
x.to("cuda", dtype=torch.float16)     # ⭐ half precision — حافظه نصف، سرعت بیشتر
```

### `nn.Module` — ساخت هر شبکه

**`nn.Module`** کلاس پایه‌ی هر شبکه‌ی عصبی در PyTorch است. کاری که می‌کند: **وزن‌ها (پارامترها) را نگه می‌دارد و ثبت می‌کند** تا ابزار آموزش بتواند آن‌ها را پیدا و به‌روز کند.

- **چرا subclass می‌کنی؟** تا لایه‌هایت (`nn.Linear`, `nn.ReLU`) را در `__init__` بسازی و متد `forward` را بنویسی. `forward` یعنی «وقتی داده‌ای دادم، این کار را کن» — یعنی **پیش‌بینی (شامل گرادیان‌ها)**.
- **`self.layers = nn.Sequential(...)`** یعنی لایه‌ها را به ترتیب در یک جعبه می‌گذاری تا با یک `self.layers(x)` اجرا شوند.

تابع **فعال‌سازی** (activation) مثل `ReLU` غیرخطی بودن اضافه می‌کند — بدون آن، هر تعداد لایه فقط یک خط می‌شود و عملاً هیچ‌چیز یاد نمی‌گیرد. `Dropout` هم موقع آموزش بعضی نورون‌ها را خاموش می‌کند تا مدل به‌جای حفظ کردن، الگو یاد بگیرد (جلوگیری از **بیش‌برازش** / overfitting).

```python
import torch
import torch.nn as nn

class Classifier(nn.Module):
    def __init__(self, input_dim: int, hidden: int, num_classes: int):
        super().__init__()
        self.layers = nn.Sequential(
            nn.Linear(input_dim, hidden),
            nn.ReLU(),              # تابع فعال‌سازی غیرخطی
            nn.Dropout(0.2),        # جلوگیری از overfitting
            nn.Linear(hidden, hidden),
            nn.ReLU(),
            nn.Linear(hidden, num_classes),
        )

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.layers(x)

model = Classifier(784, 256, 10)
```

### آموزش — حلقه‌ی پنج‌مرحله‌ای

پیش از دیدن کد، هفت واژه‌ی این حلقه را بشناس — این همان چیزی است که هر مدل یادگیری ماشین در نهایت انجام می‌دهد:

- **batch** (دسته): تعداد نمونه‌هایی که در یک قدم به مدل نشان داده می‌شود (مثلاً ۳۲ تصویر با هم). همه‌ی داده‌ها یک‌جا حافظه نمی‌خواهد.
- **epoch** (دور): یک بار که مدل **تمام** داده‌ی آموزشی را دیده. `for epoch in range(10)` یعنی ده بار روی کل داده.
- **loss** (تابع هزینه): یک **عدد** که می‌گوید پیش‌بینی مدل چقدر از جواب واقعی دور است. کمتر = بهتر. این عددِ قابل کم شدن، هدف کل یادگیری است.
- **criterion**: همان تابعی که loss را حساب می‌کند (`nn.CrossEntropyLoss` اینجا یعنی «برای کار دسته‌بندی، خطا را این‌طور حساب کن»).
- **optimizer**: چیزی که تصمیم می‌گیرد وزن‌ها **چقدر و به کدام سمت** تغییر کنند (`Adam` اینجا، با `lr=1e-3` یعنی نرخ یادگیری هر قدم).
- **autograd** (محاسبه‌ی خودکار گرادیان): سیستم PyTorch که موقع ساختن تنسورها، همه‌ی عملیات را ثبت می‌کند تا بعداً زنجیره را **به عقب** پیمایش کند.
- **`backward()`**: همان پیمایش به عقب — از loss شروع می‌کند و **گرادیان** (شیبِ خطا نسبت به هر وزن) را برای همه‌ی وزن‌ها حساب می‌کند. این بخش، همون کاری که یادگیری ماشین را از یک محاسبه‌ی ساده جدا می‌کند.

```python
model = Classifier(784, 256, 10)
criterion = nn.CrossEntropyLoss()               # تابع هزینه
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)

for epoch in range(10):
    model.train()                                  # ⭐ حالت آموزش
    for images, labels in train_loader:
        optimizer.zero_grad()                      # ① صفر کردن گرادیان
        outputs = model(images)                    # ② پیش‌بینی
        loss = criterion(outputs, labels)          # ③ محاسبه‌ی خطا
        loss.backward()                            # ④ محاسبه‌ی گرادیان (backprop)
        optimizer.step()                           # ⑤ به‌روزرسانی وزن‌ها

    # ارزیابی روی داده‌ی اعتبارسنجی
    model.eval()                                    # ⭐ حالت ارزیابی
    with torch.no_grad():                           # ⭐ بدون محاسبه‌ی گرادیان
        val_loss = evaluate(model, val_loader)
    print(f"Epoch {epoch}: loss={loss.item():.4f} val={val_loss:.4f}")
```

> 🔑 **`model.train()` و `model.eval()` را فراموش نکن.** این‌ها لایه‌هایی مثل Dropout و BatchNorm را عوض می‌کنند. فراموش کردنشان یعنی ارزیابی‌ات **غلط** است.

### چرا `no_grad()`؟

محاسبه‌ی گرادیان حافظه‌ی زیادی مصرف می‌کند (گراف محاسباتی را نگه می‌دارد). در ارزیابی که آموزشی در کار نیست، این حافظه کاملاً بی‌فایده است.

## ۱۰. تست در پایتون

> 🧒 **داستان این بخش:** یک تابع را عوض کردی. همه‌چیز در نگاه اول کار می‌کرد،
> ولی یک جای پنهان خراب شده بود. پیدا کردنش سه روز طول کشید — و آن مشتری
> زودتر از تو فهمیده بود.

> مشکل این است که تست، هزینه‌ی اولیه دارد: باید پیش از مشکل، بنویسی.
> کسی که فقط وقتی مشکل دارد تست می‌نویسد، هیچ‌وقت به آن مرحله نمی‌رسد.
>
> راه‌حلِ عملی: تست را **کنار** کد بنویس، نه قبل یا بعد از آن. یک تست = یک
> رفتار. نامِ تست خودش توضیح می‌دهد چه چیزی خراب شده.
>
> **این بخش جواب می‌دهد:** سه نوع تست (واحد، یکپارچه، API) چه فرقی دارند،
> fixture چیست، و چرا تستِ سریع باید کلِ کار را در چند ثانیه تمام کند.

```python
import pytest
from httpx import AsyncClient

# ---------- Fixture: داده‌ی مشترک بین تست‌ها ----------
@pytest.fixture
async def client():
    async with AsyncClient(app=app, base_url="http://test") as ac:
        yield ac

# ---------- تست ساده ----------
def test_add():
    assert add(2, 3) == 5

# ---------- تست پارامتری (همان تست، ورودی‌های مختلف) ----------
@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (-1, 1, 0),
    (0, 0, 0),
    (2.5, 2.5, 5.0),
])
def test_add_param(a, b, expected):
    assert add(a, b) == expected

# ---------- تست API ----------
@pytest.mark.asyncio
async def test_create_user(client: AsyncClient):
    response = await client.post("/users", json={
        "email": "ali@test.com", "name": "علی",
    })
    assert response.status_code == 201
    assert response.json()["email"] == "ali@test.com"

# ---------- mock ----------
from unittest.mock import AsyncMock, patch

async def test_llm_failure_returns_fallback():
    with patch("app.services.llm.generate", new=AsyncMock(
        side_effect=TimeoutError()
    )):
        result = await generate_answer("سوال")
        assert result == "متأسفم، خطایی رخ داد"
```

## ۱۱. مدیریت خطا و پایتونی بودن

> 🧒 **داستان این بخش:** برنامه‌ات کرش کرد. ولی پیام خطا این بود:
> `Exception` — و هیچ‌چیز دیگری. یک ساعت وقت گذاشتی تا بفهمی **کجا** و **چرا**.
>
> مشکل این بود که یک کلاس خطا، همه‌ی خطاها را گرفت — حتی اشتباهات تایپیِ ساده.
> درست مثل این است که دکمه‌ی «توقف اضطراری» ساختمار را به اپراتور بزنی تا شاید
> اصلاحی باشد.
>
> راه‌حل پایتونی: **کلاس خطای خودت را بساز**، دقیق بگو چه شده، و اجازه بده
> خطای واقعی بالا برود. کدی که خودش می‌داند چه کند، دیگر به راهنما نیاز ندارد.
>
> **این بخش جواب می‌دهد:** exception chaining چه می‌کند، چه وقت
> `raise` از پیام استفاده می‌کنی و چه وقت نه، و چرا `except Exception: pass` بدترین خطاست.

```python
# ❌ استثنای عمومی — کلاس خطاهای خودت را گم می‌کنی
try:
    result = process(data)
except:                        # ❗ نه! حتی KeyboardInterrupt را می‌بلعد
    print("خطا")
except Exception as e:         # بهتر، ولی هنوز کلی
    print(f"خطا: {e}")

# ✅ کلاس خطای اختصاصی
class AppError(Exception):
    """خطای پایه‌ی برنامه — همه‌ی خطاهای ما از این ارث می‌برند"""
    status_code = 500

class NotFoundError(AppError):
    status_code = 404

class ValidationError(AppError):
    status_code = 422

# ✅ استفاده
try:
    user = await repo.get(user_id)
    if not user:
        raise NotFoundError("کاربر یافت نشد")
except AppError as e:
    logger.warning(f"{type(e).__name__}: {e}")
    raise HTTPException(e.status_code, str(e)) from e
```

### ترتیب `except` — از خاص به عمومی

```python
try:
    ...
except NotFoundError:       # ⭐ اول خاص‌ترین
    return None
except ValidationError:
    return default
except AppError as e:       # بعد عمومی‌تر
    logger.error(e)
    raise
# ❌ هرگز Exception عمومی را اول ننویس — همه‌چیز را می‌بلعد
```

### زنجیره‌ی استثنا — `raise ... from`

```python
try:
    data = json.loads(raw)
except json.JSONDecodeError as e:
    # ⚠️ بدون from: پیام اصلی گم می‌شود
    raise ValueError("داده نامعتبر است")

    # ✅ with from: علت اصلی حفظ می‌شود
    raise ValueError(f"داده نامعتبر است: {raw[:50]}") from e
```

## ۱۲. ابزارهای کیفیت کد

> 🧒 **داستان این بخش:** یک تیم تصمیم گرفت که هیچ‌کس کدِ خود را دستی
> **کامیت** نکند مگر اینکه سه بررسی خودکار ردش کند. اولین هفته، ده‌ها خطای
> ریز پیدا شد که کسی آن‌ها را ندیده بود.
>
> نکته‌ی مهم این بود که هیچ‌کس نگفت «از این به بعد مواظب باشید». گفتند: **ابزار**.
> یک ابزارِ خودکار که **قبل از هر کامیت** اجرا می‌شود، خطاهایی را می‌گیرد که
> چشمِ آدم در آن‌ها خسته می‌شود.
>
> یک‌بار **type checker** و **linter** را معرفی کردیم. لینتر مثل یک معلمِ سخت‌گیر
> است که نگارش را می‌گیرد. Type checker مثل یک حسابرس است: نوعِ هر متغیر را می‌داند.
>
> **این بخش جواب می‌دهد:** type checker، linter و formatter چه کار می‌کنند و
> چه چیزی را پیدا می‌کنند که تست پیدا نمی‌کند — و چطور با pre-commit خودکارشان کنیم.

| ابزار | نقش | جایگزین |
|-------|------|---------|
| `ruff` | lint + format (خیلی سریع) | flake8 + black + isort |
| `mypy` / `pyright` | type checking جدی | — |
| `pytest` | تست | unittest |
| `black` | format (اگر ruff نخواهی) | — |
| `pre-commit` | اجرای خودکار قبل از commit | — |
| `ipython` | REPL بهتر از REPL پیش‌فرض | — |

```toml

## ۱۳. الگوی ترکیبی: Node + Python

> 🧒 **داستان این بخش:** یک شرکت دو تیم داشت: یکی وب (Node) و یکی علم داده
> (Python). مشتری می‌خواست یک گزارشِ سنگین بگیرد، ولی گزارش‌ساز در پایتون بود و
> بقیه‌ی سایت در جاوااسکریپت. کد را کجا می‌نوشتند؟

> پاسخِ قدیمی این بود: یک سیستمِ بزرگِ پایتون که **همه‌چیز** را با خودش
> انجام می‌داد — حتی بخش‌هایی که جاوااسکریپت بهتر انجام می‌داد.
>
> راه‌حل امروزی برعکس است: **هر زبان کارِ خودش را** و سرویس‌ها از طریق
> HTTP با هم حرف می‌زنند. و پایتون و جاوااسکریپت هر دو یک چیز مشترک دارند:
> **رویداد حلقه‌ی ناهم‌زمان**. پس برنامه‌نویسِ یک زبان، می‌تواند هر دو را بخواند.

> **این بخش جواب می‌دهد:** چه وقت دو زبان را با هم به کار ببریم، مرزِ سرویس
> کجا باید باشد، و چرا زبانِ «قوی‌تر» انتخاب نمی‌کنیم بلکه زبانِ **مناسبِ کار** را.

سیستم واقعی معمولاً این شکلی است:

┌─────────────────────────────────────────────────┐

                ↓
┌─────────────────────────────────────────────────┐

│  • تماس با مدل زبانی                            │

                │
                ↓
        [PostgreSQL]  [Redis]  [Vector DB]
```

> 🔑 **چرا دو زبان؟** چون ابزارها در یک زبان بهترند. Node برای وب، پایتون برای AI. اجبار به یکی، انتخاب‌های بدتری تحمیل می‌کند.

> 💡 **نکته‌ی عملی:** ارتباط بین این دو را ساده نگه دار — `REST` یا `gRPC`. پیچیدگی معماری توزیع‌شده در مقیاس کوچک، فقط هزینه است.

#flashcards

**کارت ۱ — چرا پایتون را باید جدی type check کرد؟**
چون type hint در پایتون اجباری نیست و در زمان اجرا بررسی نمی‌شود. بدون `mypy --strict`، یک خطای نوع می‌تواند ماه‌ها در کد بماند و فقط در production کرش کند.

**کارت ۲ — broadcasting چیست؟**
قابلیت NumPy که آرایه‌های با شکل متفاوت را خودکار به شکل مشترک گسترش می‌دهد تا عملیات ممکن شود. `np.array([1,2,3]) + 10` → `[11,12,13]`. جایگزین بسیار سریع‌تر حلقه.

**کارت ۳ — تفاوت `axis=0` و `axis=1` در pandas؟**
`axis=0` یعنی حرکت روی محور ردیف‌ها — نتیجه برای هر ستون. `axis=1` یعنی حرکت روی محور ستون‌ها — نتیجه برای هر ردیف. `df.sum(axis=0)` مجموع هر ستون می‌دهد.

**کارت ۴ — چرا `model.eval()` و `torch.no_grad()` مهم‌اند؟**
`eval()` لایه‌هایی مثل Dropout و BatchNorm را در حالت ارزیابی می‌گذارد (وگرنه ارزیابی‌ات غلط است). `no_grad()` گراف محاسباتی را نمی‌سازد، پس حافظه مصرف نمی‌شود.

**کارت ۵ — FastAPI چه چیزی به تو می‌دهد که Express نمی‌دهد؟**
اعتبارسنجی خودکار با Pydantic، مستندات خودکار Swagger (`/docs`)، و type hint محوری. در عوض، TypeScript و اکوسیستم وب فراوان ندارد.

**کارت ۶ — چرا `uv` بهتر از `pip` است؟**
چون ۱۰ تا ۱۰۰ برابر سریع‌تر است (استفاده از Rust) و مدیریت lockfile یکپارچه دارد. `uv sync` محیط را قطعی و تکرارپذیر می‌کند.

**کارت ۷ — خطر اصلی نوتبوک چیست؟**
وابستگی به ترتیب اجرای سلول‌ها. کدی که در نوتبوک کار می‌کند ممکن است در اجرای تمیز شکست بخورد چون متغیری تعریف‌نشده یا `pip install` فراموش‌شده دارد.

**کارت ۸ — چرا `raise ... from e` مهم است؟**
بدون آن، علت اصلی استثنا در زنجیره گم می‌شود و فقط پیام خودت را می‌بینی. با آن، ردیابی خطا کامل است — می‌فهمی مشکل ریشه‌ای از کجا آمده.
