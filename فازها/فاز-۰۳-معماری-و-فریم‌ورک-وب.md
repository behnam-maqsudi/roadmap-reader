# فاز ۳ — معماری نرم‌افزار و فریم‌ورک‌های وب

> 🧒 **داستان:** تا اوایل ۲۰۱۰، نوشتن یک مسیر `/api/users` در وب یعنی کپی‌کردن
> چند خط از این پروژه به آن پروژه. یک نفر برای خواندن دفترچه‌ی کاربر از دیتابیس
> کد نوشته بود، نفر دوم همان کد را با یک تغییر کوچک نوشته بود، و نفر سوم
> همین کد را دوباره ولی با یک باگ. کار درست بود، ولی هیچ‌کس نمی‌دانست این کد
> **چه** می‌کند، **کِی** اجرا می‌شود و **قبل از آن** چه باید بگذرد.
>
> آن سال یک برنامه‌نویس به اسم **TJ Holowaychuk** در پروژه‌ای به نام Sinatra
> ایده‌ی برعکس را نوشت: وب‌سرور باید کوچک باشد و ابزار زیاد نداشته باشد.
> در نوامبر ۲۰۱۰** همین فکر را برداشت و به سمتِ مخالفش رفت: Express ساخت،
> ولی با این ایده که هر کار کوچکی (خواندن هدر، ثبت لاگ، بررسی نشست) یک قطعه‌ی
> جدا باشد — یک **لایه**. هر قطعه بتواند نگذارد قطعه‌ی بعدی اجرا شود. این
> قطعه‌ها همان **middleware** هستند.
>
> این فاز از همان لحظه شروع می‌شود: یک برنامه‌ی ۸۰ خطی که خودت می‌نویسی و
> هر خطش را می‌فهمی، تبدیل می‌شود به برنامه‌ای که بزرگ شده و باز هم می‌فهمی
> چرا هر خط آنجاست.

## مقدمه: چرا حالا فریم‌ورک؟

در فاز ۲ یک وب‌سرور خام ساختیم و فهمیدیم زیر کاپوت چه می‌گذرد. حالا وقت آن است که ابزارهای واقعی را یاد بگیریم — ولی نه به‌عنوان «جادو»، بلکه به‌عنوان **لایه‌ای که می‌دانیم دقیقاً چه کار می‌کند و چه هزینه‌ای دارد**.

دو واژه در ادامه‌ی این فاز زیاد تکرار می‌شوند، پس همان اول روشنشان می‌کنیم (هر دو در همین فاز کامل باز می‌شوند):

- **middleware (میان‌افزار):** تابعی که روی هر درخواست، **قبل یا بعد** از منطق اصلی، اجرا می‌شود — مثلاً احراز هویت یا لاگ. تعریف کامل و امضای تابعش در بخش ۱ همین فاز است.
- **route (مسیر):** اتصال میان یک آدرس مشخص (مثل `GET /api/users`) و تابعی که باید هنگام فراخوانی‌اش اجرا شود. ساختار و پیاده‌سازی‌اش را در بخش ۵ می‌بینی.

> 💡 تفاوت یک مهندس با یک برنامه‌نویس در همین است: وقتی فریم‌ورک وسط می‌آید، می‌داند middleware اولویت دارد یا ترتیب routeها، و می‌داند چرا سرعتش ۲ برابر شد.

## ۱. لایه‌ی Middleware — قلب فریم‌ورک

> 🧒 **داستان این بخش:** یک رستوران را تصور کن که پیش از رسیدن به آشپزخوان،
> سه نفر باید کار کنند: نگهبان در را باز می‌کند، پیشخوان‌دار سفارش را می‌گیرد،
> حسابدار بعداً حساب می‌کند. هر کدام کار خودش را می‌کند و **نمی‌دانند** بقیه
> چه می‌کنند. در Express هم هر کار کوچک دقیقاً همین‌طور است: هر لایه‌ی میانی
> درخواست را می‌گیرد، کار خودش را می‌کند، یا نگه می‌دارد.

> مشکل این بود که قبلاً این سه نفر را باید **دستی** در هر مسیر صدا می‌زدی.
> اگر یکی یادت می‌رفت، امنیت سوراخ می‌شد. Express این‌طوری کرد که لایه‌ها
> خودشان به ترتیب روی هم سوار می‌شوند.
>
> **این بخش جواب می‌دهد:** لایه‌ی میانی دقیقاً چیست، ترتیب اجرای لایه‌ها چطور
> کار می‌کند، و چطور با `next()` یک لایه جلوی بقیه را می‌گیرد.

### چرا وجود دارد؟

یک سرور واقعی ده‌ها کار تکراری دارد که **قبل و بعد** از منطق اصلی درخواست اتفاق می‌افتد: احراز هویت، لاگ، کش، اعتبارسنجی، فشرده‌سازی، CORS. اگر این‌ها را در هر route تکرار کنی، پروژه غیرقابل نگهداری می‌شود.

- **به زبان ساده:** مثل ایستگاه‌های امنیتی در مسیر ورود به یک ساختمان. هر کسی که می‌خواهد وارد شود، از ایستگاه‌های رد می‌شود: اول کارت، بعد باربری، بعد آسانسور.
- **به زبان فنی:** تابعی با امضای `(req, res, next)` که می‌تواند درخواست را **تغییر دهد**، **متوقف کند**، یا **به بعدی بسپارد**.

### ترتیب اجرا — نکته‌ای که همه را غافلگیر می‌کند

```typescript
app.use(express.json());                    // ①
app.use(authMiddleware);                    // ②
app.get('/admin', adminOnly, handler);      // ③
app.use(errorHandler);                      // ④
```

**خروجی واقعی:**
```text
① json parser
② auth
③ adminOnly
   handler
④ errorHandler      ← فقط وقتی خطایی throw شود
```

🔑 **قواعد حیاتی:**

| قاعده | چرا |
|-------|-----|
| middleware‌ها به **ترتیب ثبت** اجرا می‌شوند | قبل از اینکه اضافه کنی، فکر کن کجا باید بنشیند |
| اگر `next()` صدا نزنی، زنجیره **متوقف** می‌شود | پس `res.send()` و `next()` را با هم قاطی نکن |
| middleware سطح‌بالا **فقط برای routeهای بعد از خودش** است | برای همه‌ی routeها، اول از همه ثبتش کن |
| error handler **باید ۴ آرگومان** داشته باشد | `function (err, req, res, next)` — وگرنه Express آن را نمی‌شناسد |

### چهار الگوی رایج Middleware

#### ۱. الگوی ثبت‌نام (Logging)

**یعنی چه:** ثبت یک خط لاگ برای هر درخواست، همراه با زمان پاسخ دادن — تا بعداً بتوانی کندترین مسیرها را پیدا کنی.

```typescript
function logger(req, res, next) {
  const start = Date.now();
  res.on('finish', () => {
    const duration = Date.now() - start;
    logger.info({
      method: req.method,
      path: req.originalUrl,
      status: res.statusCode,
      duration: `${duration}ms`,
    });
  });
  next();   // ادامه بده
}
```

#### ۲. الگوی احراز هویت (Guard)

**یعنی چه:** نگهبانِ ورودی؛ قبل از اجرای منطق اصلی بررسی می‌کند که درخواست اجازه‌ی عبور دارد یا نه، و اگر نداشت همان‌جا با ۴۰۱ یا ۴۰۳ متوقفش می‌کند.

```typescript
function requireAuth(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) {
    return res.status(401).json({ error: 'وارد نشده‌اید' });   // ← next() نکن
  }
  req.user = verifyToken(token);
  next();
}
```

#### ۳. الگوی میان‌افزار اندازه‌گیری (Metrics)

**یعنی چه:** ثبت عددهای آماری (Metrics) — مثل زمان پاسخ، تعداد درخواست و نرخ خطا — به‌جای متن لاگ، در قالبی که ابزارهای داشبورد بتوانند رویش نمودار بکشند.

```typescript
function metrics(req, res, next) {
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const ns = process.hrtime.bigint() - start;
    histogram.observe({ route: req.route?.path }, Number(ns) / 1e6);
  });
  next();
}
```

#### ۴. الگوی Circuit Breaker (تاب‌آوری)

**یعنی چه:** کلید قطع خودکار. وقتی یک سرویس پایین‌دست پشت‌سرهم خطا می‌دهد، این کلید **باز می‌شود** و به‌جای تلاش دوباره، فوراً خطا برمی‌گرداند؛ بعد از مدتی دوباره بسته می‌شود و یک درخواست آزمایشی می‌فرستد. نتیجه: سرور تو در قبال خرابی سرویس پایین‌دست، خودش هم نمی‌میرد.

```typescript
function circuitBreaker(threshold = 5, resetMs = 30_000) {
  let failures = 0;
  let openedAt = 0;

  return (req, res, next) => {
    if (Date.now() - openedAt < resetMs && failures >= threshold) {
      return res.status(503).json({ error: 'سرویس موقتاً در دسترس نیست' });
    }
    res.on('finish', () => {
      if (res.statusCode >= 500) {
        failures++;
        if (failures >= threshold) openedAt = Date.now();
      } else {
        failures = 0;
      }
    });
    next();
  };
}
```

> 💡 این middleware آخر، همان چیزی است که در **فاز ۰ بخش ۶** خواندی — آنجا مفهوم Circuit Breaker و اینکه چرا در تاب‌آوری لازم است کامل توضیح داده شد؛ حالا اینجا پیاده‌اش می‌کنی.

## ۲. Rate Limiting در عمل

> 🧒 **داستان این بخش:** یک اسکریپت که پسورد را امتحان می‌کند، کاری نمی‌کند
> جز اینکه هزار بار در ثانیه به درب می‌کوبد. اگر درب هر بار باز شود، دزد
> بالاخره وارد می‌شود — و تا آن‌وقت، بقیه‌ی مشتریان هم پشت درب گیر کرده‌اند.
> راه‌حل اسمش **rate limit** است: در یک بازه‌ی زمانی، بیشتر از N درخواست
> از یک مبدأ را قبول نکن.

> این مبحث وجود دارد چون دیدنِ IP و شمردن ساده نیست؛ در بکاپ‌های واقعی،
> پشتِ CDN همه از یک IP می‌آیند و باید کلید درست انتخاب شود.
>
> **این بخش جواب می‌دهد:** چطور جلوی درخواست بیش از حد را بگیریم، کدام
> الگوریتم (پنجره‌ی لغزان) چقدر دقیق‌تر است، و چطور با Redis در چند سرور پیاده شود.

### چرا وجود دارد؟

سه دلیل متفاوت — و اشتباه در تشخیصشان، راه‌حل اشتباه می‌سازد:

| نوع مهاجم | مشکل | راه‌حل |
|-----------|------|--------|
| **اسپم** | یک کاربر بی‌سروصدا صدها درخواست می‌فرستد | محدودیت بر اساس **کاربر** |
| **DDoS** | هزاران کاربر مختلف یک endpoint را می‌زنند | محدودیت بر اساس **IP** |
| **مصرف منابع** | یک endpoint گران، بار زیادی روی سرور می‌آورد | محدودیت بر اساس **مسیر** و **هزینه** |

### الگوریتم‌ها — از ساده به دقیق

#### Fixed Window
- **ساده:** در هر بازه‌ی ثابت (مثلاً هر دقیقه) شمارش می‌کنی.
- **مشکل:** در مرز بازه‌ها، کاربر می‌تواند **دو برابر** مجاز درخواست بفرستد.

```text
ساعت ۰۹:۵۹:۵۹ → ۱۰۰ درخواست در ثانیه ۵۹
ساعت ۱۰:۰۰:۰۰ → ۱۰۰ درخواست در ثانیه ۰۰
= ۲۰۰ درخواست در ۱ ثانیه، در حالی که limit ۱۰۰ است!
```

#### Sliding Window
- **دقیق‌تر:** پنجره به‌جای تثبیت، **حرکت** می‌کند.
- **هزینه:** محاسبه‌ی بیشتر (باید تاریخچه‌ی درخواست‌ها را نگه داری).

#### Token Bucket — پرکاربردترین
- **منطق:** یک سطل با ظرفیت مشخص داری که با نرخ ثابت (مثلاً ۱۰ توکن در ثانیه) پر می‌شود. هر درخواست یک توکن مصرف می‌کند. اگر توکن نداشتی، رد شو.

```typescript
function tokenBucket(capacity = 10, refillPerSecond = 2) {
  let tokens = capacity;
  let lastRefill = Date.now();

  return (req, res, next) => {
    const now = Date.now();
    const elapsed = (now - lastRefill) / 1000;
    tokens = Math.min(capacity, tokens + elapsed * refillPerSecond);
    lastRefill = now;

    if (tokens < 1) {
      res.setHeader('Retry-After', Math.ceil(1 / refillPerSecond));
      return res.status(429).json({ error: 'تعداد درخواست‌ها بیش از حد مجاز' });
    }

    tokens -= 1;
    next();
  };
}
```

> 💡 **چرا Token Bucket؟** برخلاف Fixed Window، اجازه‌ی **burst** (جهش) طبیعی می‌دهد. اگر کاربر ۱ ساعت بی‌کار بوده و یک‌باره ۲۰ درخواست می‌فرستد، مجاز است — ولی در ۱ ثانیه بیش از حد نیست. این دقیقاً رفتار انسانی واقعی است.

> ⚠️ **در پروداکشن:** شمارنده باید در **Redis** باشد، نه حافظه‌ی فرایند. اگر ۳ نمونه سرور داشته باشی و شمارنده در حافظه باشد، هر کدام سقف جداگانه اعمال می‌کنند و کاربر **۳ برابر** می‌تواند درخواست بدهد.

## ۳. لایه‌بندی پروژه — سه لایه، نه یک عالمه

> 🧒 **داستان این بخش:** یک آشپزخانه‌ی شلوغ را تصور کن: سرآشپز، کمک آشپز،
> ظرف‌شوی — همه در یک اتاق دارند کار می‌کنند و مدام همدیگر را می‌زنند. کار
> انجام می‌شود ولی هیچ‌کدام کار خود را تا آخر نمی‌بندد و هیچ‌چیز قابل تست
> نیست. راه‌حل: **اتاق‌ها را جدا کن.** این‌ها همان سه لایه‌ای هستند که
> الان می‌سازیم — ورودی (دریافت و اعتبارسنجی)، منطق (کار اصلی)، خروجی
> (شکل پاسخ).

> چرا برای ما مهم است؟ چون همین تفکیک اجازه می‌دهد منطق را **بدون دیتابیس**
> تست کنی — و تستِ منطق، سریع‌ترین تستِ دنیاست.
>
> **این بخش جواب می‌دهد:** چرا «سه لایه» و نه پنج‌لایه یا همه‌چیز-در-یک-فایل، و
> هر لایه مسئول چه چیزی است.

### چرا وجود دارد؟

اگر همه‌چیز در route handler باشد، تست کردن غیرممکن است، تست دیتابیس برای تست یک تابع ساده لازم می‌شود، و هیچ کد قابل استفاده‌ی مجددی نخواهی داشت.

- **به زبان ساده:** مثل رستورانی که آشپزخانه، سالن و انبار دارد. سالن (Controller) مشتری را راه می‌اندازد، آشپزخانه (Service) غذا می‌پزد، انبار (Repository) مواد اولیه را می‌آورد. آشپز نمی‌رود انبار.

```text
درخواست
   ⬇
Controller    ← فقط: خواندن req، فراخوانی service، ساخت پاسخ
   ⬇
Service       ← منطق کسب‌وکار (قوانین، تصمیم‌ها)؛ دیتابیس نمی‌شناسد
   ⬇
Repository    ← فقط: گفت‌وگو با دیتابیس
```

### پیاده‌سازی

```typescript
// ───────── Repository ─────────
// تنها جایی که از دیتابیس خبر دارد
export interface UserRepository {
  findById(id: string): Promise<User | null>;
  findByEmail(email: string): Promise<User | null>;
  save(user: User): Promise<void>;
}

export class PostgresUserRepository implements UserRepository {
  constructor(private db: Pool) {}

  async findById(id: string): Promise<User | null> {
    const { rows } = await this.db.query('SELECT * FROM users WHERE id = $1', [id]);
    return rows[0] ?? null;
  }
}
```

```typescript
// ───────── Service ─────────
// قوانین کسب‌وکار اینجاست؛ دیتابیس نمی‌شناسد
export class UserService {
  constructor(private repo: UserRepository) {}

  async register(email: string, password: string): Promise<User> {
    // قوانین کسب‌وکار (نه دیتابیس)
    if (await this.repo.findByEmail(email)) {
      throw new ConflictError('این ایمیل قبلاً ثبت شده');
    }

    const user = {
      id: randomUUID(),
      email,
      passwordHash: await hashPassword(password),   // bcrypt/argon2
      createdAt: new Date(),
    };

    await this.repo.save(user);
    return user;   // هش رمز اینجا حذف می‌شود
  }
}
```

```typescript
// ───────── Controller ─────────
// فقط: خواندن ورودی، فراخوانی service، ساخت پاسخ
export class UserController {
  constructor(private service: UserService) {}

  register = async (req: Request, res: Response) => {
    const parsed = RegisterSchema.safeParse(req.body);
    if (!parsed.success) {
      return res.status(422).json({ errors: parsed.error.flatten() });
    }

    const user = await this.service.register(parsed.data.email, parsed.data.password);
    return res.status(201).json({ id: user.id, email: user.email });
  };
}
```

### چرا ترتیب معکوس (Controller → Service → Repository)؟

قانون **وابستگی** (Dependency): لایه‌ی بالا به لایه‌ی پایین وابسته است، نه برعکس. Service هیچ چیزی از Controller نمی‌داند — پس می‌توانی آن را از هر جایی صدا بزنی.

```typescript
// چون Service فقط به Interface وابسته است، تستش با Mock ساده است
const fakeRepo: UserRepository = {
  findById: async () => null,
  findByEmail: async () => null,
  save: async () => {},
};
const service = new UserService(fakeRepo);   // ← بدون دیتابیس!
```

> 🔑 **همین یک دلیل، ارزش کل لایه‌بندی را دارد:** تست واحد (Unit Test) بدون بالا آوردن دیتابیس.

## ۴. اعتبارسنجی ورودی با Zod

> 🧒 **داستان این بخش:** یک صندوق پستی می‌خواهی بگذاری داخل یک خانه.
> نامه‌ها می‌آیند و تو بازشان می‌کنی و **نگاه می‌کنی که داخل چیست**. ولی تا
> وقتی نامه باز نشده، فقط می‌دانی «یک چیزی» است — نمی‌دانی کتاب است یا
> بمب. اعتبارسنجی (validation) دقیقاً همین است: قبل از ورود داده به برنامه،
> بازش کن و مطمئن شو همان چیزی است که فکر می‌کردی.

> مشکل قبلی این بود که هر برنامه‌نویس خودش یک راه نوشت و نیمی وقت‌ها
> یکی را فراموش می‌کرد. **Zod** (نوشته‌ی **Colin McDonnell**) یک راهِ واحد
> می‌دهد: یک بار شکل ورودی را تعریف می‌کنی، هم نوع‌های تایپ‌اسکریپت می‌شود،
> هم همان کد واقعاً ورودی را بررسی می‌کند. اولین انتشارش روی npm در مارس ۲۰۲۰ بود.
>
> **این بخش جواب می‌دهد:** چطور یک شمای ورودی بنویسیم که هم تایپ بدهد،
> هم ورودی واقعی را جدا کند و روشن بگوید کجا اشتباه دارد.

### چرا وجود دارد؟

**هر داده‌ای که از بیرون می‌آید، نامعتبر است.** حتی اگر فرانت‌اند اعتبارسنجی کند — چون هر کسی می‌تواند با `curl` یا Postman درخواست بفرستد.

### مشکل TypeScript — و جواب

```typescript
// ❌ TypeScript فقط کامپایل می‌کند، زمان اجرا هیچ اعتبارسنجی نیست
function createUser(input: { email: string }) { ... }

// ✅ Zod: هم تایپ می‌دهد، هم زمان اجرا اعتبارسنجی می‌کند
const UserSchema = z.object({
  email: z.string().email('ایمیل نامعتبر'),
  age: z.number().int().min(18).max(120),
  role: z.enum(['admin', 'user', 'editor']),
  tags: z.array(z.string()).max(5).optional(),
});
```

🔑 **مزیت اصلی Zod:** یک منبع حقیقت برای تایپ **و** اعتبارسنجی. با تغییر schema، تایپ‌ها خودکار عوض می‌شوند.

### الگوی حرفه‌ای

```typescript
import { ZodError } from 'zod';

export function validate(schema: ZodSchema) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      return res.status(422).json({
        error: 'داده‌های ارسالی نامعتبر',
        details: result.error.issues.map((i) => ({
          field: i.path.join('.'),
          message: i.message,
        })),
      });
    }

    req.body = result.data;   // ← نسخه‌ی پاک‌سازی‌شده و تایپ‌شده
    next();
  };
}

// استفاده:
app.post('/users', validate(UserSchema), userController.register);
```

### اعتبارسنجی چند لایه

| کجا | چه چیزی | چرا |
|-----|---------|-----|
| **سر** (Zod) | شکل و نوع داده | سریع‌ترین جا برای رد کردن داده‌ی بی‌معنا |
| **لایه‌ی سرویس** | قوانین کسب‌وکار | مثل «ایمیل قبلاً ثبت شده؟» |
| **لایه‌ی دیتابیس** | قیدهای نهایی | `UNIQUE`, `FOREIGN KEY`, `CHECK` |

> 🔑 **چرا هر سه؟** چون هیچ لایه‌ای به‌تنهایی کافی نیست. اگر فقط سر اعتبارسنجی کند، یک باگ در فرانت‌اند یا درخواست مستقیم به دیتابیس، همه‌چیز را خراب می‌کند. قید `UNIQUE` در دیتابیس، **آخرین خط دفاع** است — و تنها جایی که واقعاً تضمین می‌کند.

## ۵. استانداردسازی پاسخ و مدیریت متمرکز خطا

> 🧒 **داستان این بخش:** سه برنامه‌نویس در سه گوشه‌ی دنیا برای هر خطا یک شکل
> جواب ساختند: یکی ۴۰۴ داد، یکی ۵۰۰ داد، یکی متن ساده. حالا فرانت‌اند باید
> با هر سه کار کند و هیچ‌جا نمی‌داند چه اتفاقی افتاده. راه‌حل: **یک قالب
> ثابت** که هیچ‌کس حق ندارد از آن خارج شود — و یک نقطه‌ی واحد که همه‌ی
> خطاها از آن عبور می‌کنند.

> این مبحث از یک تصمیم بزرگ‌تر آمد: وقتی یک API می‌سازی، تو فقط کد نمی‌نویسی،
> **قرارداد** می‌نویسی. قرارداد وقتی خوب است که هر دو طرف، حتی اگر هرگز
> همدیگر را ندیده باشند، بتوانند با هم کار کنند.
>
> **این بخش جواب می‌دهد:** شکل استانداردِ یک پاسخ موفق و یک پاسخ خطا چیست، و
> چطور همه‌ی خطاها را در یک جا جمع کنیم.

### چرا ساختار پاسخ یکنواخت مهم است؟

اگر یک endpoint `{ user }` برگرداند و دیگری `{ data, meta }` و سومی آرایه‌ی خالی، فرانت‌اند برای هرکدام کد جدا می‌نویسد. اگر همه یک شکل داشته باشند، یک تابع در فرانت‌اند همه را هندل می‌کند.

```typescript
// پاسخ موفق
{ "success": true, "data": {...}, "meta": { "page": 1, "total": 50 } }

// پاسخ خطا
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [...] } }
```

### سلسله‌مراتب کلاس‌های خطا

```typescript
class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
    public details?: unknown,
  ) {
    super(message);
    this.name = new.target.name;
    Error.captureStackTrace(this, new.target);
  }
}

class NotFoundError extends AppError {
  constructor(resource: string) {
    super(404, 'NOT_FOUND', `${resource} یافت نشد`);
  }
}

class ConflictError extends AppError {
  constructor(message: string) {
    super(409, 'CONFLICT', message);
  }
}

class ValidationError extends AppError {
  constructor(details: unknown) {
    super(422, 'VALIDATION_ERROR', 'داده‌ها نامعتبرند', details);
  }
}
```

### Global Error Handler — قلب تاب‌آوری

```typescript
export function errorHandler(
  err: Error, req: Request, res: Response, next: NextFunction,
) {
  // ① خطاهای خودمان
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      success: false,
      error: { code: err.code, message: err.message, details: err.details },
    });
  }

  // ② خطاهای شناخته‌شده‌ی کتابخانه‌ها
  if (err.name === 'JsonWebTokenError') {
    return res.status(401).json({ error: { code: 'INVALID_TOKEN', message: 'توکن نامعتبر' } });
  }
  if (err.code === '23505') {   // unique violation در PostgreSQL
    return res.status(409).json({ error: { code: 'DUPLICATE', message: 'این مقدار تکراری است' } });
  }

  // ③ خطای ناشناخته — هیچ جزئیاتی به کاربر نده
  logger.error({ err, path: req.originalUrl }, 'خطای مدیریت‌نشده');
  return res.status(500).json({
    success: false,
    error: { code: 'INTERNAL_ERROR', message: 'خطای داخلی سرور' },
  });
}
```

> 🔑 **نکته‌ی امنیتی حیاتی:** در حالت ③، هرگز `err.message` یا `err.stack` را به کلاینت نفرست. پیام خطا ممکن است شامل **نام جدول، نام ستون، یا حتی اطلاعات اتصال دیتابیس** باشد — که نقشه‌ی گنج برای مهاجم است. جزئیات را در لاگ بنویس، نه در پاسخ.

### تبدیل خطای Async به Middleware

در Express 4، یک promise رد شده **به‌طور خودکار** به error handler نمی‌رود:

```typescript
// ❌ Express 4: خطا گم می‌شود و درخواست hang می‌ماند
app.get('/users', async (req, res) => {
  const users = await getUsers();   // اگر reject شود، هرگز به error handler نمی‌رسد
  res.json(users);
});

// ✅ راه‌حل: wrapper
const asyncHandler =
  (fn: Function) => (req: Request, res: Response, next: NextFunction) =>
    Promise.resolve(fn(req, res, next)).catch(next);

// استفاده
app.get('/users', asyncHandler(async (req, res) => {
  const users = await getUsers();
  res.json(users);
}));
```

> 💡 در **Express 5** این مشکل خودش حل شده و نیازی به wrapper نیست.

## ۶. HTTP Semantics کامل

> 🧒 **داستان این بخش:** HTTP شبیه صندوق پستی است که روی هر نامه نوشته چه
> باید بکنی: «بگیر»، «برگردان»، «امضا کن». خواننده‌ها این نوشته‌ها را سال‌ها
> پیش از اینترنت هم می‌دانستند. وقتی کسی می‌نوشت GET برای حذف کردن، مثل
> این بود که روی نامه نوشته «این را بسوزان» — و آن روزی می‌رسید که یکی
> پیامش دو بار می‌رسید و چیزی که باید یک بار پاک می‌شد، دو بار پاک می‌شد.

> کلاس‌های کد وضعیت اولین بار در RFC ۱۹۴۵ (مه ۱۹۹۶) نوشته شد و خودِ روش‌ها
> در RFC ۲۶۱۶ (ژوئن ۱۹۹۹) تعریف شدند. نسخه‌ی تازه‌اش **HTTP Semantics** در
> ۲۰۲۲ (RFC ۹۱۱۰) همه را یک‌جا جمع کرد.
>
> **این بخش جواب می‌دهد:** هر روش HTTP دقیقاً چه معنایی دارد، کد وضعیت
> یعنی چه، و چرا انتخابِ روش درست جلوی یک دسته باگ را می‌گیرد.

### چرا سه راه وجود دارد؟

تا اینجا فقط **یک** راه را دیدیم: کلاینت آدرسی را صدا می‌زند و یک پاسخ می‌گیرد. مشکل وقتی شروع می‌شود که صفحه‌ای می‌خواهی بسازی که داده‌ی زیادی لازم دارد. اگر کلاینت مجبور شود برای هر تکه از داده **یک درخواست جداگانه** بفرستد، صفحه کند می‌شود و به هر کوئری هم یک رفت‌وبرگشت اضافه می‌شود.

سه پاسخ متفاوت به همین مسئله وجود دارد:

- **REST:** برای هر منبع، آدرس و متد خودش را دارد. کلاینت باید دقیقاً بداند چه آدرس‌هایی وجود دارند.
- **GraphQL:** کلاینت **سؤالش را می‌نویسد** («از کاربر ۱۰، نام و ایمیل و نام آخرین ۳ سفارشش را بده») و سرور دقیقاً همان را برمی‌گرداند — یعنی یک درخواست برای چند تکه داده.
- **gRPC:** کلاینت یک **متد مشخص** را صدا می‌زند و پاسخ را می‌گیرد؛ روشی ساخت‌یافته برای وقتی که **دو طرف، هر دو سرور، و هر دو تحت کنترل تو** هستند.

> 🔑 **gRPC چیست؟** (این مخفف را بار اول باز می‌کنیم: **gRPC Remote Procedure Call**، یعنی «فراخوانی از راه دورِ رویه‌ها»، با حروف `g` + `RPC`). پروتکلی است که **گوگل** ساخته و در آن، به‌جای متن JSON، داده‌ها در قالبی فشرده و دودویی به نام **Protocol Buffers** (یا کوتاه `Protobuf`) فرستاده می‌شوند — یعنی ساختار هر پیام اول در یک فایل تعریف می‌شود و بعد برای هر زبانی کدِ خواندن و نوشتنش **خودکار تولید می‌شود**. تقریباً همیشه روی **HTTP/2** اجرا می‌شود که چند درخواست را هم‌زمان روی یک اتصال می‌فرستد. **هزینه‌اش:** مرورگرها اصلاً نمی‌توانند مستقیم gRPC صدا بزنند، پس همیشه پشت یک دروازه (Gateway) می‌ماند که gRPC را به REST/JSON تبدیل کند. نتیجه: gRPC برای **ارتباط داخلی بین سرویس‌ها** عالی است، نه برای کلاینتِ مرورگری.

| ویژگی | REST | GraphQL | gRPC |
|-------|------|---------|------|
| مدل | منبع‌محور (URL) | نوع‌محور (schema) | فراخوانی متد |
| تعداد رفت‌وبرگشت | زیاد — **N+1** یعنی چه؟ یک کوئری برای گرفتن لیست، و بعد **یک کوئری جدا برای هر ردیف**: فهرست ۲۰ کاربر یعنی ۱ + ۲۰ = ۲۱ رفت‌وبرگشت. راه‌حل (کوئری چندتکه یا DataLoader) در فاز ۵ بخش ۱۰ کامل توضیح داده شده. | **یکی** | یکی |
| کش | ✅ ساده (HTTP cache) | ❌ سخت | ❌ |
| منحنی یادگیری | آسان | متوسط | سخت |
| مناسب برای | CRUD، API عمومی | داشبورد با نیاز متغیر | سرویس داخلی (service-to-service) |

- **به زبان ساده:** REST مثل «سفارش غذا از منوی رستوران» است — مشخص می‌کنی چه می‌خواهی. GraphQL مثل «آشپزخانه‌ی باز» است — مواد اولیه را می‌گویی و آشپز هرچه لازم باشد می‌آورد. gRPC مثل «سفارش مستقیم آشپز» — سریع ولی فقط برای مشتری‌های ثابت.

> 🔑 **قاعده‌ی عملی:** REST پیش‌فرض باشد. GraphQL فقط وقتی که کلاینت‌ها نیازهای متفاوت و پیچیده دارند. gRPC فقط برای ارتباط **داخلی** سرویس‌ها.

### مستندسازی: OpenAPI Specs

- **چرا وجود دارد:** وقتی API تو ۲۰ endpoint دارد، هیچ‌کس نمی‌تواند به خاطر بسپارد. مستندات زنده، هم برای فرانت‌اند و هم برای نگهداری لازم است.
- **به زبان فنی:** مشخصات استاندارد و machine-readable از API، که از روی آن می‌توان کلاینت تولید کرد و مستندات ساخت.

```typescript
// نوشتن مستندات از روی همان schema های Zod
import { zodToOpenAPI } from 'zod-to-openapi';
```

> 💡 ابزارهایی مثل `tsoa` یا `nestjs/swagger` این را خودکار می‌کنند: یک schema می‌نویسی، هم اعتبارسنجی داری هم مستندات.

### API Versioning

سه روش متداول:

| روش | نمونه | مزیت | عیب |
|------|-------|-------|------|
| **در URL** | `/api/v2/users` | ساده و صریح | URL زشت می‌شود |
| **در هدر** | `Accept: application/vnd.api.v2+json` | URL تمیز | مبهم، ابزار کم |
| **در هدر** | `X-API-Version: 2` | ساده | غیراستاندارد |

> 🔑 **قاعده‌ی مهم:** نسخه‌ی جدید را **اضافه** کن، نسخه‌ی قدیم را **حذف نکن** — مگر اینکه مشتریانت را از قبل مطلع کرده باشی. حذف ناگهانی، تجربه‌ی کاربری را می‌شکند.

## ۷. HTTP Caching

> 🧒 **داستان این بخش:** یک کتابخانه که هر بار کسی کتابی را پس می‌دهد، دوباره
> همه‌ی فهرست را دستی مرتب می‌کند. کتابخانه یاد می‌گیرد: کارتِ کتاب را روی
> قفسه می‌گذارد (کش محلی)، و روی فهرست می‌نویسد کدام نسخه تازه است
> (هدر ETag). خواننده‌ی بعدی اول هدر را می‌پرسد؛ اگر همان نسخه را داشت،
> کتاب را پس نمی‌دهد.

> این مبحث از یک آمار به‌وجود آمد: در سایت‌های واقعی، **بیشترِ** درخواست‌ها
> تکراری‌اند — همان محتوا را ده‌ها بار می‌خواهند. کش یعنی بیشترین کار را با
> کمترین هزینه انجام بدهی. قواعدش هم در RFC ۹۱۱۱ (کش HTTP) نوشته شده.
>
> **این بخش جواب می‌دهد:** چطور با هدرهای Cache-Control و ETag کش خودم را
> بنویسیم، و چطور دقیق بگوییم کدام پاسخ‌ها را می‌شود کش کرد.

### چرا وجود دارد؟

اگر هر بار که کاربر صفحه را باز می‌کند، سرور دیتابیس را صدا بزند، هم پرهزینه است هم کند. بخش بزرگی از داده‌ها (لاگ‌ها، محصولات، پروفایل‌ها) به‌ندرت تغییر می‌کنند.

### دو سازوکار اصلی

#### ETag — «نسخه‌ی محتوا»
- **چرا:** یک هش از محتوا. کلاینت می‌گوید «آخرین نسخه‌ای که دارم این است»؛ سرور می‌گوید «همان است» یا «نه، این جدید است».
- **ساده:** مثل اینکه به فروشنده بگویی «همون کتابی که پارسال خریدم رو دارم؟» و او بگوید «نه، نسخه‌ی جدید چاپ شده».

```http
# درخواست
If-None-Match: "abc123"

# پاسخ اگر تغییری نکرده
304 Not Modified
ETag: "abc123"
```

> 💡 **نکته‌ی مهم:** پاسخ `304` **بدنه ندارد**. اگر بدنه بفرستی، با کد 304 غلط است و کلاینت آن را نمی‌خواند.

#### Cache-Control — «چه مدت نگه دار؟»
- **ساده:** مثل تاریخ انقضای برچسب روی قفسه.

```http
Cache-Control: max-age=3600          # تا ۱ ساعت تازه است
Cache-Control: no-cache              # همیشه قبل از استفاده بپرس (ولی کش کن)
Cache-Control: no-store              # اصلاً کش نکن (اطلاعات حساس)
Cache-Control: private               # فقط کش مرورگر، نه CDN
Cache-Control: public                # همه، از جمله CDN
```

### الگوی Cache-Aside — «اول بپرس، اگر نبود برو دوباره بخوان»

دو هدر بالا (`ETag` و `Cache-Control`) کار **سمت کلاینت** را می‌کنند: مرورگر خودش پاسخ را نگه می‌دارد. اما `Cache-Aside` کار **سمت سرور** است: داده در یک کش (مثل Redis) نگه داشته می‌شود و برنامه خودش تصمیم می‌گیرد از کش بخواند یا از دیتابیس.

الگوی استانداردش سه قدم دارد — **کش‌آسید** یعنی «کش کن، مگر اینکه نبود»:

1. اول کش را نگاه کن؛ اگر داده بود، برگردان.
2. اگر نبود، برو دیتابیس.
3. جواب را در کش بگذار (با زمان انقضا).

> 💡 این الگو در **فاز ۶ بخش ۲** کامل باز می‌شود: کجا کش کنیم، چه زمانی باطلش کنیم، و چه مشکلاتی (کهنگی داده یا cache stampede) ممکن است به وجود بیاید.

```typescript
async function getUser(id: string): Promise<User> {
  // ① اول کش را نگاه کن
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  // ② نبود → دیتابیس
  const user = await db.query('SELECT * FROM users WHERE id = $1', [id]);
  if (!user) return null;

  // ③ در کش ذخیره کن (با زمان انقضا)
  await redis.setex(`user:${id}`, 300, JSON.stringify(user));   // ۵ دقیقه
  return user;
}
```

🔑 **چرا این الگو؟** سه دلیل:
1. اگر کش خراب شود، سیستم همچنان کار می‌کند (فقط کندتر)
2. حذف کش به‌مراتب آسان‌تر از نوشتن است
3. برای داده‌هایی که کم تغییر می‌کنند، عالی است

## ۸. CORS، CSP و امنیت محتوایی

> 🧒 **داستان این بخش:** مرورگر مثل یک نگهبان سخت‌گیر است. می‌داند درخواست
> از `example.test` آمده و می‌پرسد: اجازه دارد نتیجه‌اش را به
> `evil.test` بدهد؟ این نگهبان اسمش **CORS** است — یعنی «کنترل دسترسی
> بین سایت‌ها». خیلی وقت‌ها پیام قرمزِ «ارتباط متقابل مسدود شد» را با
> CORS اشتباه می‌گیرند، در حالی که مشکل جای دیگری است.

> قاعده‌ی قدیمی **خاستگاه یکسان** با Netscape Navigator 2.0 در ۱۹۹۵ و
> جاوااسکریپت آمد؛ خواندنِ داده‌ی یک سایت توسط سایت دیگر همان لحظه غلط
> بود. این مبحث وجود دارد چون همان قاعده در عمل خطرناک شد — هر صفحه‌ای
> می‌توانست هر داده‌ای را بخواند. همکاران **CORS** این قاعده را استاندارد
> کردند، و **CSP** (سیاست امنیتی محتوا) را **رابرت هنسن** در ۲۰۰۴ پیشنهاد داد؛
> موزیلا هم در فایرفاکس ۴ پیاده‌اش کرد.
>
> **این بخش جواب می‌دهد:** پیام CORS از کجا می‌آید و چطور درست بازش کنیم،
> و CSP چطور جلوی اجرای اسکریپتی که نباید اجرا شود را می‌گیرد.

### CORS — «از کجا اجازه داری درخواست بدهی؟»

- **چرا وجود دارد:** مرورگر به‌دلایل امنیتی، از یک دامنه اجازه‌ی درخواست به دامنه‌ی دیگر را نمی‌دهد. CORS مکانیزمی است که سرور می‌گوید «بله، من اجازه می‌دهم».
- **به زبان ساده:** مثل نگهبان یک ساختمان که می‌گوید «افراد بیرونی فقط از لابی وارد شوند، نه طبقات بالا».

```typescript
// ❌ غلط: origin پویا یا باز، امنیت را از بین می‌برد
app.use(cors({ origin: '*' }));

// ✅ درست: فهرست سفید مشخص
app.use(cors({
  origin: ['https://app.example.com', 'https://admin.example.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
}));
```

> 🔑 **نکته‌ی امنیتی:** `origin: '*'` به‌همراه `credentials: true` **همیشه خطا** می‌دهد، چون مرورگرها اجازه نمی‌دهند ست کوکی با origin باز ارسال شود. این محدودیت عمدی است — وگرنه هر سایتی می‌توانست با کوکی‌های تو درخواست بفرستد.

### CSP — «چه چیزی اجازه دارد در صفحه اجرا شود؟»

- **چرا وجود دارد:** XSS یعنی مهاجم کد خودش را در صفحه‌ی تو تزریق کند. CSP مشخص می‌کند از کجا مجاز است اسکریپت و استایل بارگذاری شود.

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
```

> 💡 `'self'` یعنی فقط از همین دامنه. `unsafe-inline` یعنی اجازه‌ی اسکریپت داخل HTML — که عملاً XSS را ممکن می‌کند.

## ۹. Real-Time Data

> 🧒 **داستان این بخش:** تو در یک چت‌روم نشسته‌ای و طرف مقابل حرف می‌زند.
> اگر تو هر سه ثانیه یک بار بپرسی «چیز جدیدی هست؟»، کار می‌کند — ولی
> بی‌خودی برق می‌رود و دیر جواب می‌گیری. راه درست، یک لوله‌ی باز است که خودش
> هر چیزی که رسید را به تو می‌گوید. این لوله دو جور دارد:

> **WebSocket** (که در فاز ۱ دیدیم) یک اتصالِ همیشه‌باز می‌سازد و هر دو طرف
> هر وقت خواستند حرف می‌زنند. این خیلی کم‌مصرف است. حالتِ ساده‌ترش
> **Server-Sent Events** است: سرور فقط یک‌طرفه می‌فرستد، ولی با HTTP معمولی
> کار می‌کند.

> این مبحث از خستگی آمد: وقتی پیام‌ها زیاد شدند، کشیدن داده با پرس‌وجوی
> تکراری دیگر جواب نمی‌داد.
>
> **این بخش جواب می‌دهد:** چطور داده‌ی زنده به مرورگر برسد و چه وقت
> WebSocket، چه وقت SSE، و چه وقت همان پرس‌وجوی ساده کافی است.

### چهار روش — انتخاب درست

پیش از جدول، تعریف هر چهار روش (دو تای اول یعنی **Polling** و **Webhook**، در هیچ بخش دیگری از این فاز توضیح داده نشده‌اند):

- **Polling (نظرسنجی دوره‌ای):** کلاینت خودش، روی یک تایمر، مدام می‌پرسد «خبر جدیدی هست؟» و سرور هم هر بار پاسخ می‌دهد — حتی اگر هیچ خبری نباشد. برای به‌روزرسانی کم‌تغییر و ساده مناسب است (مثلاً وضعیت یک سفارش که هر نیم‌ساعت عوض می‌شود)، ولی ایرادش این است که **هم اتلافی است و هم با تأخیر**: اگر فاصله‌ی تایمر ۳۰ ثانیه باشد، کاربر تا ۳۰ ثانیه بعد از رخ دادن رویداد، آن را نمی‌بیند.
- **Webhook (قلاب وب):** برعکسِ Polling. تو یک آدرس (URL) به سرور می‌دهی و سرور، **درست در لحظه‌ای که رویداد رخ می‌دهد**، خودش یک درخواست HTTP به آن آدرس می‌فرستد. پس کلاینت هیچ‌وقت سؤال نمی‌کند. مناسب برای پرداخت و اعلان‌های سمت سرور (مثلاً وقتی پرداخت درگاه تأیید شد). **دو نکته‌ی عملی:** آدرس مقصد باید عمومی و قابل دسترس باشد، و چون فرستنده ممکن است چندبار تلاش کند، دریافت‌کننده باید **تکرار دریافت** را بی‌خطر مدیریت کند (مثلاً با یک شناسه‌ی یکتا).
- **SSE (Server-Sent Events — رویدادهای فرستاده‌شده از سرور):** یک **جریان یک‌طرفه‌ی HTTP** است: سرور اتصال را باز نگه می‌دارد و هر وقت داده‌ی جدیدی داشت، خودش می‌نویسد. فرقش با WebSocket این است که WebSocket **دوطرفه** است (کلاینت هم می‌تواند بفرستد)، ولی SSE فقط **سرور → کلاینت** است. در عوض پیاده‌سازی‌اش به‌مراتب ساده‌تر است و روی همان HTTP معمولی کار می‌کند.
- **WebSocket:** یک اتصال دائمی **دوطرفه**؛ هر دو طرف هر وقت خواستند می‌توانند پیام بفرستند. قوی‌ترین گزینه برای گفت‌وگوی زنده، بازی و همکاری بلادرنگ، ولی مدیریت اتصال و احراز هویت روی آن سخت‌تر است.

| روش | ارتباط | پیچیدگی سرور | مناسب برای |
|------|--------|---------------|------------|
| **Polling** | قطع و وصل | کم | داده کم‌تغییر |
| **SSE** | یک‌طرفه (سرور → کلاینت) | متوسط | نوتیفیکی، لایو-آپدیت |
| **WebSocket** | دوطرفه | **زیاد** | چت، بازی، همکاری |
| **Webhook** | سرور به سرور | کم | پرداخت، اعلان |

### SSE (Server-Sent Events) — ساده‌تر از WebSocket

همان تعریف بالا، از زاویه‌ی کد: سرور هدر `text/event-stream` را می‌گذارد و اتصال را **باز نگه می‌دارد**؛ هر پیام جدید را به شکل یک خط `data: ...` می‌نویسد و در پایان یک خط خالی می‌گذارد تا مرورگر پیام را پردازش کند. هیچ کتابخانه‌ی اضافه‌ای نمی‌خواهد — فقط یک `response` باز که هرازمان چیزی در آن بنویسی.

```typescript
app.get('/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  });

  const interval = setInterval(() => {
    res.write(`data: ${JSON.stringify({ time: Date.now() })}\n\n`);
  }, 1000);

  // ⚠️ حیاتی: وقتی کلاینت قطع شد، تایمر را پاک کن
  req.on('close', () => clearInterval(interval));
});
```

> 🔑 **نکته‌ی حیاتی:** اگر `clearInterval` نکنی، با هر اتصال ناکامل، یک تایمر بی‌پایان باقی می‌ماند. سرور به‌تدریج از کار می‌افتد. این یکی از رایج‌ترین نشت‌های منابع در اپلیکیشن‌های Real-time است.

- لایه‌ی Middleware، ترتیب اجرا، و چهار الگوی رایج

- لایه‌بندی سه‌گانه: Controller / Service / Repository و قانون وابستگی
- اعتبارسنجی چند لایه با Zod

- Global Error Handler و امنیت در افشای خطا
- HTTP semantics: REST در برابر GraphQL در برابر gRPC
- HTTP Caching: ETag، Cache-Control، الگوی Cache-Aside
- CORS، CSP، و دام‌های امنیتی‌شان
- API Versioning و مستندسازی OpenAPI
- Real-time: Polling، SSE، WebSocket

## 🔨 چه می‌سازی؟

- **API کامل با Express:** شامل Controller/Service/Repository، اعتبارسنجی Zod، Global Error Handler، و Rate Limiting با Token Bucket (مبتنی بر Redis).
- **Middleware سفارشی:** logger ساختاریافته، requireAuth، metrics، و circuitBreaker.
- **سیستم کش:** پیاده‌سازی Cache-Aside با Redis، همراه با تست hit/miss.
- **Endpoint استریمینگ:** سرور SSE بنویس که آمار زنده را به کلاینت می‌فرستد (و با قطع اتصال تمیز جمع شود).
- **مستندات OpenAPI:** تولید خودکار مستندات از schema های Zod.
