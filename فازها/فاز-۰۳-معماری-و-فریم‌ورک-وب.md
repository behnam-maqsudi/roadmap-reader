# فاز ۳ — معماری نرم‌افزار و فریم‌ورک‌های وب

> 🧒 **داستان:** تا اوایل سال ۲۰۱۰، ساخت یک مسیر ساده مثل `/api/users` در برنامه‌های تحت وب معمولاً با کپی‌کردن ده‌ها خط کد تکراری از پروژه‌ای به پروژهٔ دیگر انجام می‌شد. یک نفر برای خواندن اطلاعات کاربر از دیتابیس کدی می‌نوشت، نفر دوم همان کد را با یک تغییر جزئی برای ثبت سفارش تکرار می‌کرد، و نفر سوم همان ساختار را با یک باگ پنهان پیاده می‌کرد. برنامه کار می‌کرد، اما هیچ‌کس دقیقاً نمی‌دانست این کد کِی اجرا می‌شود، چه مراحلی پیش از آن طی شده و چطور می‌توان کارهای مشترک مثل احراز هویت، اعتبارسنجی یا ثبت لاگ را مدیریت کرد.
>
> در اواخر دههٔ ۲۰۰۰، فریم‌ورک‌های مینیمالیستی در زبان‌های دیگر (مانند Sinatra در روبی) نشان دادند که یک وب‌سرور نیازی به ابزارهای سنگین و دست‌وپاگیر ندارد. در نوامبر ۲۰۱۰، برنامه‌نویسی به نام **TJ Holowaychuk** با الهام از این تفکر مینیمال، فریم‌ورک **Express** را برای اکوسیستم نوپای Node.js خلق کرد. ایدهٔ درخشان او بسیار شفاف بود: هر وظیفهٔ مشخص (بررسی هدرها، ثبت لاگ، وارسی نشست کاربر، رمزگشایی بدنه) باید در یک قطعهٔ مستقل و مجزا اجرا شود — یک **لایه**. هر لایه می‌تواند در صورت نیاز جلوی ادامهٔ مسیر را بگیرد یا داده‌ها را به لایهٔ بعد بسپارد. این قطعات مستقل همان **میان‌افزارها (Middleware)** هستند.
>
> در این فاز، از همان نقطه آغاز می‌کنیم: یاد می‌گیریم چطور از کدهای درهم‌تنیده عبور کنیم و برنامه‌ای با معماری لایه‌ای، خوانا و مقیاس‌پذیر بسازیم که هر خط آن دلیل و جایگاه مشخصی داشته باشد.

## مقدمه: چرا حالا فریم‌ورک؟

در فاز ۲ یک وب‌سرور خام با ماژول درونی `http` ساختیم و جریان داده‌ها را در لایهٔ سوکت بررسی کردیم. اکنون زمان آن است که ابزارهای استاندارد دنیای وب را به خدمت بگیریم — نه به عنوان «جعبه‌ای جادویی»، بلکه به عنوان **لایه‌ای مهندسی‌شده که از کارکرد دقیق و هزینه‌های اجرایی آن کاملاً آگاهیم**.

دو واژه در سرتاسر این فاز مکرراً تکرار می‌شوند که فهم دقیق آن‌ها ضروری است:

- **Middleware (میان‌افزار):** تابعی که در مسیر پردازش یک درخواست HTTP، **پیش از رسیدن به کنترلر اصلی یا پس از آن**، اجرا می‌شود؛ کارهایی مثل احراز هویت، کنترل نرخ درخواست‌ها یا ثبت لاگ در این لایه‌ها قرار می‌گیرند.
- **Route (مسیر):** نگاشت میان یک ترکیب مشخص از آدرس URL و متد HTTP (مانند `GET /api/users`) و تابعی که وظیفهٔ پاسخ‌گویی به آن درخواست را بر عهده دارد.

> 💡 تفاوت یک مهندس ارشد با یک توسعه‌دهندهٔ تازه‌کار در همین درک عمیق است: او دقیقاً می‌داند میان‌افزارها با چه ترتیبی فراخوانی می‌شوند، چرخهٔ حیات درخواست چگونه مدیریت می‌شود و چرا ساختار لایه‌ای تست‌پذیری سیستم را تضمین می‌کند.

## ۱. لایه‌ی Middleware — قلب فریم‌ورک

> 🧒 **داستان این بخش:** یک رستوران منظم را در نظر بگیر که پیش از رسیدن سفارش به آشپزخانه، سه نفر روی آن کار می‌کنند: دربان ورودی را بررسی می‌کند، مسئول پذیرش سفارش را ثبت می‌کند و حسابدار فاکتور را می‌سنجد. هر یک وظیفهٔ مشخص خود را انجام می‌دهد و نیازی ندارد از جزییات فنی کار دیگران باخبر باشد. در فریم‌ورک‌های وب نیز هر کار جانبی دقیقاً به همین شکل انجام می‌شود: هر میان‌افزار درخواست ورودی را دریافت می‌کند، بررسی‌های خود را انجام می‌دهد و در صورت تأیید، آن را به نفر بعدی تحویل می‌دهد.
>
> در گذشته برنامه‌نویسان مجبور بودند تمام این بررسی‌ها را به صورت دستی در ابتدای هر تابع کپی کنند. اگر در یکی از مسیرها بررسی امنیتی فراموش می‌شد، کل سیستم آسیب‌پذیر می‌گردید. الگوی زنجیرهٔ میان‌افزارها این معضل را برای همیشه حل کرد.
>
> **این بخش جواب می‌دهد:** لایهٔ میان‌افزار دقیقاً چیست، زنجیرهٔ پردازش با چه ترتیبی کار می‌کند و چگونه تابع `next()` جریان اجرای برنامه را هدایت می‌کند.

### چرا وجود دارد؟

یک وب‌سرور در دنیای واقعی با ده‌ها وظیفهٔ مشترک و تکراری روبروست: ثبت لاگ، احراز هویت، اعتبارسنجی توکن، بررسی هدرها، فشرده‌سازی پاسخ و مدیریت خط مشی CORS. اگر این منطق‌ها داخل تک‌تک مسیرها نوشته شوند، کد ناخوانا، غیرقابل نگهداری و پر از باگ‌های امنیتی خواهد شد.

- **به زبان ساده:** میان‌افزارها مانند گیت‌های بازرسی در ورودی یک فرودگاه هستند؛ مسافر گام‌به‌گام از گیت بازرسی بلیت، گیت امنیتی و گیت خروجی عبور می‌کند تا به هواپیما برسد. اگر در هر گیت مشکلی پیش بیاید، همان‌جا متوقف می‌شود.
- **به زبان فنی:** تابعی با امضای استانداردی مانند `(req, res, next)` که به شیء درخواست (`req`) و پاسخ (`res`) دسترسی دارد و با صدا زدن `next()`، اجرای برنامه را به میان‌افزار بعدی در زنجیره واگذار می‌کند.

### ترتیب اجرا — نکته‌ای که همه را غافلگیر می‌کند

```typescript
app.use(express.json());                    // ① پارسر بدنه JSON
app.use(authMiddleware);                    // ② احراز هویت سراسری
app.get('/admin', adminOnly, handler);      // ③ مسیر با میان‌افزار اختصاصی
app.use(errorHandler);                      // ④ مدیریت متمرکز خطاها
```

**جریان فراخوانی:**
```text
درخواست ورودی
   ⬇
① express.json()      ← تبدیل بافر ورودی به شیء جاوااسکریپت
   ⬇ next()
② authMiddleware      ← بررسی نشست / توکن کاربر
   ⬇ next()
③ adminOnly           ← بررسی سطح دسترسی مدیر
   ⬇ next()
   handler            ← منطق اصلی مسیر و ارسال پاسخ (res.json)
   ⬇ (فقط در صورت بروز استثنا)
④ errorHandler        ← مدیریت متمرکز خطا با امضای ۴ آرگومانی
```

🔑 **قواعد حیاتی میان‌افزارها:**

| قاعده | چرا اهمیت دارد؟ |
|-------|-----------------|
| میان‌افزارها بر اساس **ترتیب تعریف (`app.use`)** اجرا می‌شوند | میان‌افزاری که بعد از یک مسیر نوشته شود، هرگز برای آن مسیر اجرا نخواهد شد. |
| صدا نزدن `next()` یا ارسال نکردن پاسخ، درخواست را معلق می‌کند | اگر نه `next()` صدا زده شود و نه پاسخی ارسال گردد، کلاینت در حالت انتظار نامحدود (Hang) می‌ماند. |
| هرگز نباید بعد از بستن پاسخ با `res.send()`، تابع `next()` را صدا زد | این کار خطای معروف `ERR_HTTP_HEADERS_SENT` را پرتاب می‌کند. |
| میان‌افزار خطایاب Express **باید دقیقاً ۴ آرگومان** داشته باشد | `(err, req, res, next)`. فریم‌ورک Express نوع تابع را بر اساس `fn.length` تشخیص می‌دهد! |

### چهار الگوی رایج Middleware

#### ۱. الگوی ثبت لاگ ساختاریافته (Structured Logging)

**هدف:** اندازه‌گیری دقیق زمان پردازش و ثبت مشخصات درخواست در قالب ساختاریافته (JSON) پس از اتمام پاسخ:

```typescript
import { Request, Response, NextFunction } from 'express';

export function requestLogger(req: Request, res: Response, next: NextFunction) {
  const start = process.hrtime.bigint();

  // ثبت لاگ دقیقاً زمانی که ارسال بایت‌ها تمام شد
  res.on('finish', () => {
    const elapsedNs = process.hrtime.bigint() - start;
    const durationMs = (Number(elapsedNs) / 1e6).toFixed(2);

    console.log(JSON.stringify({
      level: res.statusCode >= 400 ? 'warn' : 'info',
      method: req.method,
      path: req.originalUrl,
      status: res.statusCode,
      durationMs,
      ip: req.ip,
      userAgent: req.get('user-agent'),
    }));
  });

  next();
}
```

#### ۲. الگوی نگهبان دسترسی (Guard / Authorization)

**هدف:** جلوگیری از دسترسی کاربران غیرمجاز پیش از صرف منابع سرور برای اجرای کنترلر اصلی:

```typescript
export function requireAuth(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({
      success: false,
      error: { code: 'UNAUTHORIZED', message: 'توکن احراز هویت یافت نشد' }
    });
  }

  const token = authHeader.slice(7);
  try {
    const payload = verifyJwt(token);
    (req as any).user = payload;
    next(); // عبور مجاز است
  } catch {
    return res.status(401).json({
      success: false,
      error: { code: 'INVALID_TOKEN', message: 'توکن نامعتبر یا منقضی شده است' }
    });
  }
}
```

#### ۳. الگوی سنجه‌های عملکردی (Metrics)

**هدف:** جمع‌آوری شاخص‌های کمی (مانند تعداد درخواست‌ها و توزیع زمان پاسخ) جهت مانیتورینگ با سیستم‌هایی نظیر Prometheus:

```typescript
export function metricsCollector(histogram: any) {
  return (req: Request, res: Response, next: NextFunction) => {
    const start = process.hrtime.bigint();

    res.on('finish', () => {
      const durationSec = Number(process.hrtime.bigint() - start) / 1e9;
      histogram.observe({
        method: req.method,
        route: req.route?.path || req.path,
        status: res.statusCode
      }, durationSec);
    });

    next();
  };
}
```

#### ۴. الگوی کلید قطع جریان (Circuit Breaker)

**هدف:** محافظت از سیستم در برابر خرابی سرویس‌های پایین‌دست؛ اگر سرویسی مداوم خطا دهد، به‌جای معطل کردن منابع، مسیر موقتاً قطع می‌شود:

```typescript
export function circuitBreakerMiddleware(threshold = 5, resetTimeoutMs = 30_000) {
  let failures = 0;
  let state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  let nextAttemptTime = 0;

  return (req: Request, res: Response, next: NextFunction) => {
    const now = Date.now();

    if (state === 'OPEN') {
      if (now > nextAttemptTime) {
        state = 'HALF_OPEN'; // ارسال یک درخواست آزمایشی
      } else {
        return res.status(503).json({
          success: false,
          error: { code: 'SERVICE_UNAVAILABLE', message: 'سرویس موقتاً به دلیل خطای زیرساخت در دسترس نیست' }
        });
      }
    }

    res.on('finish', () => {
      if (res.statusCode >= 500) {
        failures++;
        if (failures >= threshold) {
          state = 'OPEN';
          nextAttemptTime = Date.now() + resetTimeoutMs;
        }
      } else if (state === 'HALF_OPEN') {
        state = 'CLOSED';
        failures = 0;
      }
    });

    next();
  };
}
```

## ۲. Rate Limiting در عمل

> 🧒 **داستان این بخش:** فرض کن فردی با یک ابزار خودکار تلاش می‌کند رمز عبور کاربران را حدس بزند؛ او در هر ثانیه صدها بار به درگاه لاگین می‌کوبد. اگر سرور بدون محدودیت به این درخواست‌ها پاسخ دهد، علاوه بر خطر نفوذ، سایر کاربران واقعی نیز به دلیل اشغال کامل منابع پردازنده و پایگاه داده پشت در معطل می‌مانند. چارهٔ کار مکانیزمی به نام **Rate Limiting** است: تعیین سقفی عادلانه که هیچ کاربری نتواند بیش از حد مجاز در یک بازهٔ زمانی معین منبع مصرف کند.
>
> اما سنجش این موضوع در سیستم‌های مقیاس‌پذیر ظرافت‌های مهمی دارد؛ چرا که پشت شبکه‌های توزیع محتوا (CDN) ممکن است هزاران کاربر با یک آدرس IP مشترک شناخته شوند.
>
> **این بخش جواب می‌دهد:** چگونه ترافیک نامتعارف را مهار کنیم، چه الگوریتم‌هایی برای سهمیه‌بندی وجود دارد و چطور با پایگاه دادهٔ Redis محدودیت را در چندین سرور همگام سازیم.

### چرا وجود دارد؟

کنترل نرخ درخواست برای دفع سه تهدید کاملاً متفاوت الزامی است؛ تشخیص اشتباه هر یک منجر به اعمال راه‌حل نامناسب می‌شود:

| نوع تهدید | ماهیت رفتار | استراتژی مهار |
|-----------|-------------|---------------|
| **حملات Brute-force و اسپم** | یک حساب کاربری صدها درخواست مشکوک ارسال می‌کند | محدودیت بر پایهٔ **شناسهٔ کاربر (`User-ID`)** |
| **حملات انکار سرویس (DDoS)** | انبوهی از ماشین‌ها یا اسکریپت‌ها یک آدرس را بمباران می‌کنند | محدودیت بر پایهٔ **آدرس شبکه (`IP Address`)** |
| **مصرف نامتعارف منابع (Resource Exhaustion)** | فراخوانی مکرر گزارش‌های سنگین یا پرس‌وجوهای پیچیده | محدودیت بر پایهٔ **مسیر و ضریب هزینه (`Cost-based Limit`)** |

### مقایسه الگوریتم‌های محدودیت نرخ

#### ۱. پنجرهٔ ثابت (Fixed Window Counter)
- **مفهوم:** شمارش تعداد درخواست‌ها در بازه‌های زمانی ثابت (مثلاً ۱ دقیقه).
- **ضعف بزرگ:** آسیب‌پذیری در مرز بازه‌ها؛ اگر کاربر در آخرین ثانیهٔ یک بازه ۱۰۰ درخواست و در اولین ثانیهٔ بازهٔ بعد ۱۰۰ درخواست دیگر بفرستد، در فاصلهٔ ۲ ثانیه ۲۰۰ درخواست پردازش می‌شود، در حالی که سقف اسمی سیستم ۱۰۰ بود!

#### ۲. پنجرهٔ لغزان (Sliding Window Log / Counter)
- **مفهوم:** محاسبهٔ تعداد درخواست‌ها بر اساس بردار زمانی واقعی در ۶۰ ثانیهٔ گذشته.
- **مزیت:** حذف خطای مرزی و دقت بالا؛ اما نیازمند ثبت زمان دقیق درخواست‌ها در حافظه است.

#### ۳. سطل توکن (Token Bucket) — استاندارد صنعت
- **مفهوم:** سطلی با ظرفیت مشخص ($C$) وجود دارد که با نرخی ثابت (مثلاً ۲ توکن در ثانیه) پر می‌شود. هر درخواست یک توکن برمی‌دارد. اگر سطل خالی باشد، درخواست رد می‌شود.
- **مزیت:** اجازهٔ جهش طبیعی (Burst) را به کاربر می‌دهد؛ اگر کاربری چند دقیقه غیرفعال بوده باشد، می‌تواند چند درخواست هم‌زمان ارسال کند، اما میانگین ترافیک او هرگز از نرخ مجاز فراتر نمی‌رود.

```typescript
export function memoryTokenBucket(capacity = 10, refillRatePerSec = 2) {
  let tokens = capacity;
  let lastRefill = Date.now();

  return (req: Request, res: Response, next: NextFunction) => {
    const now = Date.now();
    const elapsedSec = (now - lastRefill) / 1000;

    // شارژ مجدد سطل بر اساس زمان سپری‌شده
    tokens = Math.min(capacity, tokens + elapsedSec * refillRatePerSec);
    lastRefill = now;

    if (tokens < 1) {
      const waitTimeSec = Math.ceil((1 - tokens) / refillRatePerSec);
      res.setHeader('Retry-After', waitTimeSec);
      return res.status(429).json({
        success: false,
        error: { code: 'RATE_LIMIT_EXCEEDED', message: 'تعداد درخواست‌ها بیش از سقف مجاز است' }
      });
    }

    tokens -= 1;
    res.setHeader('RateLimit-Remaining', Math.floor(tokens));
    next();
  };
}
```

> ⚠️ **در محیط عملیاتی (Production):** شمارندهٔ نرخ هرگز نباید در حافظهٔ محلی فرآیند Node.js ذخیره شود. اگر برنامه پشت یک لودبالانسر روی ۴ سرور (یا چند فرآیند با کلاستر) اجرا شود، حافظه میان آن‌ها مشترک نیست و کاربر می‌تواند تا **۴ برابر سقف مجاز** ترافیک ارسال کند! ذخیرهٔ وضعیت در **Redis** با دستورهای اتمیک (`INCR` و `EXPIRE` یا اسکریپت‌های Lua) این محدودیت را سراسری و غیرقابل دور زدن می‌کند.

### هدرهای استاندارد Rate Limiting (IETF RFC 6585)

```http

RateLimit-Remaining: 42
RateLimit-Reset: 18
Retry-After: 5
```

## ۳. لایه‌بندی پروژه — سه لایه، نه یک عالمه

> 🧒 **داستان این بخش:** یک رستوران بزرگ را تصور کن که سرآشپز، صندوق‌دار و مسئول خرید انبار همگی در یک فضای کوچک کار کنند و مدام در امور یکدیگر دخالت کنند. نتیجه چیزی جز سردرگمی، کندی و اشتباهات پیاپی نخواهد بود. راهکار منطقی، تفکیک شفاف وظایف در سالن‌های جداگانه است: صندوق‌دار با مشتریان تعامل دارد، سرآشپز فرمول پخت غذا را پیاده می‌کند و انباردار مسئول تأمین مواد اولیه است.
>
> در پروژه‌های نرم‌افزاری نیز اگر تمام منطق احراز هویت، قوانین مالی و دستورهای SQL داخل یک فایل یا کنترلر نوشته شوند، تست کردن برنامه ناممکن و تغییر آن فاجعه‌بار خواهد بود. تفکیک معماری به سه لایهٔ استاندارد، به ما اجازه می‌دهد منطق اصلی کسب‌وکار را بدون نیاز به پایگاه داده و در کسری از ثانیه آزمایش کنیم.
>
> **این بخش جواب می‌دهد:** چرا معماری سه‌لایه (Controller / Service / Repository) انتخاب اول صنعت است و هر لایه چه مسئولیت‌هایی دارد.

### چرا وجود دارد؟

اگر تمام کدهای احراز هویت، اعتبارسنجی ورودی، قوانین محاسباتی و پرس‌وجوهای SQL در یک فایل یا داخل کنترلر نوشته شوند، تست کردن برنامه ناممکن، خوانایی آن صفر و توسعهٔ تیمی آن پر از تداخل خواهد شد. تفکیک به سه لایه تضمین می‌کند هر بخش فقط یک مسئولیت شفاف داشته باشد.

### ساختار معماری لایه‌ای

```text
  درخواست کلاینت (HTTP Request)
          ⬇
┌───────────────────────────────────────────┐
│              Controller                   │  ← مدیریت پروتکل HTTP:
│ (دریافت Request، اعتبارسنجی ورودی، بازگرداندن پاسخ)│    خواندن هدر، کوئری، وضعیت ۲xx/۴xx
└───────────────────────────────────────────┘
          ⬇ فراخوانی توابع کسب‌وکار
┌───────────────────────────────────────────┐
│               Service                     │  ← منطق محض کسب‌وکار (Business Rules):
│ (قوانین سیستم، محاسبات، تصمیم‌گیری‌ها)       │    کاملاً بی‌خبر از HTTP و نوع پایگاه داده
└───────────────────────────────────────────┘
          ⬇ تعامل با ذخیره‌ساز
┌───────────────────────────────────────────┐
│              Repository                   │  ← دسترسی به داده (Data Access):
│ (کوئری‌های SQL، کش، کار با ORM یا درایور) │    اجرای پرس‌وجوها روی دیتابیس
└───────────────────────────────────────────┘
```

### پیاده‌سازی گام‌به‌گام

#### ۱. لایهٔ مخزن داده (Repository)
تنها لایه‌ای که به درایور پایگاه داده و کوئری‌ها دسترسی مستقیم دارد:

```typescript
export interface User {
  id: string;
  email: string;
  passwordHash: string;
  createdAt: Date;
}

export interface UserRepository {
  findById(id: string): Promise<User | null>;
  findByEmail(email: string): Promise<User | null>;
  create(user: Omit<User, 'createdAt'>): Promise<User>;
}

export class PostgresUserRepository implements UserRepository {
  constructor(private readonly db: any) {}

  async findById(id: string): Promise<User | null> {
    const res = await this.db.query('SELECT * FROM users WHERE id = $1', [id]);
    return res.rows[0] ?? null;
  }

  async findByEmail(email: string): Promise<User | null> {
    const res = await this.db.query('SELECT * FROM users WHERE email = $1', [email]);
    return res.rows[0] ?? null;
  }

  async create(user: Omit<User, 'createdAt'>): Promise<User> {
    const res = await this.db.query(
      'INSERT INTO users (id, email, password_hash) VALUES ($1, $2, $3) RETURNING *',
      [user.id, user.email, user.passwordHash]
    );
    return res.rows[0];
  }
}
```

#### ۲. لایهٔ سرویس کسب‌وکار (Service)
این لایه قلب تپندهٔ برنامه است؛ هیچ وابستگی به اشیای Express (`req` یا `res`) ندارد:

```typescript
import { randomUUID } from 'node:crypto';
import { ConflictError } from './errors';

export class UserService {
  constructor(private readonly userRepo: UserRepository) {}

  async register(email: string, plainPassword: string): Promise<Omit<User, 'passwordHash'>> {
    // قانون کسب‌وکار: ایمیل تکراری مجاز نیست
    const existing = await this.userRepo.findByEmail(email);
    if (existing) {
      throw new ConflictError('کاربری با این نشانی ایمیل قبلاً ثبت نام کرده است');
    }

    const passwordHash = await hashPassword(plainPassword);
    const newUser = await this.userRepo.create({
      id: randomUUID(),
      email,
      passwordHash,
    });

    // حذف اطلاعات حساس از خروجی
    const { passwordHash: _, ...safeUser } = newUser;
    return safeUser;
  }
}
```

#### ۳. لایهٔ کنترلر (Controller)
تنها مسئول هماهنگی پروتکل وب، صدا زدن سرویس و ساخت خروجی مناسب:

```typescript
import { Request, Response } from 'express';

export class UserController {
  constructor(private readonly userService: UserService) {}

  register = async (req: Request, res: Response) => {
    const { email, password } = req.body;
    const user = await this.userService.register(email, password);
    return res.status(201).json({
      success: true,
      data: user,
    });
  };
}
```

### جادوی آزمون‌پذیری (Testability)
چرا این تفکیک تا این حد حیاتی است؟ چون می‌توان لایهٔ سرویس را بدون نیاز به بالا آوردن یک دیتابیس واقعی و تنها با یک شیء مجازی (Mock) با سرعت میلی‌ثانیه‌ای تست کرد:

```typescript
// تست واحد برای UserService بدون نیاز به PostgreSQL
const mockRepo: UserRepository = {
  findById: async () => null,
  findByEmail: async (email) => (email === 'dup@site.com' ? { id: '1', email } as any : null),
  create: async (u) => ({ ...u, createdAt: new Date() }),
};

const service = new UserService(mockRepo);
// تست بررسی پرتاب خطای ConflictError در ایمیل تکراری
await assert.rejects(
  () => service.register('dup@site.com', 'secret123'),
  ConflictError
);
```

## ۴. اعتبارسنجی ورودی با Zod

> 🧒 **داستان این بخش:** صندوق پستی ورودی خانه را در نظر بگیر؛ نامه‌ها و بسته‌های مختلفی از بیرون ارسال می‌شوند. اگر هر بسته‌ای را بدون وارسی باز کنی، ممکن است درون آن محتوای خطرناک یا نامناسبی باشد. در نرم‌افزار، قاعدهٔ طلایی امنیت این است: **هیچ ورودی‌ای از بیرون برنامه امن و معتبر نیست.** حتی اگر فرم فرانت‌اند ورودی را چک کرده باشد، هر کاربری می‌تواند با ابزارهایی مانند `curl` یا Postman داده‌های مخرب یا نامعتبر ارسال کند.
>
> در گذشته توسعه‌دهندگان شرط‌های دستی فراوانی می‌نوشتند که نگهداری آن‌ها کابوس بود. در سال ۲۰۲۰، کتابخانهٔ **Zod** روشی نوین خلق کرد: تعریف یک شِمای واحد که هم انواع دادهٔ TypeScript را تضمین کند و هم در زمان اجرای واقعی اعتبارسنجی داده‌ها را انجام دهد.
>
> **این بخش جواب می‌دهد:** چگونه داده‌های ورودی را با دقت ارزیابی کنیم، چرا تایپ‌های کامپایلر برای امنیت کافی نیستند و دفاع سه‌لایه در داده‌ها چیست.

### چرا وجود دارد؟

در جاوااسکریپت و تایپ‌اسکریپت، تایپ‌ها در زمان کامپایل پاک می‌شوند (Type Erasure) و زمان اجرا وجود ندارند. بنابراین یک کد مانند:

```typescript
function register(input: { age: number }) { ... }
```

در زمان اجرا نمی‌تواند مانع ارسال شیء `{ age: -50 }` یا `{ age: "هزار" }` از طرف کلاینت شود.

### اعتبارسنجی هوشمند با Zod

با Zod شِمای ورودی تعریف می‌شود و به کمک متد `safeParse`، ورودی به شکل امن ارزیابی می‌گردد:

```typescript
import { z } from 'zod';

export const RegisterUserSchema = z.object({
  email: z
    .string({ required_error: 'وارد کردن ایمیل الزامی است' })
    .email('فرمت ایمیل نامعتبر است')
    .max(100),
  password: z
    .string()
    .min(8, 'رمز عبور باید حداقل ۸ نویسه باشد')
    .regex(/[A-Z]/, 'رمز عبور باید حداقل یک حرف بزرگ داشته باشد')
    .regex(/[0-9]/, 'رمز عبور باید حداقل یک رقم داشته باشد'),
  age: z.number().int().min(18).max(120).optional(),
});

// استخراج خودکار تایپ تایپ‌اسکریپت از روی شِما بدون کدنویسی مضاعف
export type RegisterUserInput = z.infer<typeof RegisterUserSchema>;
```

### ساخت میان‌افزار اعتبارسنجی سراسری

```typescript
import { Request, Response, NextFunction } from 'express';
import { ZodSchema } from 'zod';

export function validateBody<T>(schema: ZodSchema<T>) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      return res.status(422).json({
        success: false,
        error: {
          code: 'VALIDATION_ERROR',
          message: 'داده‌های ارسالی با استاندارد سامانه مطابقت ندارد',
          details: result.error.issues.map((issue) => ({
            field: issue.path.join('.'),
            message: issue.message,
          })),
        },
      });
    }

    // جایگزینی بدنه خام با دادهٔ پاک‌سازی‌شده و کاملاً تایپ‌شده
    req.body = result.data;
    next();
  };
}

// استفاده آسان در مسیر:
app.post('/api/users', validateBody(RegisterUserSchema), userController.register);
```

| لایهٔ دفاعی | وظیفهٔ اصلی | ابزار مورد استفاده |
|------------|-------------|-------------------|
| **۱. دروازهٔ ورود (Edge / Controller)** | بررسی نوع داده، طول فیلد و الگوی کاراکترها | کتابخانهٔ Zod |
| **۲. لایهٔ سرویس (Service)** | بررسی قوانین منطقی کسب‌وکار (مانند موجودی حساب یا عدم تکرار) | منطق درون Service |
| **۳. لایهٔ پایگاه داده (Database)** | تضمین نهایی یکپارچگی اطلاعات در صورت خطای لایه‌های قبل | قیدهای `UNIQUE`, `FOREIGN KEY`, `CHECK` |

## ۵. استانداردسازی پاسخ و مدیریت متمرکز خطا

> 🧒 **داستان این بخش:** تیمی از برنامه‌نویسان را فرض کن که هرکدام برای سرویس خود شیوهٔ پاسخ‌گویی متفاوتی را در پیش گرفته است؛ یکی در زمان بروز مشکل عدد خطای متنی برمی‌گرداند، دیگری وضعیت ۵۰۰ را با صفحهٔ HTML خالی می‌فرستد و سومی اصلاً پاسخ را نمی‌بندد. برنامه‌نویس فرانت‌اند در چنین شرایطی باید برای هر خطای ساده ده‌ها شرط متناقض بنویسد. راه‌حل بنیادین، پایبندی به یک **قرارداد مشترک پاسخ و مدیریت متمرکز تمامی خطاها** در یک لایهٔ نهایی است.
>
> یک API استاندارد تنها یک فایل کد نیست، بلکه یک قرارداد ارتباطی شفاف و پیش‌بینی‌پذیر میان سیستم‌هاست.
>
> **این بخش جواب می‌دهد:** ساختار استاندارد پاسخ موفق و ناموفق چیست، چگونه کلاس‌های خطای اختصاصی بسازیم و خطایاب سراسری Express چطور مانع از افشای اسرار امنیتی به مهاجمان می‌شود.

### ساختار پاکت پاسخ (API Response Envelope)

تمامی پاسخ‌ها در سیستم باید از یک پاکت پیش‌بینی‌پذیر پیروی کنند:

```json
// پاسخ موفق (200 OK یا 201 Created)
{
  "success": true,
  "data": {
    "id": "u-102",
    "email": "user@example.com"
  },
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 120
  }
}

// پاسخ ناموفق (4xx یا 5xx)
{
  "success": false,
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "کاربر با شناسه مورد نظر یافت نشد",
    "details": []
  }
}
```

### سلسله‌مراتب کلاس‌های خطا

```typescript
export abstract class AppError extends Error {
  abstract readonly statusCode: number;
  abstract readonly code: string;

  constructor(message: string, public readonly details?: unknown) {
    super(message);
    Object.setPrototypeOf(this, new.target.prototype);
  }
}

export class NotFoundError extends AppError {
  readonly statusCode = 404;
  readonly code = 'NOT_FOUND';
}

export class ConflictError extends AppError {
  readonly statusCode = 409;
  readonly code = 'CONFLICT';
}

export class ForbiddenError extends AppError {
  readonly statusCode = 403;
  readonly code = 'FORBIDDEN';
}

export class ValidationError extends AppError {
  readonly statusCode = 422;
  readonly code = 'VALIDATION_ERROR';
}
```

### میان‌افزار خطایاب سراسری (Global Error Handler)

```typescript
import { ErrorRequestHandler } from 'express';

export const globalErrorHandler: ErrorRequestHandler = (err, req, res, next) => {
  // ۱. خطاهای عملیاتی و شناخته‌شده سامانه ما
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      success: false,
      error: {
        code: err.code,
        message: err.message,
        details: err.details,
      },
    });
  }

  // ۲. نگاشت خطاهای شناخته‌شده درایورها (مانند دیتابیس یا JWT)
  if (err.name === 'TokenExpiredError') {
    return res.status(401).json({
      success: false,
      error: { code: 'TOKEN_EXPIRED', message: 'نشست کاربری شما منقضی شده است' },
    });
  }

  if ((err as any).code === '23505') { // کد نقض قید یکتا در PostgreSQL
    return res.status(409).json({
      success: false,
      error: { code: 'DUPLICATE_ENTRY', message: 'این مقدار قبلاً در سیستم ثبت شده است' },
    });
  }

  // ۳. خطاهای پیش‌بینی‌نشده (خطای نرم‌افزاری یا باگ ۵۰۰)
  console.error('[UNHANDLED_EXCEPTION]', {
    message: err.message,
    stack: err.stack,
    url: req.originalUrl,
    method: req.method,
  });

  // ⚠️ نکته امنیتی مهم: هرگز نباید جزییات استک دیتابیس یا متن خام خطای ۵۰۰ به کاربر فرستاده شود!
  return res.status(500).json({
    success: false,
    error: {
      code: 'INTERNAL_SERVER_ERROR',
      message: 'خطایی پیش‌بینی‌نشده در پردازش سرور رخ داده است',
    },
  });
};
```

> 💡 **مدیریت خطاهای غیرهمگام (Async Errors):** در Express 4، اگر کدی با `async/await` استثنایی پرتاب کند، برنامه به‌طور خودکار آن را به خطایاب سراسری نمی‌رساند و درخواست معلق می‌ماند؛ در نتیجه استفاده از پوشش‌دهنده‌ای نظیر `fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next)` لازم بود. در **Express 5** این نقیصه برطرف شده و خطاهای Promise به شکل پیش‌فرض به خطایاب منتقل می‌شوند.

## ۶. HTTP Semantics کامل

> 🧒 **داستان این بخش:** پروتکل HTTP شبیه به صندوق مرسولات با تمبرهای استانداردی است که وظیفهٔ هر بسته را مشخص می‌کند: تمبر «بخوان»، تمبر «ایجاد کن» یا تمبر «حذف کن». سال‌ها پیش اگر فردی برای حذف یک حساب کاربری از متد `GET` استفاده می‌کرد، با باز کردن یک پیوند ساده توسط ربات جست‌وجوگر، تمام داده‌های سیستم ناخواسته پاک می‌شد!
>
> استانداردهای جهانی HTTP (مانند RFC 9110) این معانی را شفاف ساخته‌اند تا کلاینت‌ها و سرورها بر پایه‌ای استوار با یکدیگر مکالمه کنند.
>
> **این بخش جواب می‌دهد:** متدهای مختلف HTTP چه معنایی دارند، ویژگی‌های Safe و Idempotent چیست، و چه تفاوت بنیادینی میان سبک‌های معماری REST، GraphQL و gRPC وجود دارد.

### متدها و مفاهیم بنیادین HTTP

در پروتکل HTTP، متدها از نظر تأثیر روی سرور به دو دستهٔ حیاتی تقسیم می‌شوند:

- **Safe (امن):** متدی که وضعیت داده‌ها در سرور را تغییر **نمی‌دهد** (مانند `GET` و `HEAD`). این درخواست‌ها را می‌توان بدون نگرانی کش کرد یا دوباره فرستاد.
- **Idempotent (توان‌پا یا یکسان‌عمل):** متدی که اگر ده بار پشت‌سرهم با داده‌های یکسان فرستاده شود، نتیجهٔ نهایی روی سرور دقیقاً معادل **یک بار فراخوانی** خواهد بود (مانند `GET`, `PUT`, `DELETE`). متد `POST` توان‌پا نیست؛ ارسال مکرر آن منجر به ساخت رکوردهای تکراری می‌شود.

| متد HTTP | کاربرد استاندارد | Safe؟ | Idempotent؟ | کد وضعیت متداول |
|----------|-------------------|-------|-------------|-----------------|
| `GET` | دریافت یک منبع یا لیست | بله | بله | 200 OK |
| `POST` | ایجاد یک منبع جدید / ارسال فرم | خیر | خیر | 201 Created |
| `PUT` | جایگزینی کامل یک منبع موجود | خیر | بله | 200 OK / 204 No Content |
| `PATCH` | به‌روزرسانی جزئی فیلدهای منبع | خیر | خیر* | 200 OK |
| `DELETE` | حذف منبع از سیستم | خیر | بله | 200 OK / 204 No Content |

### کدهای وضعیت پرکاربرد (Status Codes)

- **2xx (موفقیت):** `200 OK`, `201 Created` (برای ساخت منابع جدید), `204 No Content` (عملیات موفق بدون بازگرداندن بدنه).
- **3xx (هدایت مجدد):** `301 Moved Permanently` (انتقال دائم), `304 Not Modified` (داده نسبت به نسخهٔ کش کلاینت تغییری نکرده و بدنه خالی است).
- **4xx (خطای کلاینت):**
  - `400 Bad Request` (فرمت درخواست غلط است).
  - `401 Unauthorized` (کاربر احراز هویت نشده یا توکن ندارد).
  - `403 Forbidden` (کاربر لاگین کرده اما اجازهٔ دسترسی به این منبع خاص را ندارد).
  - `404 Not Found` (منبع وجود ندارد).
  - `409 Conflict` (تداخل منطقی؛ مثل ایمیل تکراری).
  - `422 Unprocessable Entity` (فرمت JSON درست است اما داده‌ها ولید نیستند).
  - `429 Too Many Requests` (ترافیک فراتر از محدودیت Rate Limit).
- **5xx (خطای سرور):** `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

### مقایسه سبک‌های معماری ارتباطی

| ویژگی | REST (معماری وب سنتی) | GraphQL | gRPC (گوگل) |
|-------|-----------------------|---------|-------------|
| **مدل تفکر** | منبع‌محور (بر پایه URL و منابع) | مدل داده و شِما (Schema-driven) | فراخوانی رویه‌های راه‌دور (RPC) |
| **قالب پیام** | متنی (JSON) | متنی (JSON) | فشرده باینری (Protocol Buffers) |
| **حل معضل N+1** | نیازمند اندپوینت‌های اختصاصی | بله (کلاینت فیلدهای دقیق را می‌طلبد) | با طراحی بهینه در سرور |
| **پشتیبانی کش HTTP** | عالی و بومی روی مرورگرها و CDN | پیچیده (معمولاً همه درخواست‌ها POST هستند) | خیر (پروتکل داخلی باینری) |
| **مورد استفاده ایده‌آل** | وب عمومی، اپلیکیشن‌های CRUD | داشبوردهای پیچیده فرانت‌اند با داده متغیر | ارتباطات پرسرعت میان میکروسرویس‌ها |

> 🔑 **gRPC چیست؟** پروتکلی مدرن توسعه‌یافته توسط گوگل بر بستر HTTP/2 که داده‌ها را به‌جای متن سنگین JSON در قالبی فشرده و دودویی (Protobuf) ردوبدل می‌کند. مرورگرها امکان ارتباط مستقیم بومی با آن را ندارند؛ بنابراین gRPC بهترین انتخاب برای تبادل سریع اطلاعات **بین سرورهای داخلی** در معماری میکروسرویس است.

## ۷. HTTP Caching

> 🧒 **داستان این بخش:** کتابداری را در نظر بگیر که هر بار مراجعه‌کننده‌ای کتابی می‌خواهد، به‌جای پاسخ سریع، دوباره کل قفسه‌ها را از اول تا آخر جست‌وجو می‌کند. سیستم کارآمد به این صورت است که کتابدار کارت خلاصه‌ای با شمارهٔ نسخه (ETag) یا برچسب تاریخ اعتبار (Cache-Control) روی میز می‌گذارد. اگر مراجعه‌کننده همان نسخه را همراه داشته باشد، پاسخی بدون زحمت بازگردانده می‌شود.
>
> در دنیای واقعی وب، درصد بسیار بالایی از درخواست‌ها تکراری هستند. کش کردن اصولی یعنی بیشترین پاسخ‌گویی با کمترین بار پردازشی بر دوش پایگاه داده.
>
> **این بخش جواب می‌دهد:** چگونه با هدرهای ETag و Cache-Control رفتار مرورگر و شبکه را هدایت کنیم و الگوی سمت سرور Cache-Aside چیست.

### چرا وجود دارد؟

اگر سرور برای هر بار مشاهدهٔ یک محصول یا صفحهٔ مشخص توسط کاربران مختلف، مجدداً پرس‌وجوهای سنگین دیتابیس را تکرار کند، مصرف پردازنده سرسام‌آور شده و زمان پاسخ کند می‌شود. بخش بزرگی از داده‌ها به‌ندرت تغییر می‌کنند؛ کشینگ راهکار پرهیز از محاسبات مجدد تکراری است.

### سازوکارهای کشینگ در کلاینت و شبکه

#### ۱. هدر ETag و اعتبارسنجی مشروط (Conditional Request)
مقدار `ETag` یک هش معتبر از محتوای پاسخ است. در درخواست‌های بعدی، کلاینت این مقدار را در هدر `If-None-Match` می‌فرستد. اگر محتوا تغییری نکرده باشد، سرور با کد **`304 Not Modified`** بدون ارسال بدنه پاسخ می‌دهد و پهنای باند را حفظ می‌کند:

```http
# درخواست کلاینت
GET /api/products/42 HTTP/1.1
If-None-Match: "v1-a8f3b"

# پاسخ سرور در صورت عدم تغییر
HTTP/1.1 304 Not Modified
ETag: "v1-a8f3b"
```

#### ۲. هدر کنترل کش (Cache-Control)
دستورالعملی صریح برای تعیین زمان و مکان مجاز نگهداری داده‌ها:

```http
Cache-Control: public, max-age=86400, stale-while-revalidate=3600
```

- `public`: پاسخ در کش‌های واسط مثل CDN و سرورهای پروکسی مجاز به ذخیره‌سازی است.
- `private`: پاسخ فقط در حافظهٔ مرورگر کاربر اختصاصی ذخیره شود (حاوی اطلاعات شخصی).
- `no-cache`: کش کردن مجاز است، اما پیش از هر بار استفاده باید با سرور اصلی اعتبار آن سنجیده شود.
- `no-store`: داده بسیار حساس است و به هیچ عنوان نباید در هیچ حافظه‌ای ذخیره گردد.

### الگوی سمت سرور: Cache-Aside (Lazy Loading)

در کنار کش کلاینت، سرورها از پایگاه داده‌های فوق‌سریع درون حافظه‌ای (مانند Redis) برای کاهش بار پردازش استفاده می‌کنند:

```typescript
export async function getProductById(id: string, redis: any, db: any) {
  const cacheKey = `product:${id}`;

  // ۱. اولویت با حافظه کش
  const cachedData = await redis.get(cacheKey);
  if (cachedData) {
    return JSON.parse(cachedData); // کش موفق (Hit)
  }

  // ۲. در صورت نبود (Miss)، واکشی از دیتابیس اصلی
  const product = await db.query('SELECT * FROM products WHERE id = $1', [id]);
  if (!product) return null;

  // ۳. ذخیره در کش به همراه زمان انقضا (TTL) جهت جلوگیری از ماندگاری داده فاسد
  await redis.set(cacheKey, JSON.stringify(product), 'EX', 300); // انقضا: ۵ دقیقه

  return product;
}
```

## ۸. CORS، CSP و امنیت محتوایی

> 🧒 **داستان این بخش:** مرورگر مدرن نگهبانی بسیار محتاط است؛ هنگامی که کدی در سایت `alpha.ir` اجرا می‌شود و قصد دارد درخواستی محرمانه به سایت بانکی `bank.ir` بفرستد، مرورگر جلوی افشای داده را می‌گیرد تا جلوی سرقت هویت کاربر گرفته شود. این قانون بنیادین «سیاست خاستگاه یکسان» (Same-Origin Policy) نام دارد.
>
> اما وب یک زیست‌بوم تعاملی است و گاهی سرورها تمایل دارند به اپلیکیشن فرانت‌اند در دامنه‌ای دیگر اجازهٔ دسترسی بدهند. مکانیزم **CORS** راهکار امنیتی سرور برای صدور این مجوز است.
>
> **این بخش جواب می‌دهد:** خطای CORS ناشی از چیست، پیش‌پرواز (Preflight) چه نقشی دارد، و چگونه با سیاست امنیتی محتوا (CSP) مانع حملات XSS شویم.

### ماهیت CORS (اشتراک‌گذاری منابع بین خاستگاه‌ها)

یک «خاستگاه» یا Origin شامل سه بخش است: **پروتکل + دامنه + پورت** (مانند `https://app.site.com:443`). اگر هر یک متفاوت باشد، درخواست چندخاستگاهی (Cross-Origin) تلقی می‌شود.

مرورگر برای درخواست‌های پیچیده ابتدا یک درخواست مقدماتی با متد **`OPTIONS`** (به نام Preflight) ارسال می‌کند تا بررسی کند آیا سرور اجازهٔ این تبادل را صادر می‌کند یا خیر:

```typescript
import cors from 'cors';

// تنظیم ایمن و حرفه‌ای CORS:
app.use(cors({
  origin: (origin, callback) => {
    const whitelist = ['https://app.mydomain.com', 'https://admin.mydomain.com'];
    if (!origin || whitelist.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('درخواست از این مبدأ توسط CORS مسدود شده است'));
    }
  },
  credentials: true, // ارسال کوکی‌ها و اطلاعات نشست
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  maxAge: 86400, // کش کردن پاسخ Preflight برای ۲۴ ساعت
}));
```

> ⚠️ **دام امنیتی مرگبار:** اگر هدر `Access-Control-Allow-Origin: *` تنظیم شده باشد، مرورگرها به دلایل امنیتی **هرگز اجازه نخواهند داد** گزینهٔ `credentials: true` فعال شود. در غیر این صورت هر وب‌سایت مخربی می‌توانست با هویت کوکی‌های ثبت‌شدهٔ کاربر، عملیات بانکی انجام دهد!

### سیاست امنیتی محتوا (CSP - Content Security Policy)

خط دفاعی مستحکم در مرورگر برای مقابله با تزریق اسکریپت مخرب (XSS). به کمک این هدر، به مرورگر ابلاغ می‌شود که تنها اسکریپت‌های مبدأهای مجاز را بارگذاری کند:

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; style-src 'self' 'unsafe-inline'; object-src 'none';
```

## ۹. Real-Time Data

> 🧒 **داستان این بخش:** گفت‌وگویی دونفره را در نظر بگیر؛ اگر یکی از طرفین هر سه ثانیه با عجله بپرسد «پیام جدیدی هست؟ آیا جوابی داری؟»، مصرف انرژی بالا رفته و مکالمه کند خواهد بود. روش درست این است که لوله‌ای دائمی و باز میان دو طرف برقرار باشد تا هر زمان پیامی ارسال شد، فوراً و بدون پرس‌وجوی مکرر به مقصد برسد.
>
> در دنیای وب، ارتباطات بلادرنگ با راهکارهایی نظیر Server-Sent Events و WebSocket دقیقاً همین نیاز را برآورده می‌کنند.
>
> **این بخش جواب می‌دهد:** چه زمانی از Polling، چه زمانی از SSE و چه هنگام از WebSocket استفاده کنیم و نحوهٔ ساخت یک جریان پایدار استریم داده چگونه است.

### مقایسه فناوری‌های داده‌های بلادرنگ

| فناوری | جهت تبادل | پروتکل زیرین | پیچیدگی سرور | مورد استفاده ایده‌آل |
|--------|-----------|--------------|---------------|----------------------|
| **Polling دوره‌ای** | کلاینت به سرور بر اساس تایمر | HTTP استاندارد | بسیار پایین | بررسی دوره‌ای وضعیت‌های کم‌تغییر (سفارش پستی) |
| **Server-Sent Events (SSE)** | فقط سرور به کلاینت (یک‌طرفه) | HTTP استاندارد با استریم متنی | متوسط | اعلانات، فید قیمت طلا و بورس، استریم توکن‌های هوش مصنوعی |
| **WebSocket** | دوطرفه و هم‌زمان (Full-Duplex) | پروتکل مستقل `ws://` | بالا | اتاق‌های گفت‌وگو (Chat)، بازی‌های آنلاین، ویرایش گروهی مستندات |
| **Webhooks** | سرور به سرور (رویدادمحور) | درخواست HTTP POST مستقیم | پایین | درگاه‌های بانکی، اعلان تغییر وضعیت گیت‌هاب به CI/CD |

### پیاده‌سازی استریم پایدار با Server-Sent Events (SSE)

در SSE سرور با ارسال هدر `text/event-stream` اتصال را باز نگه می‌دارد و داده‌ها را در بسته‌های خطی ارسال می‌کند:

```typescript
app.get('/api/live-metrics', (req: Request, res: Response) => {
  // تنظیم هدرهای ضروری برای استریم متن
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  });

  // ارسال داده اولیه
  res.write(`data: ${JSON.stringify({ status: 'connected', time: new Date() })}\n\n`);

  // ارسال منظم گزارش هر دو ثانیه
  const timer = setInterval(() => {
    const payload = {
      cpuUsage: Math.random() * 100,
      activeUsers: 1420,
    };
    res.write(`data: ${JSON.stringify(payload)}\n\n`);
  }, 2000);

  // ⚠️ نکته حیاتی جلوگیری از Memory Leak: پاک‌سازی تایمر هنگام قطع ارتباط کاربر
  req.on('close', () => {
    clearInterval(timer);
    res.end();
  });
});
```

- درک عمیق چرخهٔ حیات درخواست HTTP و الگوی زنجیرهٔ میان‌افزارها (Middleware Chaining).

- راهکارهای بلادرنگ (Real-Time) و پیاده‌سازی استریم یک‌طرفه با Server-Sent Events بدون نشت حافظه.
