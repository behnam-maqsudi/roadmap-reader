# فاز ۸ — تست، کانتینرسازی، استقرار و مشاهده‌پذیری

> 🧒 **داستان:** روز اول، یک تیم پنج‌نفره‌ای شروع کرد. کد می‌نوشتند، روی
> سرورِ تست می‌گذاشتند، و دستی کلیک می‌کردند تا مطمئن شوند کار می‌کند. همه
> خوشحال بودند.
>
> یک سال بعد، سرورِ تست هنوز همان بود و نسخه‌ی جدید **همان‌جا** بود. تنها
> تفاوت این بود که آن کلیک‌های دستی دیگر انجام نمی‌شد — چون وقتشان نبود. یک
> تغییرِ کوچک، دو روز پیدا نشد و وقتی پیدا شد، دیگر کسی نمی‌دانست **از کِی**
> خراب شده. چون آن تغییر، شش ماه پیش رفته بود و از آن ۲۰ تا تغییر دیگر هم آمده بود.
>
> مشکل این بود که «تست» را گرفته بودند به معنیِ «یک بار امتحان کردن». ولی تست یعنی
> **قابل تکرار، خودکار، و سریع** — وگرنه فقط همان کلیکِ دستی است با هزینه‌ی بیشتر.
>
> و بعد سراغ بخشِ دوم رفتیم: آن پنج نفر، همیشه با ترس زندگی می‌کردند که «اگر
> خراب شود چه؟» جوابش این بود: کارِ دیگری. نسخه‌ی قبلیِ برنامه را نگه می‌دارند و
> اگر نسخه‌ی جدید خراب شد، **برمی‌گردند**. این تنها چیزی است که خوابت را
> راحت می‌کند — و کاری است که این فاز می‌سازد.
>
> این فاز از همان سؤال شروع می‌شود: چطور کاری کنیم که **هر تغییر**، قبل از رسیدن
> به کاربر، خودش را ثابت کند — و اگر خراب شد، برگشتش یک دکمه باشد.

## مقدمه: چطور مطمئن شویم که کارمان کار می‌کند؟

فرض کن ساعت ۲ بامداد یک باگ جدید deploy کرده‌ای. ساعت ۳ بامداد بیدار می‌شوی و می‌بینی نیمی از کاربران نمی‌توانند وارد شوند.

سؤال: **چقدر طول می‌کشد تا بفهمی مشکل چیست؟**

| پاسخ | یعنی چه؟ |
|------|---------|
| ۲ ساعت، با خواندن لاگ | 😰 فاجعه |
| ۱۵ دقیقه، با هشدار خودکار | 😐 قابل قبول |
| ۱ دقیقه، با داشبورد و نمودار | 😊 خوب |
| **اصلاً نفهمیدی، مشتری خبر داد** | 💀 فاجعه‌ی مطلق |

> 💡 این فاز دقیقاً درباره‌ی همین است: تست (قبل از deploy) + استقرار (درست و قابل برگشت) + مشاهده‌پذیری (بعد از deploy).

## نقشه‌ی کلان: خط لوله‌ی تحویل

```
کد تغییر کرد
   ⬇
[Commit + Push]
   ⬇
[CI: lint → test → build]        ← اگر شکست خورد، deploy نمی‌شود
   ⬇
[Build Docker Image]              ← تصویر تغییرناپذیر
   ⬇
[Deploy Staging] → [Smoke Tests]
   ⬇
[Deploy Production]
   ⬇
[Observe]  ← ⭐ اگر خطایی بود، Alert
   ⬇
[Rollback] ← اگر لازم شد
```

**راهنمای برچسب‌های دیاگرام** (هر کدام در بخش خودش کامل تعریف می‌شود):

- **CI** (یکپارچه‌سازی پیوسته): هر بار کد به ریپازیتوری push می‌شود، lint و تست خودکار اجرا می‌شود.
- **Docker**: ابزاری که یک برنامه را همراه همه‌ی وابستگی‌هایش در یک بسته‌ی ایزوله می‌بندد — بخش ۶.
- **Deploy Staging** (استقرار روی محیط آزمایشی): محیطی که دقیقاً شبیه محیط واقعی است ولی ترافیک کاربران واقعی را ندارد؛ برای اطمینان قبل از انتشار.
- **Smoke Test** (تست دود): تست سریعی که فقط چک می‌کند سرویس بالا آمده و مسیر اصلی کار می‌کند یا نه — کوتاه‌تر و کم‌هزینه‌ترین نوع تست، برای اینکه بفهمیم نسخه‌ی تازه‌نصیب‌شده اصلاً قابل استفاده هست یا خیر.
- **Observe** (مشاهده) و **Alert** (هشدار): نگاه کردن به وضعیت سیستم بعد از انتشار، و خبر دادن خودکار به تیم وقتی خرابی از آستانه رد شد.
- **Rollback** (برگشت): برگرداندن سیستم به نسخه‌ی قبلیِ سالم.

## ۱. تست — سه سطح

> 🧒 **داستان این بخش:** مکانیکِ ماشین را تصور کن. اول یک پیچ را تنها عوض می‌کند.
> بعد موتور را روشن می‌کند و می‌بیند راه می‌رود. بعد ماشین را می‌برد جاده‌ای
> چند کیلومتری و می‌بیند ترمز می‌کند. هر کدام چیزهای متفاوتی می‌گویند.

> تست هم سه سطح دارد و هر کدام **چیزِ متفاوتی** می‌گویند. تستِ واحد می‌گوید
> «این تابع درست کار می‌کند؟» تستِ یکپارچه می‌گوید «این دو تکه با هم کار
> می‌کنند؟» تستِ انتها‌به‌انتها می‌گوید «کاربر واقعاً می‌تواند کارش را بکند؟»
>
> این سه **رقیب** هم نیستند. هر کدام چیزی را می‌گویند که دو تای دیگر نمی‌گویند.
>
> **این بخش جواب می‌دهد:** هر سطح دقیقاً چه چیزی را می‌سنجد و کدام باگ را
> پیدا می‌کند که سطح‌های دیگر از آن رد می‌شوند.

**تست (Test)** یعنی کدی که خودش اجرا می‌شود و بررسی می‌کند رفتار برنامه همان چیزی است که باید باشد. دستوری مثل `npm test` که چند تست را می‌بیند و می‌گوید کدام‌ها شکست خوردند.

**I/O** (ورودی/خروجی): هر کاری که برنامه بیرون از حافظه‌ی خودش انجام می‌دهد — خواندن فایل، زدن درخواست به دیتابیس یا API، نوشتن در شبکه. دلیل اینکه تست unit «بدون I/O» نوشته می‌شود این است که I/O کند است و به محیط بیرونی وابسته است؛ تابعی که فقط محاسبه می‌کند در چند میکروثانیه و بدون هیچ وابستگی تست می‌شود.

سه سطح، از ریز به درشت:

- **Unit Test** (تست واحد): تست یک تابع یا کلاس **به‌تنهایی**، دور از هر چیز بیرونی. ورودی می‌دهی، خروجی را چک می‌کنی. مثل اینکه فقط یک چرخ‌دنده را از ماشین جدا کنی و ببینی درست می‌چرخد یا نه.
- **Integration Test** (تست یکپارچگی): تست **دو یا چند بخش واقعی با هم** — مثلاً HTTP endpoint به‌علاوه‌ی دیتابیس واقعی. اینجاست که مرزها هستند و بیشتر باگ‌های واقعی زاده می‌شوند.
- **E2E Test** (تست سرتاسری، End-To-End): تست کل مسیر کاربر از ابتدا تا انتها، روی یک مرورگر واقعی. کندترین و گران‌ترین سطح، ولی تنها چیزی است که واقعاً «همه‌چیز با هم کار می‌کند» را ثابت می‌کند.

| نوع | چه چیزی را تست می‌کند | سرعت | چند بار در روز |
|-----|---------------------|------|-----------------|
| **Unit** | یک تابع، بدون I/O | ⚡ میلی‌ثانیه | هزاران |
| **Integration** | چند بخش با هم (مثلاً API + دیتابیس) | 🐌 ثانیه | ده‌ها |
| **E2E** | کل مسیر کاربر در مرورگر واقعی | 🐌🐌 ده‌ثانیه | چند تا |

```
         تعداد:      ◄──────────────────────►
    زمان اجرا:      ──────────────────────────────────►

    ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  Unit        (90% تست‌ها)
    ▓▓▓▓▓▓▓▓                        Integration  (8%)
    ▓▓▓                                E2E        (2%)
```

> 🔑 **قانون معروف:** تست‌های سریع‌تر باید بیشتر باشند. اگر خط لوله‌ات ۲۰ دقیقه طول بکشد، تیم کم‌کم تست را skip می‌کند — و تستی که skip شود، از نبودنش هم بدتر است.

### Unit Test — چیزی که واقعاً ارزش تست دارد

```typescript
import { describe, it, expect } from 'vitest';

import { calculateDiscount } from '../domain/pricing';

describe('calculateDiscount', () => {
  it('تخفیف ساده را اعمال می‌کند', () => {
    expect(calculateDiscount(100_000, 10)).toBe(90_000);
  });

  it('تخفیف پلکانی را محاسبه می‌کند', () => {
    // بیش از ۱۰۰ هزار → ۱۵٪ + بیش از ۵۰۰ هزار → ۲۵٪
    expect(calculateDiscount(600_000, 0)).toBe(450_000);
  });

  it('قیمت منفی را نمی‌پذیرد', () => {
    expect(() => calculateDiscount(-100, 10)).toThrow(ValidationError);
  });

  // ⭐ تست مرزی — جایی که باگ‌ها پنهان می‌شوند
  it('دقیقاً روی مرز پلکان اول', () => {
    expect(calculateDiscount(100_000, 0)).toBe(90_000);   // ۱۰٪
    expect(calculateDiscount(100_001, 0)).toBe(85_000);   // ۱۵٪
  });
});
```

### 🔴 کدام چیزها را **نباید** تست کرد

| ❌ تست نکن | چرا |
|-----------|-----|
| کتابخانه‌ی شخص ثالث | آن‌ها تست دارند |
| getter/setter ساده | بی‌ارزش |
| توابع بدون منطق | فقط coverage را بالا می‌برند |
| جزئیات پیاده‌سازی | تست را می‌شکند بدون اینکه باگ را بگیرد |

> 💡 **Coverage مهم نیست، رفتار مهم است.** تستی که فقط `expect(fn).toBeDefined()` می‌کند هیچ ارزشی ندارد.

## ۲. تست Integration — کجا شکست‌های واقعی هستند

> 🧒 **داستان این بخش:** دو قطعه را تنها تست کنی، هر دو سالم‌اند. ولی وقتی به هم
> وصلشان می‌کنی، یکی دنبال زمانِ سمتِ UTC است و آن یکی دنبال زمانِ محلی. هر دو
> درست کار می‌کردند.
>
> این نوع باگ را تستِ واحد **نمی‌بیند** — و این دقیقاً همان چیزی است که
> در واقعیت اتفاق می‌افتد. باگ‌های گران، باگ‌هایی هستند که در **مرزِ**
> دو سیستم زندگی می‌کنند.
>
> مشکلِ تستِ یکپارچه این است که کند و شکننده است. اگر به دیتابیس واقعی وصل شود،
> هر بار باید بالا بیاید. به همین دلیل جای دیگری از راه می‌آید.
>
> **این بخش جواب می‌دهد:** چرا باگ‌های گران در مرزها هستند، چرا تستِ
> یکپارچه معمولاً کندترین تست است، و چطور آن را قابل اعتماد نگه می‌داریم.

بیشتر باگ‌های واقعی در مرز بین اجزا هستند، نه داخل یک تابع.

```typescript
import { describe, it, beforeAll, afterAll, expect } from 'vitest';
import request from 'supertest';
import { app } from '../app';
import { db } from '../db';

describe('POST /api/users', () => {
  beforeAll(async () => {
    await db.migrate();           // ⭐ اسکیمای واقعی بساز
  });

  afterAll(async () => {
    await db.close();
  });

  it('کاربر معتبر می‌سازد', async () => {
    const res = await request(app)
      .post('/api/users')
      .send({ email: 'ali@test.com', name: 'علی' });

    expect(res.status).toBe(201);
    expect(res.body).toHaveProperty('id');

    // آیا واقعاً در دیتابیس ذخیره شد؟
    const saved = await db.users.findById(res.body.id);
    expect(saved.email).toBe('ali@test.com');
  });

  it('ایمیل نامعتبر را رد می‌کند', async () => {
    const res = await request(app)
      .post('/api/users')
      .send({ email: 'not-an-email', name: '' });

    expect(res.status).toBe(422);
  });

  it('ایمیل تکراری را رد می‌کند', async () => {
    await request(app).post('/api/users').send({ email: 'dup@test.com' });
    const res = await request(app)
      .post('/api/users').send({ email: 'dup@test.com' });
    expect(res.status).toBe(409);      // Conflict
  });
});
```

### تست دیتابیس واقعی، نه Mock

- **به زبان ساده:** کوکی روی قیاس است، نه غذا. برای مطمئن شدن از غذا، باید غذا را بپزی.

| رویکرد | سرعت | واقع‌گرایی | کِی |
|---------|------|------------|-----|
| Mock همه‌چیز | ⚡⚡⚡ | ❌ | فقط واحدهای خالص |
| دیتابیس واقعی (در حافظه یا Testcontainer) | 🐌 | ✅✅ | اکثر integration test‌ها |
| دیتابیس واقعی در CI | 🐌 | ✅✅✅ | تست‌های حیاتی |

> 💡 PostgreSQL را می‌توانی با [PGlite](https://pglite.dev/) (نسخه‌ی درون‌حافظه‌ای WASM) در چند میلی‌ثانیه بالا بیاوری — کاملاً شبیه دیتابیس واقعی، بدون نصب.

## ۳. Mocking — چه چیزی را mock کنیم؟

> 🧒 **داستان این بخش:** می‌خواهی منطقِ خرید را تست کنی. ولی برای این کار باید به
> درگاهِ پرداختِ واقعی وصل شوی، یا هر تست کارت می‌خواهد و پول واقعی جابه‌جا می‌کند.

> راه‌حل: یک **نسخه‌ی قلابی** از درگاه بساز. همان رابط را دارد، ولی به‌جای
> بانک، جوابِ از پیش تعیین‌شده می‌دهد. اسمش **mock** است.

> ولی این یک خطر دارد: اگر همه‌چیز را mock کنی، دیگر **هیچ‌چیز واقعی** را
> تست نکرده‌ای. تستِ سریعی که هیچ باگِ واقعی را پیدا نمی‌کند، فقط یک
> **تستِ دروغیِ سریع** است.
>
> **این بخش جواب می‌دهد:** قاعده‌ی ساده‌ی «چه چیزی را mock کنیم» چیست (مرزها،
> نه قلب)، و چطور با یک تستِ یکپارچه‌ی کوچک، ریسکِ mock را جبران می‌کنیم.

- **به زبان ساده:** mock یعنی یک نسخه‌ی **تقلبی** بسازی که فقط رفتار مورد نیاز را داشته باشد.

```typescript
// ❌ Mock بد: بیش از حد ساختگی، تست را بی‌معنا می‌کند
userRepo.findById = vi.fn().mockResolvedValue({
  id: 1, email: 'a@b.c', name: 'x', role: 'admin',
  passwordHash: 'x'.repeat(60), createdAt: new Date(),   // 😱
});

// ✅ Mock خوب: فقط چیزی که این تست به آن اهمیت می‌دهد
const mockUserRepo: Partial<UserRepository> = {
  findById: vi.fn().mockResolvedValue({ id: 1, email: 'a@b.c' } as User),
  create: vi.fn().mockResolvedValue({ id: 1 }),
};
```

| چه چیزی را mock کن | دلیل |
|--------------------|------|
| API بیرونی (stripe، پیامک) | کند، پولی، غیرقابل اعتماد |
| زمان و تاریخ | غیرقابل تکرار |
| تصادف (`Math.random`) | نتیجه‌ی غیرقابل پیش‌بینی |
| سرویس داخلی سنگین (ایمیل) | مرز مسئولیت |

| چه چیزی را mock **نکن** | دلیل |
|---------------------|------|
| دیتابیس خودت | باگ را مخفی می‌کند |
| کد خودت | داری همان چیزی را تست می‌کنی که ساخته‌ای |

## ۴. TDD — آیا واقعاً لازم است؟

> 🧒 **داستان این بخش:** معلمی را تصور کن که می‌گوید «اول امتحان را بنویس،
> بعد درس را بخوان». عجیب به‌نظر می‌رسد، ولی یک دلیل دارد: اگر اول درس را
> بخوانی و بعد امتحان را بنویسی، آن‌قدر درگیرش می‌شوی که دیگر یادت نمی‌آید
> اصلاً قرار بود یاد بگیری.

> در کد هم همین است. اگر اول کد را بنویسی و بعد تست، معمولاً تست را طوری
> می‌نویسی که به کدت بخندد — چون کد را می‌بینی و حالت را می‌دانی.
>
> روشِ برعکس، یعنی **اول تست، بعد کد**، اسمش TDD است. سه گام دارد: قرمز،
> سبز، تمیز — و هر تستِ جدید اول باید **بشکند** تا ثابت کند واقعاً کار می‌کند.
>
> **این بخش جواب می‌دهد:** TDD دقیقاً چه ترتیبی دارد، چه فایده‌ای می‌دهد، و

```
قرمز  →  تستی بنویس که شکست بخورد
سبز  →  کمترین کدی بنویس که تست را پاس کند
بازبرگشت  →  تست‌ها و کد را پاک‌سازی کن
تکرار  →  قدم بعدی
```

- **چرا:** چون نوشتن تست **بعد** از نوشتن کد، تقریباً همیشه انجام نمی‌شود. تست قبل از کد، تنها راهی است که واقعاً اجرا شود.
- **چالش:** برای کدهای اکتشافی (که هنوز نمی‌دانی چه می‌خواهی) TDD سخت است. آن‌جا تست بعدی هم قابل قبول است.

> 💡 توصیه‌ی عملی: برای **منطق کسب‌وکار** (قیمت‌گذاری، احراز شرط، محاسبه) TDD. برای لایه‌های تکراری (CRUD boilerplate) تست یکپارچه کافی است.

## ۵. Test-Driven Security — تست امنیتی

> 🧒 **داستان این بخش:** یک باگ امنیتی که با تستِ عادی پیدا نشود، همان باگی است که
> می‌ماند. تستِ عادی می‌گوید «کاربر وارد شد؟ بله. درست جواب داد؟ بله.»
> ولی هیچ‌وقت نمی‌پرسد «آیا ورودیِ **غلط** هم امن رد می‌شود؟»

> تست امنیتی دقیقاً همان سؤال را می‌پرسد. یعنی به‌جای اینکه بگویی «کد کار
> می‌کند»، می‌گویی «کد **نمی‌تواند** کارِ نادرست را بکند».
>
> نکته‌ی کلیدی: هر تست امنیتی یک **تستِ منفی** است. یعنی ورودیِ بد، و انتظارِ
> رد شدن. این با الگوی معمولِ تست فرق دارد و همین باعث می‌شود اغلب نوشته نشود.
>
> **این بخش جواب می‌دهد:** (همه‌ی مثال‌ها روی سیستمِ تمرینیِ خودمان است، نه
> روی سیستمِ کسی) تست امنیتی چطور نوشته می‌شود، چرا باید **منفی** باشد، و

تست امنیتی یعنی تست معمولی که **حمله** را شبیه‌سازی می‌کند:

**چهار آسیب‌پذیری که این تست‌ها می‌گیرند** — هر کدام یک دسته‌ی مشخص از اشتباه‌های برنامه‌نویسی‌اند:

- **IDOR** (دسترسی مستقیم ناامن به شیء، Insecure Direct Object Reference): برنامه بررسی می‌کند «آیا این کاربر **وارد** شده؟» ولی بررسی نمی‌کند «آیا این کاربر **مالک** این پست است؟». نتیجه‌اش این است که هر کاربرِ واردشده می‌تواند با عوض کردن یک عدد در URL به داده‌ی بقیه دسترسی بزند — چیزی که سیستم اصلاً فکر نمی‌کند وجود داشته باشد. **مهم‌ترین آسیب‌پذیری این فاز**، چون خیلی ساده اتفاق می‌افتد: کافی است شناسه در URL باشد و یک شرط `if` جا نیفتد.
- **Mass Assignment** (انتساب انبوه): وقتی API ورودی کاربر را کورکورانه به مدل دیتابیس وصل می‌کند، کاربر می‌تواند فیلدهایی بفرستد که نباید دستشان باشد (مثلاً `role: admin`). دفاع: **فهرست سفید** فیلدهای مجاز، نه کپی کردن هرچه رسید.
- **XSS** (تزریق اسکریپت بین‌سایتی): ورودی کاربر بدون escape در صفحه‌ی HTML برگردانده می‌شود و مرورگر آن را کد اجرا می‌کند.
- **SQL Injection** (تزریق SQL): ورودی کاربر داخل کوئری SQL چسبانده می‌شود و ساختار خود کوئری را تغییر می‌دهد. همیشه با **کوئری پارامتری** جلویش را بگیر، نه با فیلتر کردن رشته.

> 💡 نکته‌ی مهم روش: این تست‌ها روی **محیط تست خودت** و با داده‌ی ساختگی اجرا می‌شوند. یک تست امنیتی فقط یک `assert` است که ثابت می‌کند سیستم در برابر آن ورودی رفتار درستی دارد.

```typescript
describe('امنیت: دسترسی به منابع دیگران', () => {
  let userA: User, userB: User, adminToken: string, userBToken: string;

  beforeAll(async () => {
    userA = await createUser('a@test.com');
    userB = await createUser('b@test.com');
    adminToken = await loginAsAdmin();
    userBToken = await loginAs(userB);
  });

  // 🔴 IDOR — مهم‌ترین تست امنیتی
  it('کاربر نمی‌تواند پست دیگران را بخواند', async () => {
    const post = await createPost(userA.id);
    const res = await request(app)
      .get(`/api/posts/${post.id}`)
      .set('Authorization', `Bearer ${userBToken}`);
    expect(res.status).toBe(403);
  });

  it('کاربر نمی‌تواند پست دیگران را حذف کند', async () => {
    const post = await createPost(userA.id);
    const res = await request(app)
      .delete(`/api/posts/${post.id}`)
      .set('Authorization', `Bearer ${userBToken}`);
    expect(res.status).toBe(403);
  });

  // 🔴 Mass Assignment
  it('کاربر نمی‌تواند خودش را ادمین کند', async () => {
    const res = await request(app)
      .patch('/api/users/me')
      .set('Authorization', `Bearer ${userBToken}`)
      .send({ name: 'تست', role: 'admin' });
    expect(res.status).toBe(200);
    expect(res.body.role).not.toBe('admin');       // ⭐ مهم‌ترین assert
  });

  // 🔴 XSS — ورودی باید escape شود
  it('اسکریپت در ورودی ذخیره نمی‌شود', async () => {
    const res = await request(app)
      .post('/api/posts')
      .set('Authorization', `Bearer ${userBToken}`)
      .send({ title: '<script>alert(1)</script>' });
    // اگر API خروجی HTML-escaped برمی‌گرداند، کاراکترها تغییر کرده‌اند
    expect(res.body.title).not.toContain('<script>');
  });

  // 🔴 SQL Injection
  it('در برابر SQL Injection مقاوم است', async () => {
    const res = await request(app)
      .get(`/api/users?email=' OR '1'='1`)
      .set('Authorization', `Bearer ${userBToken}`);
    expect(res.status).not.toBe(200);
    expect(Array.isArray(res.body) && res.body.length).toBeLessThanOrEqual(1);
  });
});
```

> 💡 اگر این پنج تست را برای هر endpoint حساس بنویسی، بخش بزرگی از آسیب‌پذیری‌های واقعی گرفته می‌شود.

## ۶. Containerization — چرا Docker؟

> 🧒 **داستان این بخش:** جمله‌ی مشهورِ قدیمی برنامه‌نویسی این بود: «روی سیستمِ
> من کار می‌کند.» و همیشه یعنی روی سیستمِ من **نمی‌کند**. چون نسخه‌ی پایتون،
> بسته‌های نصب‌شده و تنظیماتِ محیط، هیچ‌کدام ثبت نشده بودند.

> ایده‌ای که مشکل را حل کرد، از راه‌آهن بود: کشی که همه‌ی بارهایش با هم
> جا می‌رفت. ظرفی که کالا در آن ریخته شده بود، خودش هم می‌رفت.
>
> یک ظرف (container) یعنی برنامه به‌همراه **هرچه لازم دارد**: کتابخانه، نسخه‌ی
> زبان، تنظیمات. تحویل می‌دهی، هرجا اجرا شود — به‌جز محدودیت‌های هسته‌ای —
> یکسان کار می‌کند.
>
> تفاوتِ ظریف با ماشینِ مجازی: ظرف **هم‌هسته‌ی هسته‌ی سیستم‌عامل** را با
> سیستمِ تو می‌بیند. سبک‌تر است، ولی ایزولاسیونش کمی کمتر.
>
> **این بخش جواب می‌دهد:** ظرف دقیقاً چه چیزی را ثابت می‌کند، تفاوتش با ماشین
> مجازی چیست، و چرا `Dockerfile` دروازه‌ی تکرارپذیری است.

### مسئله‌ای که حل می‌کند

> «روی سیستم من کار می‌کند.» ← این جمله یعنی مشکل.

سه نفر هرکدام سیستم‌عامل متفاوت، نسخه‌ی متفاوت Node، نسخه‌ی متفاوت کتابخانه. تولید هم یک محیط دیگر.

- **به زبان ساده:** مثل ظرف دربسته‌ی غذای خانگی. مهم نیست آنجا غذا را درست کردی یا بیرون؛ بسته‌بندی همان است، نتیجه همان است.
- **به زبان فنی:** ایمیج کانتینر یک محیط ایزوله و **تکرارپذیر** است که شامل همه‌ی وابستگی‌هاست.

**سه واژه که نباید قاطی شوند:**

- **Docker** (خود ابزار): موتوری که ایمیج می‌سازد و کانتینر اجرا می‌کند — همان چیزی که با دستور `docker build` و `docker run` صدا می‌زنی.
- **Image** (ایمیج): یک قالب **تغییرناپذیر** — مثل یک فایل ISO. یک‌بار ساخته می‌شود و همه‌جا همان کپی اجرا می‌شود.
- **Container** (کانتینر): یک نمونه‌ی **در حال اجرا** از آن ایمیج. از یک ایمیج می‌توانی ده کانتینر هم‌زمان بالا بیاوری.

### لایه‌های یک ایمیج

```
لایه ۰: ubuntu:24.04            ← سیستم‌عامل پایه
لایه ۱: apt-get install curl   ← ابزارها
لایه ۲: COPY package*.json      ← فقط فایل‌های وابستگی
لایه ۳: npm ci                 ← نصب node_modules      ⭐ کش‌پذیر
لایه ۴: COPY . .                ← کد برنامه             ⭐ تغییر می‌کند
```

> 🔑 **نکته‌ی کلیدی:** لایه‌ی `npm ci` **قبل** از کپی کد بیاید. چون وقتی فقط کد تغییر می‌کند، لایه‌ی نصب وابستگی‌ها از cache استفاده می‌کند و build چند ثانیه طول می‌کشد، نه چند دقیقه.

### Dockerfile چندمرحله‌ای — Multi-stage

**Multi-stage Build** (ساخت چندمرحله‌ای) یعنی در یک Dockerfile چند `FROM` داشته باشی: مرحله‌ی اول با همه‌ی ابزارهای سنگین (کامپایلر، devDependency) کد را **می‌سازد**؛ مرحله‌ی آخر فقط خروجی آماده (`dist` + چیزهای لازم برای اجرا) را از مرحله‌ی اول **کپی** می‌کند. پُلی که بین‌شان کپی می‌شود همان دستور `COPY --from=builder` است که در مثال زیر می‌بینی. نتیجه: ابزارهای ساخت وارد ایمیج نهایی نمی‌شوند.

```dockerfile
# ---------- مرحله ۱: build ----------
FROM node:22-alpine AS builder
WORKDIR /app

# اول فقط فایل‌های وابستگی (برای استفاده از cache)
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build && npm prune --omit=dev

# ---------- مرحله ۲: production ----------
FROM node:22-alpine AS production

# ⚠️ کاربر غیر root
RUN addgroup -S app && adduser -S app -G app

WORKDIR /app
ENV NODE_ENV=production

COPY --from=builder --chown=app:app /app/node_modules ./node_modules
COPY --from=builder --chown=app:app /app/dist          ./dist
COPY --chown=app:app package*.json ./

USER app                                    # ⭐ بدون root اجرا می‌شود
EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "dist/main.js"]
```

### چرا Multi-stage؟

| بدون Multi-stage | با Multi-stage |
|-------------------|---------------|
| ایمیج ۱.۲ گیگابایت (با compiler و devDependency) | ⭐ ایمیج ۱۵۰ میلی‌بایت |
| سطح حمله‌ی بزرگ | فقط runtime |
| push کند | deploy سریع |

### 🔴 اشتباهات رایج در Dockerfile

```dockerfile
# ❌ ۱: اجرا با root
CMD ["npm", "start"]
# ✅ USER app در مرحله‌ی نهایی

# ❌ ۲: کپی کردن کل پروژه (شامل .env و node_modules)
COPY . .
# ✅ استفاده از .dockerignore

# ❌ ۳: پنهان کردن خطا در لاگ
RUN npm run build 2> /dev/null
# ✅ خطا باید build را متوقف کند

# ❌ ۴: هر دستور یک لایه (ایمیج بزرگ)
RUN apt-get update
RUN apt-get install curl
RUN rm -rf /var/lib/apt/lists/*
# ✅ یک لایه، تمیزکاری در همان دستور
```

### .dockerignore

```
node_modules
dist
.env
.env.*
.git
*.md
coverage
Dockerfile
.dockerignore
```

## ۷. Docker Compose — چند سرویس با هم

> 🧒 **داستان این بخش:** کار تو فقط خودِ برنامه نیست. یک دیتابیس هم می‌خواهد،
> یک کش هم، و یک صف هم. و هر بار که پروژه را از نو شروع می‌کنی، باید این سه تا
> را با تنظیمات درست بالا بیاوری — و این کار چند ساعت طول می‌کشد.
>
> راه‌حل این بود که کلِ این مجموعه را در **یک فایل** بنویسی: چه سرویس‌هایی،
> با چه نسخه‌ای، با چه پورتی، و به چه ترتیبی. بعد با یک دستور همه با هم بالا
> می‌آیند و با یک دستور پاک می‌شوند.
>
> نکته‌ی عملی: سرویسِ اول نباید به سرویسِ دوم وابسته باشد، مگر آنکه دومی **آماده**
> باشد. این انتظار را خودِ ابزار مدیریت می‌کند — وگرنه برنامه‌ی تو با شانسِ
> نصف اجرا می‌شود.
>
> **این بخش جواب می‌دهد:** یک فایل compose چه چیزی را تعریف می‌کند،
> شبکه‌ی داخلیِ ظرف‌ها چگونه کار می‌کند، و چطور محیط توسعه را از محیط

```yaml
services:
  app:
    build: .
    ports: ['3000:3000']
    environment:
      DATABASE_URL: postgres://app:pass@db:5432/app
      REDIS_URL: redis://redis:6379
    depends_on:
      db: { condition: service_healthy }
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: pass          # ⚠️ فقط برای توسعه!
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U app']
      interval: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru

volumes:
  pgdata:
```

> 🔑 نکته‌ی حیاتی: `depends_on` به‌تنهایی کافی نیست — اپ ممکن است قبل از آماده شدن دیتابیس به آن وصل شود. `condition: service_healthy` این را حل می‌کند. (در یک اپ واقعی، retry logic در خود کد هم لازم است.)

## ۸. CI/CD — خط لوله‌ی خودکار

> 🧒 **داستان این بخش:** تیمی که هر تغییر را دستی روی سرورِ تست می‌گذاشت، یک شب
> فراموش کرد. فردا صبح آن نسخه روی سرورِ اصلی بود — و خراب.
>
> مشکل همان یک جمله است: **انسان**. هر جایی که آدم باید یادش بماند، یک بار
> فراموش می‌شود. پس کاری کنیم که آدم یادش نماند.

> خط لوله یعنی هر بار که کد را push می‌کنی، یک سرورِ خودکار: تست‌ها را اجرا
> می‌کند، لینت را می‌گیرد، و اگر همه‌چیز سبز بود — **بیلد** می‌گیرد و
> منتشر می‌کند. نه کمتر، نه بیشتر.
>
> **این بخش جواب می‌دهد:** هر مرحله از خط لوله دقیقاً چه می‌کند، چرا ترتیبِ
> مراحل مهم است (تستِ ارزان اول، تستِ گران بعد)، و چه وقت انتشار باید **خودکار**

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: 'npm' }

      - run: npm ci

      - run: npm run lint          # ① سبک کد
      - run: npm run typecheck     # ② بررسی تایپ
      - run: npm run test:coverage # ③ تست + پوشش
      - run: npm audit --audit-level=high  # ④ امنیت وابستگی‌ها

      - run: docker build -t app:test .
      - run: docker run --rm app:test npm run test:e2e
```

> 🔑 **قاعده:** اگر یکی از مراحل شکست خورد، **deploy انجام نمی‌شود**. این تنها چیزی است که CI واقعاً انجام می‌دهد.

## ۹. Deployment — گزینه‌ها

> 🧒 **داستان این بخش:** قبلاً کد را روی سرور کپی می‌کردی و فایل را reload
> می‌کردی. ولی آن سرور خاموش شد. و جایی برای کپی کردن نبود. و راه‌حل این
> بود که با سرورِ خودت حرف بزنی.

> اولین لایه: ماشین مجازی. یک سیستم‌عاملِ کامل را شبیه‌سازی می‌کنی. راحت
> است ولی سنگین.
>
> لایه‌ی بعد: **سرورِ بی‌نام** (serverless). دیگر سرور نداری؛ فقط **کد** را
> می‌دهی و شرکت برایت اجرا می‌کند و اندازه می‌گیرد. سال ۲۰۱۴ با AWS Lambda
> این مدل برای عموم شد.
>
> هیچ‌کدام بهترین نیست. هر کدام یک هزینه دارد که بقیه ندارند.
>
> **این بخش جواب می‌دهد:** سه گزینه‌ی اصلیِ استقرار چه تفاوتی دارند، و

| روش | مناسب برای | پیچیدگی |
|-----|-----------|----------|
| **VPS + PM2** | پروژه‌ی کوچک، یک سرور | کم |
| **Docker Compose روی سرور** | اپ متوسط | کم |
| **Kubernetes** | تیم بزرگ، ده‌ها سرویس | 💀 زیاد |
| **PaaS (Render, Railway, Fly)** | نمونه‌ی اولیه | خیلی کم |
| **Serverless (Lambda)** | ترافیک نوسانی و قابل پیش‌بینی | کم |

> 💡 **قاعده:** Kubernetes را یاد نگیر مگر واقعاً لازم باشد. برای ۹۰٪ پروژه‌ها، Docker Compose + یک load balancer کافی است. Kubernetes پیچیدگی‌ای می‌افزاید که معمولاً توجیه ندارد.

### استراتژی‌های استقرار

| استراتژی | توضیح | ریسک |
|---------|-------|------|
| **Recreate** | کل سرویس را خاموش و روشن کن | ⛔ قطعی سرویس |
| **Rolling** | کم‌کم نمونه‌های جدید جایگزین قدیمی می‌شوند | ✅ کمترین ریسک |
| **Blue-Green** | دو محیط کامل؛ ناگهان سوییچ | ⭐ صفر قطعی، هزینه‌ی دو برابر |
| **Canary** | ۵٪ ترافیک به نسخه‌ی جدید | ✅✅ ایمن‌ترین |

### دقیقاً چه اتفاقی می‌افتد؟

- **Blue-Green** (آبی-سبز): دو محیط کامل و مستقل داری — «آبی» (نسخه‌ی فعلی و سالم) و «سبز» (نسخه‌ی تازه). اول سبز را بالا می‌آوری و **تمام تست‌ها را روی سبز اجرا می‌کنی**؛ تا وقتی سبز سالم است هیچ تغییری برای کاربران رخ نمی‌دهد. بعد فقط یک‌بار ترافیک را از آبی به سبز سوییچ می‌کنی. اگر خراب شد، برگشتش تقریباً **آنی** است. هزینه‌اش: همیشه دو نسخه بالا می‌مانند، یعنی دو برابر منابع.

- **Canary** (کاناری — پرنده‌ی آزمایشی در معدن): یک **درصد کوچک** از ترافیک واقعی (مثلاً ۵٪) به نسخه‌ی جدید می‌رود و ۹۵٪ به نسخه‌ی قدیمی. عملاً یعنی یک load balancer جلوی دو نسخه است و درخواست‌ها را بر اساس یک نسبت مشخص (یا با hash کردن شناسه‌ی کاربر، تا هر کاربر همیشه یک نسخه را ببیند) بین آن‌ها پخش می‌کند. اگر نرخ خطا یا کندی در آن ۵٪ بالا رفت، همان لحظه درصد را صفر می‌کنی و هیچ‌کس جز شما آسیب ندیده.

### چرا Graceful Shutdown اینجا حیاتی است؟

در Rolling Update، نسخه‌ی قدیمی باید درخواست‌های در حال پردازشش را تمام کند:

```
سرور جدید: ████ آماده
سرور قدیمی:      ▓▓▓▓▓▓ خالی می‌شود
```

اگر `SIGTERM` را مدیریت نکنی، درخواست‌های در حال اجرا **قطع** می‌شوند و کاربر خطا می‌بیند. (این را در [فاز ۶](فاز-۰۶-کش-و-صف.md) دیدیم.)

## ۱۰. مشاهده‌پذیری (Observability) — سه ستون

> 🧒 **داستان این بخش:** ساعت ۴ بامداد یک سیستم کند می‌شود. صبح که رسیدی،
> هیچ‌کس نگفته بود کجا خراب شده. یکی می‌گفت دیتابیس، یکی می‌گفت شبکه.
> سه روز صرف کردی تا بفهمی.
>
> مشکل این بود که وقتی سیستم خراب می‌شود، خودش نمی‌گوید چه‌طور. اگر از قبل
> **ابزارِ اندازه‌گیری** نگذاشته باشی، آن موقع هیچ داده‌ای نداری که نگاه کنی.
>
> راه‌حل سه‌ستونی است: **لاگ** (رویدادها)، **معیار** (اعدادِ کلی مثل زمان
> پاسخ)، و **ردِابی** (مسیرِ یک درخواست از ابتدا تا انتها). مثل سه
> دوربینِ متفاوت که یک حادثه را از سه زاویه می‌بینند.
>
> **این بخش جواب می‌دهد:** سه ستون چه چیزی به تو می‌گویند که دو تای دیگر نمی‌گویند،

**Observability / مشاهده‌پذیری**: بتوانی از روی خروجی‌های سیستم (لاگ، متریک، ردیابی) بفهمی **درون آن چه می‌گذرد**، بدون اینکه از قبل حدس زده باشی چه چیزی را باید نگاه کنی. یعنی سیستم خودش به‌قدر کافی «حرف می‌زند» که تو بتوانی سؤال بپرسی و جواب بگیری.

**تفاوت با Monitoring** (پایش)، که قاطی‌شان می‌شود:

| | Monitoring | Observability |
|---|-----------|---------------|
| فرضش | از قبل می‌دانیم چه چیزی خراب می‌شود | نمی‌دانیم؛ هر خرابی تازه‌ای ممکن است پیش بیاید |
| کارش | نگاه کردن به چند نمودارِ از پیش تعیین‌شده | پاسخ دادن به هر سؤال دلخواه، روی داده‌ی خام |
| ابزار | داشبورد و alert ثابت | لاگ، متریک و trace با هم |

- **به زبان ساده:** monitoring مثل ترمومتر ماشین است — می‌گوید دما بالاست. observability مثل داشبورد کامل است — با دیدن همه‌ی چراغ‌ها می‌فهمی **چرا** دما بالا رفته.
- **چرا مهم است اینجا:** سیستم‌ها خرابی‌هایی می‌دهند که هیچ‌کس از قبل پیش‌بینی‌شان نکرده. اگر فقط monitoring داشته باشی، برای هر خرابی تازه باید اول alert بنویسی و بعد بفهمی چه شده.

سه ستون، سه نوع داده که با هم این کار را می‌کنند:

| ستون | سؤالی که جواب می‌دهد | ابزار |
|-------|---------------------|-------|
| **Logs** (لاگ) | چه اتفاقی افتاد؟ | Pino، Loki |
| **Metrics** (متریک) | وضعیت سیستم چیست؟ | Prometheus، Grafana |
| **Traces** (ردیابی) | کجای مسیر کند شد؟ | OpenTelemetry، Jaeger |

> 🔑 مثال: **«سفارش‌ها خیلی کند شد.»**
> - Logs: خطای اتصال به پرداخت در ۵۰۰ درخواست
> - Metrics: نرخ خطای `payment-service` از ۰٫۱٪ به ۱۲٪ رفت
> - Traces: نشان می‌دهد کدام تکه‌ی کاری (بازه یا span) زمان گرفته
>
> هر سه با هم، **۲ دقیقه** تا تشخیص. فقط یکی؟ ساعت‌ها.

### ۱۰.۱ Metrics — چهار نوع اصلی

**متریک** یک عدد است که وضعیت سیستم را در یک لحظه خلاصه می‌کند (برخلاف لاگ که یک رویداد را ثبت می‌کند). مسیر هر عدد مشخص است: کد شما با `increment` یا `observe` آن را تولید می‌کند، بعد هر چند ثانیه یک برنامه (در Prometheus به اسم **scraper**) مقادیر را جمع می‌کند و یک **Time Series Database** نگه می‌دارد.

انتخاب نوع درست متریک، مهم‌ترین تصمیم اینجاست — نوع غلط یعنی یا داده‌ی بی‌استفاده، یا انفجار حجم:

- **Counter** (شمارنده): عددی که فقط **می‌رود بالا** و هیچ‌وقت خودش کم نمی‌شود (مگر ری‌استارت شود). مثل «از ابتدای ساعت چند بار پرداخت شد؟». برای نرخ‌ها از این استفاده می‌کنی و در پایان دوره‌ی زمانی با یکی دیگر تقسیم می‌کنی تا «در دقیقه» به دست آید.
- **Gauge** (سنجه): عددی که **بالا و پایین می‌شود** — وضعیت لحظه‌ای را نشان می‌دهد. مثل «الان ۴۲ درخواست در صف است» یا «الان ۱.۲ گیگابایت حافظه مصرف شده». اینجا مقدارِ همین لحظه مهم است، نه مجموع.
- **Histogram** (بافت‌نما / توزیع): مدت‌ها را در **سطل‌های از پیش تعیین‌شده** می‌اندازد و می‌شمارد که چندتا زیر ۱۰ms بود، چندتا بین ۱۰ تا ۵۰ms. خروجی‌اش فقط یک عدد نیست؛ مجموعه‌ای از شمارنده‌ها به‌علاوه‌ی صدک‌ها (p50, p95, p99) می‌دهد. برای سنجش **تأخیر** تنها انتخاب درست همین است.
- **Summary** (خلاصه): شبیه Histogram ولی فقط چند صدک مشخص را نگه می‌دارد و درصدها را دقیق‌تر می‌دهد. تفاوت کلیدی: چند نمونه‌ی جدا از سرورها را نمی‌توان با هم **ادغام** کرد و صدک درست به دست آورد، ولی برای یک پروسه یا یک سرویس تنها کاملاً درست است.

```
Counter    : فقط بالا می‌رود    http_requests_total
Gauge      : بالا و پایین       memory_usage_bytes, queue_length
Histogram  : توزیع مقادیر        http_request_duration_seconds
Summary    : مشابه Histogram    (بدون قابلیت merge)
```

```typescript
// پترن کلیدی: meter و histogram
import { metrics } from 'prom-client';

const httpDuration = new metrics.Histogram({
  name: 'http_request_duration_seconds',
  help: 'مدت درخواست‌های HTTP',
  labelNames: ['method', 'route', 'status'] as const,
  buckets: [0.005, 0.01, 0.05, 0.1, 0.3, 0.5, 1, 3, 5],
});

// ⚠️ نکته: labelNames را کنترل کن — اگر userId را label بگذاری، انفجار کاردینالیتی!
```

> 🔴 **انفجار کاردینالیتی (Cardinality Explosion):**
>
> **کاردینالیتی** یعنی «چند ترکیب متمایز از برچسب‌ها را برای یک متریک ذخیره می‌کنی؟». یک متریک با برچسب‌های `method` و `route` شاید ۳۰ ترکیب داشته باشد — کاملاً قابل مدیریت. ولی اگر برچسبی بگذاری که خودش مقدار یکتا دارد (مثل `user_id` یا `request_id` یا URL خام)، ترکیب‌ها منفجر می‌شوند: با ۱۰۰ هزار کاربر، ۱۰۰ هزار سری وقت‌سری جداگانه ساخته می‌شود. Prometheus این‌ها را نگه نمی‌دارد و از حافظه می‌میرد؛ داشبورد هم کند می‌شود.
>
> قاعده: هر برچسب باید از یک **مجموعه‌ی کوچک و بسته** بیاید: اگر `route` را `/users/12345` بگذاری، هر کاربر یک سری زمانی جدید می‌سازد و Prometheus می‌میرد. **همیشه از الگو** استفاده کن: `req.route.path` نه `req.originalUrl`.

### ۱۰.۲ RED — چه متریکی را واقعاً جمع کنیم؟

**RED** مخفف سه واژه است و از کتاب *Google SRE Book* آمده — روشی که گوگل انتخاب می‌کند کدام سه متریک برای **هر سرویس** کافی است:

- **R — Rate** (نرخ): چند **درخواست در ثانیه** به سرویس می‌رسد. این عدد پایه است؛ تقریباً هر تصمیمی درباره‌ی ظرفیت با همین گرفته می‌شود.
- **E — Errors** (خطاها): چند **درخواست با خطا** شکست خورد (کد وضعیت ۵xx، یا خطای زمان‌اتمام). نرخ خطا معمولاً به‌صورت نسبت خطا به کل نرخ سنجیده می‌شود.
- **D — Duration** (مدت): هر درخواست چقدر طول کشید. این را با **صدک‌ها** نگاه کن، نه میانگین.

هر سه، به تفکیک مسیر (`/checkout` در برابر `/profile`) — چون یک مسیر می‌تواند سالم باشد و مسیر دیگر خراب.

```
RED برای هر مسیر:  rate = 230 req/s   errors = 12 req/s (5.2%)   duration: p50=45ms  p95=1.8s  p99=4.2s
                                                                       └─ p95 و p99 مهم‌اند، نه میانگین
```

- **چرا «صدک» و نه میانگین؟** چون میانگین حوصله‌سربر می‌آورد. اگر ۹۵ درصد درخواست‌ها ۴۰ میلی‌ثانیه باشند و ۵ درصد ۸ ثانیه، میانگین ۴۳۰ میلی‌ثانیه است — عددی که **هیچ کاربری تجربه نکرده**. p95 یعنی «۹۵ درصد کاربران سریع‌تر از این تجربه کرده‌اند»؛ p99 دقیقاً همان ۵ درصدِ بدحال را نشان می‌دهد.
- **اینجا چه چیزی لازم است؟** یک هشدار (alert) فقط روی **rate خطا**. درباره‌ی مدت (duration) هشدار نده؛ آن را در داشبورد ببین و قبل از اینکه کاربر حس کند، برطرفش کن. اگر روی هر سه هشدار بدهی، هشدارهای بی‌ربط و خسته‌کننده می‌سازی.

> 💡 **چرا نه هزار متریک؟** RED نگفت که بقیه را بردار و جمع نکن. می‌گوید هر سرویس **دست‌کم** این سه را داشته باشد. بیشتر تیم‌ها ده‌ها متریک دارند و هیچ‌کدام را نمی‌بینند. ۱۰ متریک خوب از ۱۰۰ متریک بی‌استفاده بهتر است — چون هر متریکِ اضافه، بار ذخیره‌سازی و کار اضافه است و هیچ تصمیمی را بهتر نمی‌کند.

### ۱۰.۳ Distributed Tracing — دنبال کردن یک درخواست

**Tracing** (ردیابی): دنبال کردن مسیر یک **درخواست واحد** از لحظه‌ای که کاربر کلیک می‌کند تا لحظه‌ای که پاسخ برمی‌گردد. متریک می‌گوید «کندی هست»؛ tracing می‌گوید «این درخواست مشخص، در این سرویس مشخص، ۲ ثانیه معطل شد».

سه واژه‌ی لازم:

- **Trace** (ردّ): کل مسیر یک درخواست از ابتدا تا انتها. یک شناسه‌ی یکتا دارد.
- **Span** (بازه): **یک تکه‌ی کاری** داخل آن ردّ — مثلاً «اجرای کوئری دیتابیس در Payment Service» یا «خواندن فایل در Order Service». هر span زمان شروع و پایان و پدر دارد؛ مجموعه‌ی span‌ها درخت می‌سازند.
- **`trace_id`**: همان شناسه‌ی یکتای ردّ. کلید فهم الگوی propagation است.

**الگوی انتشار (Propagation)**: در معماری میکروسرویسی یک درخواست از چند سرویس رد می‌شود و هیچ‌کدام نمی‌دانند شناسه‌ی ردّ چیست. راه‌حل: سرویس اول یک `trace_id` می‌سازد و در هدر (مثلاً `x-trace-id`) می‌فرستد؛ هر سرویس بعدی آن را **می‌خواند، به کار خودش می‌بندد، و باز به سرویس بعدی می‌فرستد**. اگر درخواستی بدون `trace_id` رسید (کسی نفرستاده یا هدرش گم شده)، سرویس خودش یکی می‌سازد. در نهایت همه‌ی span‌ها با همان یک شناسه جمع می‌شوند و یک درخت زمانی می‌سازند.

**چرا این الگو مهم است:** بدون آن، تشخیص مشکل فقط از راه حدس زدن است. با آن، می‌توانی بگویی «این trace خاص، ۲ ثانیه در Payment Service گم شد».

```
[کاربر] → [NGINX] → [API Gateway] → [Order Service] → [Payment Service] → [DB]
            └───── trace_id: 8f3a2b1c ─────────────────────────────────┘

زمان:  0ms      2ms        8ms          45ms            240ms        242ms
        └─ DNS ─┘└─ parse ─┘└─ validate ┘└─ call + retry×2 ┘└── SQL ──┘
                                    ⭐ مشکل اینجاست: ۲ بار retry!
```

هر سرویس `trace_id` را در هدر دریافت و به سرویس بعدی می‌فرستد — یعنی همان الگوی انتشار، در عمل:

```typescript
// در هر سرویس: استخراج و ادامه‌ی trace
const incoming = req.headers['x-trace-id'];
req.traceId = incoming ?? crypto.randomUUID();
res.setHeader('x-trace-id', req.traceId);   // ⭐ به سرویس بعدی هم بفرست
```

## ۱۱. Structured Logging — چرا JSON؟

> 🧒 **داستان این بخش:** لاگِ کلاسیک مثل متنِ نامه است: «کاربر ۴۲۴۲ وارد شود».
> حالا می‌خواهی بدانی **چند** بار این اتفاق افتاد. یک انسان باید بخواند و بشمارد،
> و برای گزارشِ هر روز این کار هزار بار انجام می‌شود.

> اگر لاگ **ساختاریافته** باشد — یعنی هر چیز یک کلید با مقدار داشته باشد —
> ماشین می‌تواند بخواند، بشمارد، گروه‌بندی کند و نمودار بسازد. آدم فقط
> نتیجه را نگاه می‌کند.

> یک قانونِ ساده هم هست که همه فراموشش می‌کنند: **شناسه‌ی درخواست** را در
> هر خط بگذار. بدون آن، لاگِ یک درخواست از هزار تا، تکه‌تکه و بی‌معنا می‌شود.
>
> **این بخش جواب می‌دهد:** چرا JSON خواندن و فیلتر کردن را آسان می‌کند، و چرا

```typescript
import pino from 'pino';

const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'],
  // ⭐ حذف خودکار داده‌های حساس
});

// ✅ استفاده
logger.info({ userId: 'u123', orderId: 'o456', durationMs: 45 }, 'سفارش ثبت شد');

// ❌ نه این
logger.info(`کاربر ${userId} سفارش ${orderId} ثبت کرد`);
```

| قالب | مزیت | عیب |
|-------|------|------|
| متن ساده (`userId=123`) | خوانا برای چشم | قابل جستجوی ساخت‌یافته نیست |
| JSON | ⭐ قابل فیلتر، تجمیع، و نمودار | برای چشم کمتر خواناست |

> 💡 **قانون:** هرگز رشته‌های پویا در پیام نگذار — داده را در فیلد جدا بگذار. این تنها راه جستجوی درست است.

### سطوح لاگ

| سطح | کِی | مثال |
|------|-----|------|
| `trace` | جزئیات داخلی | مقدار هر تابع |
| `debug` | عیب‌یابی توسعه | «کوئری اجرا شد» |
| `info` | رویدادهای عادی | «کاربر وارد شد» |
| `warn` | چیزی غیرعادی ولی قابل بازیابی | «rate limit نزدیک شد» |
| `error` | عملیات شکست خورد | «پرداخت ناموفق بود» |
| `fatal` | کل سیستم مرده | «دیتابیس در دسترس نیست» |

## ۱۲. Health Check و Graceful Shutdown

> 🧒 **داستان این بخش:** سیستم را به‌روزرسانی کردی. نسخه‌ی جدید بالا آمد، ولی
> همان لحظه پردازشِ کاری را شروع کرد — در حالی که هنوز کامل بالا نیامده بود.
> و پردازش‌های قبلی، وسطِ کار، کشته شدند.
>
> نتیجه: چند دقیقه خطا برای کاربران. و این اتفاق آن‌قدر تکرار شد که به یک
> عادت تبدیل شد — و عادت یعنی دیگر کسی نمی‌پرسد چرا.
>
> دو پاسخ لازم بود. یکی: سرور بگوید «من **آماده‌ام**» — و تا وقتی نگفته، ترافیک
> نگیر. دومی: وقتی می‌خواهد خاموش شود، **اول** درخواست‌های در جریان را تمام
> کند، **بعد** بمیرد.
>
> **این بخش جواب می‌دهد:** تفاوت بررسیِ سلامت (زنده‌ام؟) با بررسیِ آمادگی
> (آماده‌ام؟)، و چرا «خاموشیِ محترمانه» از قطعِ ناگهانی خیلی بهتر است.

### دو نوع health check

| نوع | چه می‌گوید | کِی استفاده |
|-----|----------|-------------|
| **Liveness** | «زنده‌ام؟» | اگر نه → کانتینر را ری‌استارت کن |
| **Readiness** | «آماده‌ی ترافیک هستم؟» | اگر نه → ترافیک نفرست، ولی ری‌استارت نکن |

```typescript
// ⭐ تفاوت حیاتی:
// Liveness: اگر دیتابیس قطع باشد، نباید کانتینر را ری‌استارت کنی!
// Readiness: اما نباید هم ترافیک بفرستی

app.get('/health/live', (req, res) => {
  res.json({ status: 'ok' });            // همیشه ok اگر پروسه زنده است
});

app.get('/health/ready', async (req, res) => {
  const checks = await Promise.allSettled([
    db.ping(),
    redis.ping(),
  ]);

  const healthy = checks.every(c => c.status === 'fulfilled');
  res.status(healthy ? 200 : 503).json({
    status: healthy ? 'ok' : 'degraded',
    checks: Object.fromEntries(
      checks.map((c, i) => [[
        ['db', 'redis'][i], c.status === 'fulfilled' ? 'ok' : 'fail',
      ]])
    ),
  });
});
```

> 🔴 **اشتباه مرگبار:** اگر health check لایونِس‌کارت را چک کند، یک قطعی موقت دیتابیس باعث **ری‌استارت زنجیره‌ای** همه‌ی کانتینرها می‌شود. قطعی ۵ ثانیه‌ای دیتابیس → کل سیستم ری‌استارت → قطعی بلندتر. چرخه‌ی مرگ.

## ۱۳. مدیریت اسرار و پیکربندی

> 🧒 **داستان این بخش:** برنامه‌ات را روی لپ‌تاپت اجرا کردی و کار کرد. همان کد
> را روی سرور گذاشتی و کار نکرد — چون کلیدِ اتصال به سرویسِ پیام‌کننده، روی
> لپ‌تاپ بود و روی سرور نبود.
>
> اگر برای هر محیط، کد را **دستی عوض** کنی، یک روز فراموش می‌کنی — و آن روز،
> کدِ محیطِ توسعه روی محیطِ اصلی نشسته. یعنی جایی که هر کسی دسترسی دارد.
>
> راه‌حل: کد یکی است؛ **تنظیمات** از بیرون می‌آید. و تنظیماتِ حساس هیچ‌وقت
> داخل کد نمی‌آید — نه حتی داخل تنظیماتِ نسخه‌بندی‌شده.
>
> **این بخش جواب می‌دهد:** اصلِ «پیکربندی بیرون از کد» یعنی چه، تفاوتِ
> محیطِ توسعه و اصلی در چه چیزی باید فرق کند، و کجا کلیدهایت را بگذاریم.

```
۱۲ factor app: پیکربندی از محیط، نه از کد
```

**اسرار** (Secrets) چیزهایی‌اند که اگر لو بروند، امنیت کل سیستم می‌ریزد: رمز دیتابیس، کلید امضای توکن، API Key. برخلاف پیکربندی، اسرار **نباید** داخل کد یا فایل `.env` داخل گیت باشند.

دو ابزار نگهداری اسرار:

- **Vault** (سرویس HashiCorp): یک سرور مرکزی که اسرار را ذخیره می‌کند، با نسخه‌بندی، انقضا، و امکان چرخش خودکار (rotation). برنامه در زمان اجرا از آن می‌خواند، نه از روی دیسک.
- **KMS** (سرویس مدیریت کلید، مثل AWS KMS یا Google Cloud KMS): سخت‌افزار سازنده نگه می‌دارد و برای **رمزگشایی** باید درخواست بدهی؛ خود کلید هیچ‌وقت از آن بیرون نمی‌آید. کاربردش بیشتر رمزنگاری داده‌ها و امضای توکن است تا نگهداری رمز عبور.

هر دو یک اصل مشترک دارند: **کد فقط یک نشانی می‌گیرد، نه خودِ اسرار** — و اپ می‌تواند در startup بررسی کند که اسرار لازم واقعاً موجودند، وگرنه بالا نمی‌آید.

| نوع | مکان | مثال |
|-----|------|------|
| پیکربندی | متغیر محیطی | `PORT`, `LOG_LEVEL` |
| اسرار | Vault / KMS | کلید دیتابیس، JWT_SECRET |
| تنظیمات هر محیط | فایل جدا | `.env.development`, `.env.production` |

```typescript
// ✅ الگوی بارگذاری پیکربندی
import { z } from 'zod';

const schema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  REDIS_URL: z.string().url().optional(),
});

// ⚠️ در production: اگر چیزی ناقص بود، اپ نباید بالا بیاید
export const config = schema.parse(process.env);
```

## ۱۴. Rollback — شبکه‌ی ایمنی نهایی

> 🧒 **داستان این بخش:** ساعت ۲ بامداد نسخه‌ی جدید منتشر شد. ساعت ۳ فهمیدی مشتری‌ها
> دارند شکایت می‌کنند. اولین فکر: «برگرد». ولی وقتی نگاه کردی، نسخه‌ی
> قبلی **هم پاک شده بود**.

> این فاجعه‌ی رایجی است: راه‌حلِ جالب برای سریع کردنِ کار، حذفِ چیزی است که
> به آن نیاز داشتی. مشکل این است که **لحظه‌ای که لازمش داری، دیر است**.
>
> قاعده‌ی طلایی: هر تغییری باید **برگشت‌پذیر** باشد. یعنی دقیقاً بدانی
> با چه دستوری برمی‌گردانی، و آن را **قبل از** انتشار امتحان کرده باشی.
>
> **این بخش جواب می‌دهد:** Rollback چیست، چه چیزی را قابل بازگشت می‌کند (کد) و
> چه چیزی را نه (داده)، و چه سه چیزی باید هر بار پیش از انتشار آماده باشد.

```
تغییر بد → مستقر کن → مشاهده کن → اگر خراب بود → برگرد
```

> 🔑 **قاعده:** هیچ تغییری در production نباید **غیرقابل برگشت** باشد. اگر نمی‌توانی در ۵ دقیقه برگردی، آن تغییر را دو بخش کن.

**راهبردهای Rollback:**

| راهبرد | توضیح |
|---------|-------|
| **Rollback سریع** | نسخه‌ی قبلی ایمیج را دوباره deploy کن |
| **Forward Fix** | یک deploy کوچک دیگر با رفع باگ |
| **Feature Flag** | ویژگی جدید را با یک سوییچ روشن/خاموش کن — بدون deploy |
| **Canary + Kill Switch** | نسخه‌ی جدید را خاموش کن |

```typescript
// ✅ Feature Flag — امن‌ترین راه انتشار تدریجی
if (flags.isEnabled('new-checkout', { userId })) {
  return newCheckoutFlow(cart);
}
return oldCheckoutFlow(cart);      // مسیر قدیمی هنوز هست
```

> 💡 **Feature Flag vs Config Flag:** اگر رفتار عوض می‌شود، Feature Flag. اگر فقط زمان/آدرس تغییر می‌کند، Config Flag.

#flashcards

**کارت ۱ — تفاوت تست unit و integration؟**
Unit یک تابع را جدا تست می‌کند (بدون I/O). Integration چند جزء واقعی را با هم تست می‌کند (مثلاً API + دیتابیس). بیشتر باگ‌های واقعی در مرزها هستند، پس تست integration مهم‌تر از آنچه فکر می‌کنی.

**کارت ۲ — چرا Dockerfile را باید چندمرحله‌ای بنویسی؟**
چون مرحله‌ی build شامل compiler و devDependency است (ایمیج ۱ گیگابایتی). مرحله‌ی production فقط runtime را کپی می‌کند (ایمیج ۱۵۰ میلی‌بایتی). سریع‌تر، کوچک‌تر، سطح حمله کمتر.

**کارت ۳ — تفاوت Liveness و Readiness؟**
Liveness می‌پرسد «پروسه زنده است؟» — اگر نه، کانتینر ری‌استارت شود. Readiness می‌پرسد «آماده‌ی ترافیک هست؟» - اگر نه، فقط ترافیک نفرست. اگر liveness را به دیتابیس گره بزنی، قطعی دیتابیس باعث ری‌استارت زنجیره‌ای می‌شود.

**کارت ۴ — تفاوت XSS و CSRF از نظر دفاع چیست؟**
XSS دفاعش escape + CSP است. CSRF دفاعش SameSite + توکن CSRF است. این‌ها متفاوت‌اند چون مکانیسم حمله متفاوت است: تزریق اسکریپت در برابر استفاده‌ی ناخواسته از هویت تو.

**کارت ۵ — چرا `req.route.path` را به‌جای `req.originalUrl` در متریک بگذاری؟**
چون `originalUrl` شامل شناسه‌ی یکتا است (`/users/12345`)، که هر کاربر یک سری وقت‌سریع جدید می‌سازد. `route.path` الگو می‌دهد (`/users/:id`) و تعداد سری‌ها محدود می‌ماند.

**کارت ۶ — چرا JSON log بهتر از متن ساده است؟**
چون می‌توانی فیلدها را جدا جستجو و تجمیع کنی (`level = "error" AND userId = "123"`). در متن ساده، جستجو تقریباً ناممکن است.

**کارت ۷ — Feature Flag چه مشکلی را حل می‌کند که Rollback نمی‌کند؟**
اگر تغییر را با Feature Flag منتشر کنی، می‌توانی بدون deploy سوییچش را خاموش کنی و در **یک ثانیه** همه را برگردانی. Rollback نیاز به deploy دارد که دقیقه‌ها طول می‌کشد.

**کارت ۸ — تفاوت CI و CD؟**
CI (Continuous Integration): هر بار merge می‌شود، کد خودکار تست می‌شود. CD (Continuous Delivery/Deployment): بعد از تست، خودکار منتشر می‌شود (تحویل) یا با تأیید انسان (استقرار).
