# فاز ۱۱ — RAG (بازیابی و تولید با داده)

> 🧒 **داستان:** سال ۲۰۱۸، آدم‌ها با مدل‌های زبانی یک مشکلِ عجیب داشتند: مدل
> هرچه می‌پرسیدی، جوابِ **مطمئن** می‌داد — و خیلی وقت‌ها جوابش را از خودش ساخته بود.
> درباره‌ی قوانینِ یک کشورِ خاص پرسیدی، جوابی می‌داد که هیچ‌جای دنیا
> ننوشته بود. محصول را با چند دستور به‌روز کنی، نه با آموزش دوباره.
>
> راه‌حل درست همان چیزی بود که آدم‌ها هزاران سال در کتابخانه‌ها می‌کردند:
> اول **پیدا کن**، بعد **بخوان**. یعنی سؤال را بپرس، قطعه‌های مرتبط را از میان
> هزاران صفحه بیرون بکش، و **فقط با همان‌ها** جواب بده.
>
> همین، ایده‌ی کاملِ این فاز است. به آن می‌گویند RAG — بازیابی و تولید.
> مدل را **آموزش نمی‌دهی**؛ فقط کتابی جلویش می‌گذاری که در آن لحظه
> باز کند.
>
> فاصله‌ی این با آموزش دادن مثل فاصله‌ی باز کردنِ کتاب با حفظ کردنِ کتاب است.
> اولی همیشه تازه‌تر است و هزینه‌ای ندارد. دومی ماه‌ها طول می‌کشد.
>
> این فاز از همان‌جا شروع می‌شود: چطور کاری کنیم که مدل از **سندِ تو** جواب بدهد،
> و از هر جای دیگری — و چطور بفهمیم اگر جواب را پیدا نکرد، صادقانه بگوید.

## مقدمه: مسئله‌ای که RAG حل می‌کند

**RAG** سرنامِ *Retrieval-Augmented Generation*، به فارسی **تولید تقویت‌شده با بازیابی**: به‌جای اینکه مدل فقط از حافظه‌ی آموزشی‌اش جواب بدهد، اول از اسناد تو **چیزهای مرتبط را بازیابی** می‌کند و بعد با همان‌ها جواب می‌سازد. یعنی «اول پیدا کن، بعد جواب بده».

در مقابل، **Fine-tuning** یعنی **تنظیم دوباره‌ی خودِ مدل**: با داده‌ی مثال‌های خودت دوباره آموزش می‌دهی تا سبک، لحن، یا قالب خروجی‌اش عوض شود. فرقش این است که Fine-tuning وزن‌های مدل را تغییر می‌دهد، ولی RAG اصلاً مدل را دست نمی‌زند — فقط ورودی‌اش را غنی می‌کند.

مدل زبانی سه مشکل بنیادی دارد:

```
۱. دانشش قدیمی است      ← تا تاریخ آموزش، نه امروز
۲. از تو چیزی نمی‌داند    ← مستندات شرکت تو را ندیده
۳. نمی‌تواند استناد کند  ← نمی‌گوید این جواب از کجا آمده
```

**RAG** هر سه را حل می‌کند — بدون اینکه مدل را دوباره آموزش بدهی.

> 💡 **تشبیه:** مدل مثل دانشجوی باهوشی است که هرچه در کتاب‌های عمومی نوشته شده می‌داند، ولی کتاب‌های **شرکت شما** را ندیده. RAG یعنی قبل از هر سوال، کتاب‌های شرکت را جلویش بگذاری و بگویی «فقط از همین جواب بده».

### RAG در برابر Fine-tuning

| | RAG | Fine-tuning |
|--|-----|-------------|
| **هزینه** | کم | زیاد |
| **سرعت** | فوری | هفته‌ها |
| **به‌روزرسانی داده** | ⭐ آپلود فایل جدید | آموزش دوباره |
| **تغییر رفتار** | فقط دانش | دانش + سبک + فرمت |
| **استناد** | ✅ منبع را داری | ❌ نداری |
| **مناسب برای** | دانش اختصاصی و متغیر | تغییر **سبک** و **فرمت** |

> 🔑 **قاعده:** اول RAG. فقط وقتی RAG جواب نداد، سراغ fine-tuning برو. اکثر پروژه‌های واقعی فقط RAG لازم دارند.

## ۱. قطعه‌بندی (Chunking) — مهم‌ترین تصمیم طراحی

> 🧒 **داستان این بخش:** یک کتاب ۴۰۰ صفحه‌ای را می‌خواهی به مدل بدهی. نمی‌شود —
> هم جا نمی‌شود، هم مدل وسطش حواسش پرت می‌شود. پس باید تکه‌تکه‌اش کنی.
>
> ولی کجا بشکنی؟ اگر وسطِ یک جمله بشکنی، دو تکه می‌شود که هیچ‌کدام
> **به‌تنهایی** معنا نمی‌دهند. و بعد پیدا کردن یک تکه به‌درد‌بخور،
> شانسی می‌شود.
>
> راه‌حل: تکه‌ها را **در مرزهای معنی** بشکن — اول پاراگراف، بعد جمله، و
> اگر لازم شد کلمه. و هر تکه را کمی با تکه‌ی قبل و بعدش **هم‌پوشان** بده تا
> جمله‌ای که وسط بود، از دست نرود.
>
> این تصمیم پرعیب‌ترین جای کل RAG است. تکه‌ی کوچک = دقتِ بیشتر ولی
> زمینه‌ی کمتر. تکه‌ی بزرگ = زمینه‌ی بیشتر ولی نویز. هیچ فرمولی ندارد.
>
> **این بخش جواب می‌دهد:** چه روش‌هایی برای شکستن سند هست، چرا مرزِ معنی از
> برشِ با طول برتر است، و چطور با اندازه‌گیری (فصل ۸) بهترین اندازه را پیدا کنیم.

### چرا قطعه‌بندی؟

**قطعه** (`chunk`) یعنی تکه‌ای از سند که پر از یک موضوع و معناست — نه یک جمله، نه یک صفحه، بلکه «یک واحد قابل بازیابی». کل ایده این است: سند بزرگ را به چند قطعه بشکن تا بعداً بتوانی فقط همان ۵ تای مرتبط را به مدل بدهی، نه کل ۵۰۰ صفحه را.

مدل context محدودی دارد. کتاب ۵۰۰ صفحه‌ای را نمی‌توان یک‌جا داد. پس باید **تکه‌تکه** کنی.

- **به زبان ساده:** کتاب را نمی‌شود یک‌جا به کسی داد. باید صفحه‌ها را جدا کنی و بعداً فقط صفحه‌های مرتبط را بدهی.

### 🔴 مشکل: اگر قطعه‌ها بد باشند، هیچ چیز کار نمی‌کند

```
قطعه‌ی بد: جداسازی وسط یک جمله → جمله‌ی ناقص → بی‌معنا
قطعه‌ی بد: خیلی بزرگ → حاوی اطلاعات نامرتبط → سردرگمی مدل
قطعه‌ی بد: خیلی کوچک → جمله‌ی جدا از معنا → بی‌فایده
```

| اندازه‌ی قطعه | نتیجه |
|---------------|--------|
| خیلی کوچک (۱۰۰ کلمه) | ⭐ محتوا ناقص، معنا گم می‌شود |
| متوسط (۵۰۰ کلمه) | ✅ معمولاً بهترین برای اسناد متنی |
| بزرگ (۲۰۰۰ کلمه) | نویز زیاد، دقت پایین |
| خیلی بزرگ (کل سند) | ❌ context پر می‌شود، دقت می‌ریزد |

### روش‌های قطعه‌بندی

**۱. قطعه‌ی ثابت (Fixed-size)**

```python
chunks = [
    text[i:i+1000]
    for i in range(0, len(text), 1000)      # ساده ولی وسط جمله می‌بُرد
]
```

**۲. قطعه‌بندی ساختاری — بهترین برای متن ساختاریافته**

```python
# ✅ بر اساس ساختار سند: عنوان، پاراگراف، بخش
chunks = []
current = []
current_len = 0

for para in document.paragraphs:
    if current_len + len(para) > MAX_CHUNK:
        chunks.append("\n\n".join(current))
        current, current_len = [], 0
    current.append(para)
    current_len += len(para)
```

**۳. قطعه‌بندی معنایی — بهترین کیفیت**

```python
# بر اساس **شباهت معنایی**، نه طول
# وقتی شباهت دو جمله‌ی متوالی از آستانه کمتر شد → مرز قطعه
def semantic_chunk(text: str, threshold: float = 0.5) -> list[str]:
    sentences = split_sentences(text)
    embeddings = embed(sentences)                 # ⭐ از مدل embedding استفاده می‌کند

    chunks, current = [], [sentences[0]]
    for i in range(1, len(sentences)):
        similarity = cosine(embeddings[i], embeddings[i-1])
        if similarity < threshold:                 # تغییر موضوع ← قطع
            chunks.append(" ".join(current))
            current = [sentences[i]]
        else:
            current.append(sentences[i])
    chunks.append(" ".join(current))
    return chunks
```

### Overlap — همپوشانی

اگر مرز قطعه‌ها دقیقاً روی یک جمله‌ی مهم بیفتد، آن جمله از دست می‌رود.

```
بدون overlap:  [جمله ۱ تا ۵] | [جمله ۶ تا ۱۰]
                                ⚠️ جمله ۵ نیمه‌کاره!

با overlap:    [جمله ۱ تا ۵] | [جمله ۴ تا ۱۰]
                            ^^^                ↑
                      جمله ۴ و ۵ در هر دو قطعه هست
```

```python
def chunk_with_overlap(text: str, size: int = 1000, overlap: int = 200) -> list[str]:
    step = size - overlap                          # ⭐ همپوشانی یعنی گام کوچک‌تر از اندازه
    return [text[i:i+size] for i in range(0, len(text), step) if text[i:i+size].strip()]
```

> 💡 **قاعده:** همپوشانی ۱۰ تا ۲۰٪ اندازه‌ی قطعه، تقریباً همیشه مفید است. ولی هزینه‌ی ذخیره‌سازی را بالا می‌برد.

```python
chunks.append({
```

## ۲. Embedding — تبدیل متن به عدد

> 🧒 **داستان این بخش:** کاربر می‌نویسد «چطور سرم درد می‌کند ولی تب ندارم؟» و
> سندِ تو درباره‌ی «میگرن بدون تب» است. هیچ کلمه‌ای مشترک نیست — ولی
> هر دو درباره‌ی یک چیز‌اند.
>
> جست‌وجوی معمولی فقط **حرف** را می‌بیند. ولی Embedding (تکِبُرداری) متن را
> به یک **فهرست از اعداد** تبدیل می‌کند که معنی را نشان می‌دهد. متن‌های
> نزدیک، عددهای نزدیک دارند. یعنی «شبه‌حرفی» را می‌شود **ریاضی** کرد.
>
> ایده‌ی اصلی از یک کشف ساده آمد: **کلمه‌هایی که در جمله‌های مشابه به کار
> می‌روند، در فضا هم نزدیک‌اند.** «پزشک» و «دکتر» هرگز کنار هم نمی‌آیند، ولی
> در فضا نزدیک‌اند.
>
> **این بخش جواب می‌دهد:** Embedding دقیقاً چه می‌کند، «فاصله» بین دو بردار یعنی
> چه، و مهم‌تر: چه وقت **مدلِ زبانیِ جاسوسی** این کار را خراب می‌کند.

### چیست؟

- **به زبان ساده:** تبدیل یک جمله به یک **فهرست اعداد** که «معنای» آن را نشان می‌دهد. دو جمله با معنای مشابه، اعداد نزدیک دارند.
- **به زبان فنی:** بردار با ابعاد بالا (۳۰۰ تا ۴۰۹۶ عدد) که در فضای برداری، زاویه‌ی بین آن‌ها **شباهت معنایی** را نشان می‌دهد.

```
"سگ"            → [0.21, -0.13, 0.87, ..., 0.05]    ← نزدیک به
"این حیوان خانگی" → [0.19, -0.15, 0.84, ..., 0.03]
"بانک مرکزی"     → [0.75, 0.32, -0.41, ..., 0.66]   ← دور
```

### سنجش شباهت

شباهت کسینوسی اندازه می‌گیرد **دو بردار چقدر هم‌جهت‌اند**، نه چقدر به هم نزدیک. نتیجه عددی بین ۰ تا ۱ است: ۱ یعنی کاملاً هم‌جهت (شباهت معنایی کامل)، ۰ یعنی بی‌ربط. برای همین به طول بردارها حساس نیست — که در متن خوب است، چون جمله‌ی بلندتر لزوماً معنای متفاوت‌تری ندارد.

```
cosine_similarity(A, B) = (A · B) / (|A| × |B|)
```

> ⚠️ **برخلاف برداشت رایج:** این کار **معنا** را نمی‌فهمد؛ فقط **الگوی آماری متن** را می‌فهمد. پس «تهران پایتخت است» و «پایتخت تهران است» عالی کار می‌کند، ولی «قیمت ۱۰۰ هزار تومان است» در برابر «قیمت ۱۰۰ هزار ریال است» — معنای مخالف، ولی شباهت بالا.

### مقایسه‌ی مدل‌های embedding

**ابعاد** (dimensions) یعنی تعداد عددهای هر بردار. و این فقط یک عدد تزئینی نیست: هر بعد یک صفتِ معنایی است که مدل آموخته. پس ۱۵۳۶ بعد یعنی مدل فضای «ریزتری» برای جدا کردن مفاهیم دارد و دقتش بالاتر است — به قیمت **حجم و هزینه‌ی بیشتر**: ذخیره‌سازی و جستجو روی بردار ۱۵۳۶ تایی سنگین‌تر از ۳۸۴ تایی است. ضمناً باید با ابعاد ستون دیتابیس هم بخواند؛ عوض کردن مدل یعنی ساختن جدول از نو.

| مدل | کیفیت | ابعاد | هزینه | زبان فارسی |
|-----|--------|-------|-------|-----------|
| مدل‌های OpenAI | خوب | 1536–3072 | $$ | متوسط |
| مدل‌های Cohere | عالی | 1024 | $$$ | متوسط |
| **مدل‌های Open-Source** | خوب | 768–1024 | رایگان | ⭐ بهتر |
| Sentence-Transformers | خوب | 384–1024 | رایگان | ✅ خوب |

> 💡 اگر محتوایت فارسی است، **حتماً مدل را روی داده‌ی فارسی تست کن.** مدل‌های انگلیسی‌محور روی فارسی ضعیف‌تر عمل می‌کنند.

## ۳. پایگاه‌داده‌ی برداری (Vector Database)

> 🧒 **داستان این بخش:** یک کتابخانه‌ی بزرگ را تصور کن که هزاران کتاب دارد. ولی
> کتاب‌ها را **بر اساس موضوع** چیده، نه بر اساس الفبا. یعنی «موضوعِ کتاب»
> روی جلد نوشته و تو مستقیم می‌روی سراغ قفسه‌ی درست.
>
> این دقیقاً کاری است که پایگاه‌داده‌ی برداری می‌کند. ولی تفاوت این است که
> «موضوع» یک کلمه نیست — یک فهرست از صدها عدد است. و پیدا کردنِ نزدیک‌ترین
> به این فهرست، کاری است که با **تقریب** انجام می‌شود، نه با دقیق.
>
> همین یک تفاوت، همه‌چیز را می‌سازد: به‌جای «دقیقاً پیدا کن»، می‌گویی
> «۱۰ تای **نزدیک‌ترین** را بده». و همین، جست‌وجوی معنایی را ممکن می‌کند.
>
> **این بخش جواب می‌دهد:** پایگاه‌داده‌ی برداری چه چیزی اضافه می‌کند، جست‌وجوی
> تقریبی (ANN) یعنی چه، و کِی اصلاً لازم نیست یکی بسازی.

**پایگاه‌داده‌ی برداری** دیتابیسی است که به‌جای ستون‌های متنی، **بردار** ذخیره می‌کند و می‌تواند سریع پیدا کند «کدام بردار به این بردار نزدیک‌تر است». یعنی به‌جای `LIKE '%تهران%'` می‌پرسی «کدام قطعه **معناش** شبیه این سؤال است؟»

### چرا دیتابیس معمولی کافی نیست؟

```
دیتابیس SQL:  WHERE content LIKE '%تهران%'     ← تطبیق متنی، نه معنایی
برداری:        WHERE embedding <=> query_vector   ← تطبیق معنایی
```

### عملگر `<=>` چیست؟

این عملگر معمولاً یعنی **فاصله‌ی کسینوسی** (کمتر = نزدیک‌تر). یعنی «کدام قطعه **معناش** شبیه‌تر است؟»

### گزینه‌ها

چطور انتخاب کنی؟ با این سه سؤال: (۱) دیتابیس رابطه‌ای همین حالا داری؟ → pgvector. (۲) حجم خیلی بالا و سرعت حیاتی است؟ → یک موتور تخصصی مثل Qdrant. (۳) فقط نمونه‌ی اولیه‌ی سریع یا کار آفلاین/تحقیقاتی؟ → Chroma یا FAISS.

| گزینه | نوع | بهترین برای |
|-------|-----|-----------|
| **pgvector** | افزونه‌ی PostgreSQL | ⭐ اکثر پروژه‌ها — دیتابیس از قبل داری |
| **Qdrant** | تخصصی، رایگان | حجم بالا، سرعت بهینه |
| **Weaviate** | تخصصی، رایگان | امکانات غنی |
| **Chroma** | سبک، محلی | نمونه‌ی اولیه، تست سریع |
| **Pinecone** | ابری، مدیریت‌شده | نمی‌خواهی خودت اداره کنی |
| **FAISS** | کتابخانه (نه دیتابیس) | تحقیق، آفلاین |

> 💡 **توصیه‌ی عملی:** اگر همین حالا PostgreSQL داری، **pgvector** را نصب کن. یک دیتابیس کمتر، یک منبع حقیقت واحد، تراکنش مشترک. برای شروع کاملاً کافی است.

### با pgvector

**HNSW** (سرنامِ *Hierarchical Navigable Small World*) نوعی **ایندکس تقریبی** است: به‌جای اینکه هر بردار را با تک‌تکِ بردارهای دیگر مقایسه کند (که با رشد مجموعه کند می‌شود)، بردارها را در یک ساختار درختیِ چندلایه می‌چیند و فقط مسیرهای نزدیک را می‌پیماید. نتیجه: جستجوی نزدیک‌ترین همسایه در مقیاس میلیون‌ها قطعه، از چند دقیقه به چند میلی‌ثانیه می‌رسد — با دقتی که عملاً کافی است.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          BIGSERIAL PRIMARY KEY,
  content     TEXT NOT NULL,
  metadata    JSONB NOT NULL DEFAULT '{}',
  embedding   vector(1024),              -- ⭐ ابعاد مدل تو
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- ⭐ ایندکس HNSW برای جستجوی سریع نزدیک‌ترین همسایه
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- جستجو
SELECT content, metadata,
       embedding <=> $1::vector AS distance
FROM chunks
WHERE metadata->>'category' = 'billing'      -- ⭐ فیلتر متادیتا
ORDER BY embedding <=> $1::vector
LIMIT 5;
```

> 🔑 **قاعده:** همیشه **اول متادیتا را فیلتر کن، بعد شباهت برداری**. اگر برعکس، باید روی کل مجموعه جستجو کنی و بعد فیلتر کنی — کند است.

## ۴. بازیابی (Retrieval) — چند راهبرد

> 🧒 **داستان این بخش:** کتابخانه هزار کتاب دارد. کاربر می‌گوید «درباره‌ی خواب
> بگو». تو می‌توانی **همه‌ی** هزار کتاب را بدهی — و مدل گمراه می‌شود.
> یا می‌توانی **فقط پنج تای مرتبط** را بدهی — و جواب دقیق می‌شود.
>
> مسئله این است که «مرتبط» را چطور تشخیص می‌دهی. سه راهبردِ ساده: **فقط
> معنا** (بردارها)، **فقط حرف** (کلیدواژه)، و **هر دو با هم**. راه سوم معمولاً
> بهترین است — چون یکی معنایی قوی دارد و دیگری دقیق.
>
> و یک راهبرد چهارم که خیلی مهم است: **ترکیبی از چند جست‌وجو** (Hybrid).
> وقتی سؤال پیچیده است، چند زاویه را هم‌زمان بپرس و نتیجه‌ها را یکی کن.
>
> **این بخش جواب می‌دهد:** هر راهبرد چه چیزی را خوب پیدا می‌کند و چه چیزی را
> از دست می‌دهد، و چرا ترکیبِ «معنا + کلیدواژه» از هرکدام به‌تنهایی بهتر است.

### ب) جستجوی کلیدواژه‌ای (Keyword / BM25)

**BM25** روشی است که در صدها مقاله و داکیومنت رسمی به‌عنوان استاندارد جستجوی کلیدواژه‌ای استفاده می‌شود: کلمه‌هایی که کمتر در مجموعه آمده‌اند وزن بیشتری می‌گیرند، و کلمه‌های پرتکرار مثل «را» یا «که» عملاً بی‌اثر می‌شوند. جستجوی متنی در PostgreSQL و Elasticsearch زیر همین نام شناخته می‌شود.

فقط متن. بهترین برای: «کد خطای E-4021» یا نام محصول.

### ج) ترکیبی (Hybrid) — ⭐ بهترین

```python
def hybrid_search(query: str, k: int = 5) -> list[Chunk]:
    # ① جستجوی معنایی
    semantic = vector_db.search(embed(query), k=k * 2)

    # ② جستجوی کلیدواژه‌ای
    keyword = bm25_search(query, k=k * 2)

    # ③ ترکیب با Reciprocal Rank Fusion
    return reciprocal_rank_fusion(semantic, keyword, k=k)

def reciprocal_rank_fusion(*result_lists, k: int = 60) -> list:
    """
    RRF: امتیاز هر نتیجه = Σ 1 / (k + rank)
    مزیت: نیازی به وزن‌دهی دستی ندارد
    """
    scores = defaultdict(float)
    for results in result_lists:
        for rank, item in enumerate(results, start=1):
            scores[item.id] += 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)[:k]
```

> 💡 **چرا ترکیب؟** جستجوی معنایی در «معنا» قوی است ولی در **کلمات دقیق** (شماره، کد، نام خاص) ضعیف. جستجوی کلیدواژه برعکس. ترکیب، بهترین هر دو را می‌گیرد.

## ۵. Reranking — چرا و چگونه

> 🧒 **داستان این بخش:** یک آگهی شغلی گذاشته‌ای. صد نفر فرستادند. تو سریع
> ۲۰ نفرِ «نزدیک‌ترین» را جدا می‌کنی. ولی برای صد نفر، نفرِ اول لزوماً
> **بهترین** نیست — فقط از بقیه به سؤال نزدیک‌تر بود.
>
> Reranking دقیقاً همین کار را می‌کند: اول با روش سریع ۲۰ تای برتر را پیدا
> کن، بعد با یک روش **کندتر ولی دقیق‌تر** آن ۲۰ تا را دوباره رتبه‌بندی کن و
> ۵ تای آخر را تحویل بده.
>
> این یک معامله‌ی کلاسیک است: کارِ ارزان برای غربال، کارِ گران برای دقت.
> دقیقاً مثل کارمندی که اول همه‌ی رزومه‌ها را سریع رد می‌کند و بعد چندتای
> باقی‌مانده را با دقت می‌خواند.
>
> **این بخش جواب می‌دهد:** reranker چه می‌کند، چرا ارزان‌تر و دقیق‌تر از
> جست‌وجوی برداری است، و در چه اندازه‌ی کتابخانه واقعاً ارزشش را دارد.

Rerank را با دو نوع مدل می‌فهمیم: **bi-encoder** جداگانه برای سؤال و قطعه بردار می‌سازد و بعد با کسینوس مقایسه می‌کند — سریع ولی سطحی. **Cross-encoder** (رمزگشای متقابل) سؤال و قطعه را *باهم* خوانده و یک عدد می‌دهد «این قطعه چقدر مرتبط است؟» پس هر دو معماری از یک خانواده‌اند، ولی cross-encoder کندتر و دقیق‌تر است؛ به همین دلیل برای ۲۰ تا ۵۰ نتیجه‌ی آخر که کیفیت مهم است، از cross-encoder استفاده می‌کنیم.

### مسئله

جستجوی برداری باید **سریع** باشد. ولی کیفیتش متوسط است — قطعه‌ی مرتبط ممکن است رتبه ۷ باشد در حالی که قطعه‌ی مرتبط‌تر رتبه ۱۵ است.

> **به زبان ساده:** کارآموز می‌آید و ۵۰ کارت را دسته‌بندی می‌کند. مدیر ارشد می‌آید و از بین آن‌ها بهترین ۵ را انتخاب می‌کند.

```
جستجوی برداری:  ۵۰۰ قطعه → ۲۰ قطعه      (سریع، کیفیت متوسط)
Reranking:       ۲۰ قطعه → ۵ قطعه‌ی نهایی   (کندتر، کیفیت عالی)
```

```python
# Cross-encoder — دقیق‌ترین روش، ولی گران
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")   # مدل چندزبانه، فارسی خوب

query = "چطور درخواست مرجوعی بدهم؟"
results = vector_db.search(embed(query), k=20)         # ① ۲۰ نتیجه

scores = reranker.predict([(query, r.content) for r in results])
final = [r for _, r in sorted(zip(scores, results), key=lambda x: x[0], reverse=True)][:5]
```

> ⚠️ Cross-encoder هر **جفت** (سؤال، قطعه) را جدا پردازش می‌کند، پس کند است. فقط برای ۲۰-۵۰ نتیجه‌ی اول استفاده کن، نه برای کل مجموعه.

> 🔑 **Reranking یکی از بیشترین بهبودهای کیفیت در RAG است** و خیلی‌ها آن را نمی‌سازند. اگر RAG تو ضعیف است، اول این را اضافه کن.

## ۶. ساخت Prompt — از قطعه تا جواب

> 🧒 **داستان این بخش:** کتابخانه کتاب‌های درست را آورده. ولی کتاب‌ها را **چطور**
> می‌دهی؟ اگر همه را بدون توضیح بدهی، مدل نمی‌داند کدام را جدی بگیرد. اگر
> بگویی «فقط از این‌ها استفاده کن» و واقعاً هم بدهی، جواب قابل اعتماد می‌شود.
>
> سه تکه‌ی دستور که هر RAGِ خوبی دارد: قطعه‌ها را بده، بگو **فقط** از همین
> استفاده کن، و بگو اگر جواب **پیدا نشد**، صریح بگو که پیدا نشد.
>
> موردِ سوم مهم‌ترین قسمت است. بدون آن، مدل یک جوابِ **روان** می‌سازد از
> چیزی که تو نداده‌ای — یعنی همان توهمی که می‌خواستی حذفش کنی.
>
> **این بخش جواب می‌دهد:** چه سه دستوری پرامپت RAG را از توهم جدا می‌کند، و
> چرا «فقط از این سند» باید هم در دستور باشد و هم در **داده** جدا نگه داشته شود.

### ❌ خطای رایج: context زیاد

**راه‌حل: فشرده‌سازی context**

```python
def build_context(chunks: list[Chunk], max_tokens: int = 4000) -> tuple[str, list[int]]:
    selected, used, kept_ids = [], 0, []

    for i, chunk in enumerate(chunks, start=1):
        chunk_tokens = estimate_tokens(chunk.content)
        if used + chunk_tokens > max_tokens:
            break
        selected.append(f"[{i}] {chunk.content}")
        kept_ids.append(i)
        used += chunk_tokens

    return "\n\n---\n\n".join(selected), kept_ids
```

> 🔑 **قاعده:** کیفیت context از حجم آن مهم‌تر است. **۵ قطعه‌ی دقیق** بهتر از **۲۰ قطعه‌ی نصفه‌نیمه** است.

## ۷. RAG ساده در برابر RAG پیچیده

> 🧒 **داستان این بخش:** یک نفر می‌خواهد آب دوش را درست کند. به‌جای باز کردن
> شیر، سه پمپ و یک سیستم هوشمند نصب می‌کند. شیر خراب بود.
>
> رایج‌ترین اشتباهِ RAG همین است: از روز اول یک سیستم چندمرحله‌ای با
> مسیریابی و تکرار و حافظه می‌سازند، در حالی که مشکل اصلی فقط این بود که
> قطعه‌ها غلط بودند.
>
> قانونِ مهندسی این است: **اول ساده، بعد درست، بعد سریع**. نسخه‌ی اول باید
> آن‌قدر کوچک باشد که در یک روز ساخته شود. اگر نسخه‌ی اول را نتوانستی
> بسازی، هنوز مسئله را نفهمیده‌ای.
>
> **این بخش جواب می‌دهد:** حداقلِ قابل‌قبول یک RAG چیست، چه چیزی را باید
> **به‌تعویق** انداخت، و چه چیزی را هرگز نباید ساخت.

| سطح | معماری | چه زمانی |
|------|---------|---------|
| **پایه** | قطعه‌بندی ثابت → جستجوی برداری → prompt | MVP، اسناد کم |
| **متوسط** | + قطعه‌بندی ساختاری + Rerank + Hybrid | ⭐ بیشتر پروژه‌های واقعی |
| **پیشرفته** | + مسیریابی پرس‌وجو + بازیابی سلسله‌مراتبی + خلاصه‌سازی | مجموعه‌های بزرگ و پرسش‌های متنوع |
| **پیچیده** | + Agentic RAG + گراف دانش + حافظه | محصولات پژوهشی |

> 💡 **قاعده:** از ساده شروع کن. **اول ساده کار کند، بعد پیچیده کن.** اکثر تیم‌ها در حالی که پایه درست نشده، یک معماری پیچیده می‌سازند و بعد نمی‌توانند بفهمند کجا خراب است.

### مسیریابی پرس‌وجو — میان‌بر هوشمند

**مسیریابی پرس‌وجو** یعنی قبل از جستجو، تشخیص بدهی **این سؤال از چه نوعی است** و بفرستی‌اش مسیر درست — به‌جای اینکه هر سؤال را با همان یک روش بفرستی. یک سؤال که «کد خطای E-4021» می‌پرسد، مسیر کلیدواژه‌ای می‌خواهد؛ سؤالی که «چند ساعت کار کرده‌ام» می‌پرسید، مسیر محاسبه.

```python
    if re.search(r"اخیر|جدید|امروز|۱۴۰۴|۲۰۲۵", question):
        return hybrid_search(question, k=5, 
                             filter={"created_at": "> now() - 90d"})

    # ③ نیاز به محاسبه دارد؟ → مسیر متفاوت
    if re.search(r"چند|محاسبه|مجموع|درصد", question):
        return aggregate_search(question)

    # ④ پیش‌فرض: معنایی + rerank
    return hybrid_with_rerank(question, k=5)
```

## ۸. ارزیابی RAG — از کجا بدانیم کار می‌کند؟

> 🧒 **داستان این بخش:** پرسیدی «قطعه‌بندی را بهتر کردم». ولی از کجا بدانی
> **بهتر** شده؟ جواب‌ها به نظر درست‌تر می‌آیند، ولی شاید فقط چند تا از آن‌ها
> بهتر شده و بقیه بدتر.
>
> مشکل این است که RAG دو جای خرابی دارد که به هم قاطی می‌شوند: شاید
> **قطعه‌ی درست** پیدا نشده، یا شاید پیدا شده و **مدل** نتوانسته از آن
> استفاده کند. اگر ندانی کدام، داری در جای اشتباه دنبال مشکل می‌گردی.
>
> راه‌حل: جدا اندازه بگیر. اول بپرس «آیا قطعه‌ی درست در نتایج بود؟» و
> بعد بپرس «آیا جواب، از همان قطعه درست بود؟». اولی مربوط به بازیابی است، دومی
> مربوط به پرامپت.
>
> **این بخش جواب می‌دهد:** دو معیارِ جدا برای بازیابی و تولید چیست، چه
> **دیتاستِ کوچکی** برای شروع کافی است، و چرا «۳۰ تا نمونه‌ی دستی» شروعِ

### شاخص‌های کلیدی

| بخش | شاخص | یعنی چه؟ | چگونه اندازه بگیریم؟ |
|-----|-------|---------|---------------------|
| بازیابی | **Recall@k** | قطعه‌ی درست در ۵ اول هست؟ | آیا جواب در context آمد؟ |
| بازیابی | **Precision@k** | چند تا از ۵ تا واقعاً مرتبط‌اند؟ | نسبت قطعات مرتبط |
| تولید | **Faithfulness** | پاسخ فقط از context آمده؟ | آیا جمله‌ای بدون منبع دارد؟ |
| تولید | **Answer Relevance** | جواب به سؤال مربوط است؟ | ارزیابی انسانی یا LLM |

### ارزیابی خودکار با LLM-as-Judge

```python
async def evaluate_rag(answer: str, context: str, question: str) -> dict:
    judge = await client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1000,
        system="""تو ارزیاب RAG هستی. برای هر معیار نمره ۱ تا ۵ بده.

معیارها:
- faithfulness: آیا پاسخ فقط و فقط از context آمده؟
- relevance: آیا پاسخ به سؤال مربوط است؟
- completeness: آیا پاسخ کامل است؟

فقط JSON برگردان: {"faithfulness": n, "relevance": n, "completeness": n, "reason": "..."}""",
        messages=[{
            "role": "user",
            "content": f"سؤال: {question}\n\nContext: {context}\n\nپاسخ: {answer}",
        }],
        temperature=0,
    )
    return json.loads(judge.content[0].text)
```

## ۱۰. الگوی پیاده‌سازی کامل

> 🧒 **داستان این بخش:** همه‌ی بخش‌های قبل تکه‌های پازل بودند. پازلِ ناتمام یعنی
> سیستمی که هرگز کامل نمی‌شود.
>
> این بخش خط لوله‌ی کامل را از سند تا جواب کنار هم می‌گذارد: سند می‌آید، تکه
> می‌شود، تبدیل به عدد می‌شود، ذخیره می‌شود. سؤال می‌آید، عدد می‌شود،
> نزدیک‌ها پیدا می‌شوند، دوباره رتبه‌بندی می‌شوند، و در قالبِ پرامپت به مدل می‌رود.
>
> نکته‌ی عملی که در همه‌ی این فازها تکرار می‌شود: **هر مرحله را جدا تست کن.**
> اگر جواب بد بود، بدون تست نمی‌فهمی مشکل از کجاست — و در نیمه‌ی راهی
> می‌مانی که نه‌کدام کار نمی‌کند.
>
> **این بخش جواب می‌دهد:** هر مرحله از خط لوله دقیقاً چه ورودی و خروجی‌ای دارد،

```python
from dataclasses import dataclass

@dataclass
class RAGConfig:
    chunk_size: int = 1000
    chunk_overlap: int = 200
    top_k: int = 5              # نتیجه‌ی اولیه
    rerank_top_n: int = 20       # قبل از rerank
    context_max_tokens: int = 4000

class RAGPipeline:
    async def ingest(self, doc: Document) -> None:
        chunks = semantic_chunk(doc.content)
        for chunk in chunks:
            embedding = await self.embed(chunk)
            await self.vector_db.upsert({
                "content": chunk,
                "embedding": embedding,
                "metadata": {**doc.metadata, "chunk_index": i},
            })

    async def query(self, question: str, user_id: str) -> dict:
        # ① تعیین دامنه‌ی مجاز (فیلتر امنیتی)
        filters = {"tenant_id": get_tenant(user_id)}

        # ② بازیابی ترکیبی
        semantic = await self.vector_search(question, k=20, filters=filters)
        keyword  = await self.bm25_search(question, k=20, filters=filters)
        candidates = reciprocal_rank_fusion(semantic, keyword)[:20]

        # ③ rerank
        final = await self.rerank(question, candidates)[:5]

        # ④ ساخت context
        context, used_ids = build_context(final, self.config.context_max_tokens)

        # ⑤ تولید با استناد
        response = await self.llm.generate(
            system=self.system_prompt(context),
            user=question,
        )

        # ⑥ لاگ برای دیباگ
        self.log_query(question, [c.id for c in final], response)

        return {
            "answer": response.text,
            "sources": [c.metadata for c in final if c.id in used_ids],
        }
```

> 🔑 **نکته‌ی مرحله ۶:** بدون لاگ کردن اینکه **چه چیزی بازیابی شد**، هیچ‌وقت نمی‌توانی دیباگ کنی چرا جواب بد بود. این را حتماً ثبت کن.

#flashcards

**کارت ۱ — RAG چه سه مشکلی را حل می‌کند؟**
دانش قدیمی مدل، ندانستن مستندات اختصاصی، و ناتوانی در استناد. RAG با تزریق داده‌ی به‌روز و قابل استناد در پیام، هر سه را حل می‌کند.

**کارت ۲ — چرا قطعه‌بندی (chunking) مهم‌ترین تصمیم است؟**
چون اگر قطعه‌ها نامناسب باشند، حتی بهترین مدل و بهترین جستجو جواب نمی‌دهد. قطعه‌ی خیلی بزرگ = نویز، خیلی کوچک = بی‌معنا. میانه (۵۰۰ کلمه) معمولاً بهترین است.

**کارت ۳ — همپوشانی (overlap) چه فایده‌ای دارد؟**
اگر مرز قطعه‌ها روی یک جمله‌ی مهم بیفتد، آن جمله بیرون می‌ماند. همپوشانی یعنی دو قطعه‌ی متوالی ۱۵۰ کلمه مشترک دارند تا هیچ جمله‌ای گم نشود.

**کارت ۴ — تفاوت جستجوی معنایی و کلیدواژه‌ای؟**
معنایی: بر اساس شباهت برداری، «شرایط مرجوعی» را با «چطور پس بدهم» پیدا می‌کند. کلیدواژه‌ای: بر اساس متن دقیق، «E-4021» را پیدا می‌کند. اولی در معنا قوی، دومی در کلمات دقیق. ترکیب بهترین است.

**کارت ۵ — Reciprocal Rank Fusion چیست؟**
روشی برای ترکیب چند نتیجه‌ی جستجو بدون نیاز به وزن‌دهی دستی. امتیاز هر نتیجه = مجموع ۱/(k + رتبه). نتایجی که در چند روش بالا آمده‌اند، بالاتر می‌آیند.

**کارت ۶ — چرا Reranking مهم است؟**
جستجوی برداری برای سرعت بهینه است ولی کیفیتش متوسط. Rerank ۲۰ نتیجه‌ی اول را با یک مدل دقیق‌تر (Cross-encoder) مرتب می‌کند. اگر RAG ضعیف است، اول Rerank اضافه کن.

**کارت ۷ — تفاوت Recall و Faithfulness؟**
Recall: آیا قطعه‌ی حاوی پاسخ، در نتایج بازیابی آمده؟ (کیفیت بازیابی). Faithfulness: آیا پاسخ فقط از همان context آمده؟ (کیفیت تولید).

**کارت ۸ — چرا داده‌ی ساختاریافته (جدول) را نباید در RAG ریخت؟**
چون جستجوی معنایی روی اعداد و جدول ضعیف است. بهتر است داده‌ی ساختاریافته را به‌عنوان ابزار (function calling) در اختیار مدل بگذاری تا خودش کوئری بزند.
