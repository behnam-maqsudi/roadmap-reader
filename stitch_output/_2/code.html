چرا در سیستم‌های توزیع‌شده با نرخ عملیات بالا، استفاده از پروتکل 2PC (Two-Phase Commit) توصیه نمی‌شود و الگوی جایگزین استاندارد صنعتی چیست؟

// Anti-pattern: Blocking Distributed Coordinator distributed_tx.go 
// Phase 1: Prepare Phase holds locks across network partitions
err := coordinator.Prepare(ctx, []Participant{OrderSvc, PaymentSvc, StockSvc})
// CRITICAL HAZARD: If StockSvc stalls, locks remain held globally
if err != nil {
    coordinator.Rollback(ctx) // Latency spike & Cascading Thread Exhaustion
}

علت رد 2PC در سیستم‌های مقیاس‌پذیر:

پروتکل 2PC یک الگوی کاملاً همگام (Synchronous) و مسدودکننده (Blocking) است. تا زمان پاسخ تک‌تک مشارکت‌کنندگان، منابع و ردیف‌های پایگاه‌داده قفل می‌مانند. بروز پارتیشن شبکه (CAP Theorem) یا کندی یک گره، فوراً موجب انسداد رشته‌های سرور (Thread Starvation)، ایجاد گلوگاه SPOF و کاهش شدید吞吐量 (Throughput) کل سامانه می‌گردد.

کدام سناریو در الگوی Transactional Outbox نیازمند ثبت اجباری کلید یکتایی (Idempotency Key) در لایه مصرف‌کننده (Consumer) است؟

با توجه به ویژگی‌های تضمین تحویل سیستم‌های پیام‌رسان توزیع‌شده (مانند Apache Kafka یا RabbitMQ)، دقیق‌ترین پاسخ را انتخاب کنید.

task_alt پاسخ صحیح تایید شد: ضمانت At-Least-Once بروکر پیام

توضیح تحلیلی: پردازشگر Outbox پیام‌ها را تا زمان تایید قطعی مجدداً ارسال می‌کند. همچنین در صورت کرش کردن کانسومر پیش از Commit آفست، کافکا پیام را مجدداً به گره جانشین ارسال خواهد کرد. بدون Idempotency Key در پایگاه‌داده مصرف‌کننده، پردازش تکراری و ناهماهنگی وضعیت مالی رخ می‌دهد.
